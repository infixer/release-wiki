## 新機能

### バンドルアナライザーにルートのサマリー画面を追加（[#98787](https://github.com/vercel/next.js/pull/98787)）

> [!tip] 何ができるようになったか
> Turbopack のバンドルアナライザーのトップ（`/`）が、ルートのサマリー画面になった。個々のルートの分析は `/analyze` に移動した。以前は `/` を開くとルートを選ぶまで空のツリーマップが表示され、ルートのサイズを出すには全ルートの `analyze.data` を取得する必要があった。
>
> - **中身**: クライアントに送られるサイズが大きい上位 15 ルートを表示し、ルート検索もできる。各行はリンクなので新しいタブでも開ける
> - **仕組み**: 全ルートの raw・圧縮後・クライアントバンドルのサイズを Rust 側で事前計算し、1 つの `route-summaries.json` として出力する。ルートピッカーのラベルや比較時のルートごとの差分にも使われる
> - **補足**: 比較の操作は、ルートを選んだ分析ページに残る

📦 v16.4.0-canary.60 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### 比較ツリーマップでバンドルの増減を表示（[#98837](https://github.com/vercel/next.js/pull/98837)）

> [!tip] 何ができるようになったか
> バンドルアナライザーの比較ツリーマップで、各モジュールの大きさを「サイズの差分の絶対値」で表し、色で増えたか減ったかを示すようになった。
>
> - **補足**: 両方のスナップショットの変更モジュールから表示を組み立てるので、削除されたモジュールも見える。ソースマップで元をたどれない生成チャンクは、ソースモジュールとしてではなく `Unattributed output` にまとめて表示する
> - **関連**: 増減の色は [#99607](https://github.com/vercel/next.js/pull/99607) で比較画面全体の青・アンバーのテーマトークンに統一された

### facade を使ったエクスポート名マングリングをオプトインで有効にできるように（[#99309](https://github.com/vercel/next.js/pull/99309)）

> [!tip] 何ができるようになったか
> [#99285](https://github.com/vercel/next.js/pull/99285) のロールバックで、ローカル専用モジュールは既定では分割しないようになった（remote-components のシングルトンのリグレッション [#99279](https://github.com/vercel/next.js/issues/99279) を避けるため）。名前空間が外に漏れる場合でも短いキーの恩恵を受けたいアプリ向けに、facade を使ったマングリングをオプトインとして残した。
>
> - **使い方**: `experimental.turbopackMangleViaMaterializedNamespaceObject`。未指定なら、`turbopackMangleExportNames` を明示的に `true` にしたときだけ有効（canary の本番ビルドでの暗黙のマングリングでは有効にならない）。明示的な `false` が優先される
> - **注意**: 複数の部分に分割されたモジュールにパッチを当てるコードとの互換性のリスクが、設定のコメントに記載されている。本番の既定値は変わらない

### React Compiler のオプション `enablePreserveExistingMemoizationGuarantees` を追加（[#98589](https://github.com/vercel/next.js/pull/98589)）

> [!tip] 何ができるようになったか
> `reactCompiler.enablePreserveExistingMemoizationGuarantees` を next.config で指定できるようになり、Babel と実験的な Turbopack の Rust コンパイラの両方に渡される。省略した場合は、それぞれのコンパイラ実装の既定値のまま。
>
> - **使い方**: `reactCompiler: { enablePreserveExistingMemoizationGuarantees: false }` のように指定する（ドキュメント `reactCompiler.mdx` に追記）

📦 v16.4.0-canary.60 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### trace-server の MCP にメモリ・アロケーションの情報を追加（[#98546](https://github.com/vercel/next.js/pull/98546)）

> [!tip] 何ができるようになったか
> Turbopack の trace-server の MCP ツールで、メモリの調査ができるようになった。エージェントからのフィードバックをもとに使い勝手と性能も改善した。
>
> - **追加された情報**: 各スパンに `allocations` / `deallocations` / `persistentAllocations` / `allocationCount`（子を除いた `self*` 版も）、`memorySummary`、`heaviestSpanId`
> - **検索**: `search` が再帰的になり、`depth` / `pageSize` でサブツリーや広いページを 1 回の呼び出しで取得できる

## 変更・修正

### アップグレード関連の用語を「Agent」に統一し、`--ai` を `--agent` に（[#99545](https://github.com/vercel/next.js/pull/99545)）

> [!quote] Before
> アップグレードコマンドは `--ai` / `--experimental-ai` フラグを使い、テレメトリや設定にも「AI」の名前が使われていた。

> [!success] After
> フラグが `--agent` に置き換わり、アップグレードの推奨表示・DevTools のプロンプトも更新された。テレメトリのイベントは `NEXT_AGENT_UPGRADE_*`、設定（preferences）の名前空間は `agent-upgrade.*` になり、テレメトリのモジュール・型、完了レポーター、run ID の環境変数も改名された。

> [!warning] 移行が必要
> canary で `next upgrade --ai` や `--experimental-ai` を使っている場合は `--agent` に書き換える。

📦 v16.4.0-canary.60 · トピック: [[repos/vercel-next.js/topics/AI-アップグレード|AIアップグレード]]

### エージェントフィードバックの報告を確実に（[#99591](https://github.com/vercel/next.js/pull/99591)）

> [!quote] Before
> Codex や OpenCode が、アプリの問題を修正した後にフィードバック候補を捨ててしまうことがあった。また、レビュー URL を応答に含めるのはフォームを開けなかったときだけだったため、バックグラウンドで開いたタブが見つけにくかった。

> [!success] After
> エージェントが問題を解決・回避した後も、条件を満たすフィードバック候補を報告まで保持する。生成されたレビュー URL は、ブラウザのタブが開いたかどうかに関係なく最終応答に必ず含める。管理対象の `AGENTS.md` ブロックと報告プロトコルの説明も明確にした。

### `partialPrefetching` を指定していないと警告を表示（[#99452](https://github.com/vercel/next.js/pull/99452)）

> [!quote] Before
> `cacheComponents` を有効にしても、`partialPrefetching` を指定していないことについて何も表示されなかった。

> [!success] After
> `cacheComponents` が有効で `partialPrefetching` が明示されていないと、`true` か `false` を選ぶよう警告する。`false` は古い Cache Components アプリを段階的に移行するときだけに使うものだと説明し、移行ガイドへのリンクを表示する。

> [!warning] 移行が必要
> `cacheComponents` を使っている場合は `partialPrefetching` を明示的に設定する。新しいアプリは両方を有効にすることが推奨されている。PR によると、次のメジャーリリースで両機能はすべてのアプリで有効になり、古い設定オプションは削除される。

### シャロー URL 更新でクライアントの `params` がサスペンドしないよう修正（[#99611](https://github.com/vercel/next.js/pull/99611)）

> [!quote] Before
> Cache Components が有効なとき、`use(params)` や `use(searchParams)` を読むクライアントのページ・レイアウトが、`history.pushState` / `history.replaceState` のたび（およびその履歴の戻る・進むのたび）に最寄りの Suspense フォールバックを表示していた。数百ミリ秒内容が隠れるため、フォーカス中の入力欄がフォーカスを失い、キー入力が落ちていた（[#99512](https://github.com/vercel/next.js/issues/99512)）。

> [!success] After
> ナビゲーションによるレンダーでは `params` / `searchParams` はすでに分かっているので、Promise を最初から fulfilled（React が同期的に取り出せる `status` / `value` を設定済み）として作るようにし、サスペンドしなくなった。

📦 v16.4.0-canary.60 · トピック: [[repos/vercel-next.js/topics/ルーティング|ルーティング]]

### Turbopack: additional roots 内の `import.meta.url` でパニックしないよう修正（[#99511](https://github.com/vercel/next.js/pull/99511)）

> [!quote] Before
> `import.meta.url` が additional root 内のファイルにあると、Turbopack がパニックしていた。

> [!success] After
> additional root 内では `file:///@rootName/...` という仮の URL を返す。`import.meta.url` からの相対パスでファイルを読む一般的なケースはアナライザーが処理するので引き続き動き、外部化された node modules には影響しない。

### Turbopack のモジュールキャッシュを `Map` で保持（[#98947](https://github.com/vercel/next.js/pull/98947)）

> [!quote] Before
> Turbopack のランタイムはモジュールキャッシュを Object で保持していた。

> [!success] After
> `Map` で保持するようになり、`bench/module-cost` ではモジュール実行時間が client commonjs・pages api commonjs で約 4.4%、pages api esm で約 2.1% 短くなった。`require.cache` は、ランタイムモジュールが `Proxy` でモジュールキャッシュを Object として見せることで引き続きサポートされる。

### ESM エクスポートの受け渡しプロトコルを変えて出力を縮小（[#98932](https://github.com/vercel/next.js/pull/98932)）

> [!quote] Before
> ライブバインディングと循環参照のために ESM のエクスポートを getter として結び付けており、値そのものを渡すときは毎回 `0` のタグを付けて区別していた。

> [!success] After
> エクスポートの約 9 割を占める値の側ではなく、getter 関数の側にタグを付けるようにし、出力のバイト数を少し減らした（この変更による CI の破損は [#99621](https://github.com/vercel/next.js/pull/99621) で修正）。

### turbo-tasks: `outdated_collectibles` を正しく維持し、不要な再実行を防止（[#99386](https://github.com/vercel/next.js/pull/99386)）

> [!quote] Before
> `outdated_collectibles` がタスク実行開始時に正しく初期化されず、タスクを dirty にするときにも使われていなかった。そのため余計な dirty 呼び出しでタスクが stale になり、トップレベルで collectibles を読むタスクが再実行されることがあった。

> [!success] After
> 「stale と dirty」の最適化を活かし、一般的なケースでの再実行を避けるようになった。

### turbo-tasks: 永続化データが空で上書きされる問題を修正（[#99581](https://github.com/vercel/next.js/pull/99581)）

> [!quote] Before
> シリアライズの無効化（`invalidate_serialization`）で、Data だけでアクセスしたタスクの Data と Meta の両方を変更済みとしていた。そのため eviction 後にセル内の `State` を変更すると空の Meta が永続化され、次回の復元でタスクの出力が失われて黙って再実行されていた。

> [!success] After
> シリアライズの無効化では Data だけを変更済みにする。`track_modification` は、ガードがそのカテゴリのアクセスで取得されたかを（永続タスクで）確認するようになり、不一致はデバッグビルドとテストで明示的に失敗する。

📦 v16.4.0-canary.60 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### turbo-tasks: ディスク読み込みで存在しないタスクの扱いを統一（[#99249](https://github.com/vercel/next.js/pull/99249)）

> [!quote] Before
> 存在しないタスクを 2 つの読み込みが同時に読むと、一方が途中の空エントリをタスクと取り違えることがあった。

> [!success] After
> 同時に読んでもどちらも「存在しない」と判断する（`AllowMissing` はどちらも `None`、`MustExist` はどちらもパニック）。要求した Data / Meta キーが無ければ確定扱いとし、復元処理がそのキーをビジーループで再試行しないようにした。

📦 v16.4.0-canary.60 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Docker のサンプルで pnpm 11 のインストールが失敗する問題を修正（[#97352](https://github.com/vercel/next.js/pull/97352)）

> [!quote] Before
> `examples/with-docker` と `examples/with-docker-export-output` の Dockerfile は `pnpm install --frozen-lockfile` を実行するが、`sharp` のビルドスクリプトの扱いを指定していなかった。pnpm 11 では明示が必要なため、`ERR_PNPM_IGNORED_BUILDS` で失敗していた。

> [!success] After
> 各サンプルの `pnpm-workspace.yaml` に `allowBuilds: { sharp: false }` を追加し、pnpm を使う 3 つの Dockerfile の依存ステージでそのファイルをコピーするようにした。`Dockerfile.serve` も他と同じく任意の `.npmrc` をコピーする。
