## 変更・修正

### Turbopack: チャンクのタグを探すときの document 全体の走査をやめる（[#100047](https://github.com/vercel/next.js/pull/100047)）

> [!quote] Before
> Turbopack のブラウザランタイムは、チャンクの URL を初めて読み込むとき、既存の `<script>` / `<link rel=stylesheet>` を document 全体への `querySelectorAll` で探していた。ハイドレーション中にメインスレッドでチャンクごとに走り、DOM が大きいほど遅くなった。URL をエスケープせずにセレクターへ埋め込んでいたため、`"` を含むと `SyntaxError`、`\` を含むと既存のタグを見落としていた（[#99993](https://github.com/vercel/next.js/issues/99993)）。

> [!success] After
> 本番のローダー（`doLoadChunk`）と開発時のバックエンド（`unloadChunk` / `reloadChunk`）は `getElementsByTagName` と単純な文字列比較でタグを探す。一致の条件（URL と `decodeURI` した形、`?` 付きの前方一致、`rel` が `stylesheet`）は変わらない。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack: 既存のチャンクのタグを `<head>` の中だけで探す（[#100175](https://github.com/vercel/next.js/pull/100175)）

> [!quote] Before
> [#100047](https://github.com/vercel/next.js/pull/100047) の後も、探索は document 中のすべての `<script>` / `<link>` をたどるため、ページの内容に比例してコストが増えていた。`turbopack-dev-server` はチャンクのスクリプトを `<body>` の末尾に置いていた。

> [!success] After
> ランタイムは `<head>` の中だけを探し、`turbopack-dev-server` はチャンクのスクリプトを `<head>` に `<script async>` として置く。PR のマイクロベンチマークでは、body に 32,000 要素ある場合の 80 回の探索が 23.3ms → 2.5ms（CPU 1×）になった。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack: 起動直後に取りこぼした CSS の更新をフルリロードで回復（[#99963](https://github.com/vercel/next.js/pull/99963)）

> [!quote] Before
> ブラウザが HMR を始める前に CSS の読み込みが終わることがあり、その間に編集すると古い CSS が残った。ブラウザが現在の WebSocket のバージョンで初期化されるため、ずれが隠れていた。

> [!success] After
> Turbopack の HMR を使う開発サーバーの HTML に、実際に描画したバージョン（`__nextHmrInitialVersion`）をインラインスクリプトで出力し（CSP の nonce を使う）、初回接続ではこれを基準にする。サーバーは HTML を返す前に CSS を含むクライアント出力（Pages Router の `_app` も含む）を監視する。ずれていれば既存のリロードの仕組みでフルリロードし、通常の CSS の HMR は状態を保ったまま。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### バンドルアナライザー: ルートの一覧を `route-summaries.json` に一本化（[#100081](https://github.com/vercel/next.js/pull/100081)）

> [!quote] Before
> `generateImageMetadata` や `generateSitemaps` を使うメタデータルートで `next analyze export` が ENOENT で失敗し、アナライザー UI もそのデータを読めなかった。ルートの一覧が 2 つ（`routes.json` と Turbopack の `route-summaries.json`）あり、キーが食い違っていたため（例: `/icon` と `/icon/[__metadata_id__]`）。

> [!success] After
> `next analyze`・`next build --analyze`・`next analyze export`・UI のルート選択・比較画面のすべてが `route-summaries.json` だけを使う。`routes.json` は書き出されなくなり、`/_global-error` もほかのルートと同じく一覧に出る。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack: 親ディレクトリがバッチに入っているだけでイベントを関係ありとみなさない（[#99782](https://github.com/vercel/next.js/pull/99782)）

> [!quote] Before
> macOS で、追跡していないファイルに頻繁に書き込むとファイル監視のバッチが閉じず、追跡しているファイルの無効化が書き込みが止まるまで遅れていた（FSEvents が `Create(File)` を出し続け、親ディレクトリがバッチにあるだけで関係ありと判定していたため）。

> [!success] After
> 判定の高速経路はパスそのものだけを確認する。一覧を追跡しているディレクトリの下のイベントは、従来どおり低速経路で関係ありとみなされる。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### webpack の開発時のマニフェストをアトミックに書き込む（[#100112](https://github.com/vercel/next.js/pull/100112)）

> [!quote] Before
> webpack の開発時、マニフェスト（`next-font-manifest.json`・`page_client-reference-manifest.js` など）はその場で上書きされるため、再ビルド中に 0 バイトのマニフェストを読んでしまうことがあった。`app/page.js` を一時的に消して `/_not-found` を表示するような場面で 500 になり、ページが回復しなかった。

> [!success] After
> マニフェストは一時ファイルに書いてから名前を変えて置き換える（ほかの出力は従来どおり）。Turbopack はもともと `writeFileAtomic` で書いていて影響は無い。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### turbo-tasks: 集約の更新をロックの外で整理する（[#100165](https://github.com/vercel/next.js/pull/100165)）

> [!quote] Before
> 集約タスクの上位が増減するときの `AggregatedDataUpdate` には、打ち消し合うエントリが大量に含まれていた（大きな `next build` の調査では 106,268 件中、非ゼロは 4 件）。フォロワーのロックを持ったまま作られるため、多数のワーカーで処理が直列化していた。

> [!success] After
> 新しい `AggregatedDataUpdate::optimize()` が、ロックを手放した後でコレクティブルごとの件数を合算し、ゼロになったものを捨てる。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### turbopack-trace-server: 同じスパンに再入したときの自己時間の欠落を修正（[#100205](https://github.com/vercel/next.js/pull/100205)）

> [!quote] Before
> instrument された future のように、同じスレッドで同じスパンに再入すると、内側の Exit が外側のフレームの計測を消してしまい、バイナリトレースの自己時間が欠けていた。

> [!success] After
> スレッドごとのスタックフレームに計測中の区間の開始を持たせて正しく数える。バイナリのフレームグラフの CPU 時間・自己時間・並行度の指標は、欠けていた分が入るため値が変わる。トレースの形式は変わらない。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Cache Components + 共有ランタイムで、nonce を使う CSP でもハイドレーションするように（[#100102](https://github.com/vercel/next.js/pull/100102)）

> [!quote] Before
> `cacheComponents` と既定の `experimental.turbopackSharedRuntime` を使った Turbopack の本番ビルドでは、ルートのチャンクグループのブートストラップ（16.4 からのインラインの `globalThis.TURBOPACK.push(...)`）がビルド時にプリレンダーされる静的シェルに nonce 無しで入っていた。nonce ベースの CSP（`script-src 'self' 'nonce-…'`）ではブラウザがこれをブロックし、ページが操作できないままになっていた。

> [!success] After
> ブートストラップを静的シェルから外し、PPR の resume（リクエストごとの部分）からリクエストの nonce 付きのインラインスクリプトとして出力する。共有ランタイムは既定で有効のまま。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]、[[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### middleware を通るリクエストを 1 つの OpenTelemetry トレースにまとめる（[#100136](https://github.com/vercel/next.js/pull/100136)）

> [!quote] Before
> `instrumentation.ts` で OTel を設定していると、middleware / `proxy.ts` を通るリクエストが 2〜3 個のトレースに分かれていた。middleware が処理を続けさせると `BaseServer.handleRequest` が 2 回走り、それぞれがルートのトレースを始めていたため（13.5 から）。さらに 16.3 では、プロセス内の Node.js の middleware を `ROOT_CONTEXT` で実行するようにした変更（[#95306](https://github.com/vercel/next.js/pull/95306)）で外側のスパンから切り離され、16.2 → 16.3 で「トレースが倍になった」状態になっていた。

> [!success] After
> どの場合も 1 つのトレースになる。middleware が処理を続けさせたときは、レンダリングが常に middleware のスパンの中に入れ子になる。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/OpenTelemetry|OpenTelemetry]]

### fetch のスパンで HTTP の失敗をエラーとして記録（[#99877](https://github.com/vercel/next.js/pull/99877)）

> [!quote] Before
> fetch のスパンは、HTTP の失敗でもエラーのステータスにならなかった。

> [!success] After
> ステータスが 400 以上のレスポンスを記録したスパンをエラーにする。レスポンスの本文やストリーミングはそのまま。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/OpenTelemetry|OpenTelemetry]]

### 拡張子の無い Google Fonts の URL を両方のバンドラーで扱えるように（[#100158](https://github.com/vercel/next.js/pull/100158)）

> [!quote] Before
> Google Fonts は UA に応じて拡張子の無い URL の WOFF2 を返すことがあり（[#99114](https://github.com/vercel/next.js/issues/99114)）、webpack は正規表現の結果が null のまま参照してクラッシュしていた。Turbopack はシリアライズしたオプションをクエリ文字列として解析していたため、JSON に含まれる `&` で分断され、拡張子の確認も失敗していた。

> [!success] After
> webpack は URL に拡張子が無ければ CSS の `format('…')` から拡張子を決める。Turbopack は CSS の抽出時に決めた拡張子をアセットの出力まで引き継ぎ、オプションの JSON は 1 つのクエリとしてパーセントエンコードする。

⏳ 未リリース · トピック: [[repos/vercel-next.js/topics/next-font|next/font]]
