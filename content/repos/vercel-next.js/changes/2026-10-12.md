## 新機能

### `next build` / `next dev` の `--custom-webpack` を再投入（[#99234](https://github.com/vercel/next.js/pull/99234)）

> [!tip] 何ができるようになったか
> revert された [#98862](https://github.com/vercel/next.js/pull/98862)（revert: [#99227](https://github.com/vercel/next.js/pull/99227)）を、webpack を peer dependency にしない形で戻した。アプリにインストールした webpack を明示的に使って開発・ビルドできる（experimental）。`next.config.js`・ユーザーのプラグイン・Next.js のコンパイルが同じ webpack を使うよう、webpack の import はプロジェクト基準の `createRequire` で解決する。
>
> - **使い方**: `next dev --custom-webpack` / `next build --custom-webpack`（webpack はアプリ側にインストールし、有効化時に検証される）。`--webpack` は従来どおり同梱の webpack を使う
> - **嬉しい場面**: 同梱版ではなく、アプリで固定した webpack のバージョン（e2e では 5.98.0 と 5.111.0 を検証）でビルドしたいとき

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### 画像最適化の変換処理を `next/image-optimizer-transform` として公開（[#99312](https://github.com/vercel/next.js/pull/99312)）

> [!tip] 何ができるようになったか
> 画像最適化の変換モジュールを、公開のサブパス `next/image-optimizer-transform` から import できるようになった（`next/og` と同じ形）。`ImageError` と `getMaxAge` も再エクスポートし、モジュールの場所とエクスポートは安定した契約と明記された。`imageOptimizerTransform`・`optimizeImage`・`getSharp`・`getMaxAge`・`ImageError` の API リファレンスも追加。
>
> - **使い方**: `import { optimizeImage } from 'next/image-optimizer-transform'`
> - **嬉しい場面**: Vercel のプロキシのように、画像最適化の変換を別プロセスで動かすとき。内部パス `next/dist/server/image-optimizer/*` に依存しなくてよくなる

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/画像最適化|画像最適化]]

### Turbopack: webp を常に有効にしてビルド（wasm 版でも webp に対応）（[#99964](https://github.com/vercel/next.js/pull/99964)）

> [!tip] 何ができるようになったか
> image-rs 0.25 から webp が Rust 実装になり、プラットフォームの互換性の心配が無くなったため、`turbopack-image` の webp の feature フラグを削除して常に有効にした。これまで webp は wasm 版以外では有効だった（wasm は見落としとされている）。
>
> - **嬉しい場面**: wasm 版の `@next/swc` でも Turbopack が webp 画像を扱える

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]、[[repos/vercel-next.js/topics/画像最適化|画像最適化]]

## 変更・修正

### canary で Turbopack の GC を既定で有効に（[#99596](https://github.com/vercel/next.js/pull/99596)）

> [!quote] Before
> Turbopack の GC は既定では無効で、ファイルシステムキャッシュが時間とともに大きくなりうる。

> [!success] After
> canary では GC を既定で有効にする（`packages/next/src/server/config.ts`）。キャッシュの肥大化を防ぎ、キャッシュが小さいほど読み込みも速くなる。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack: GC で依存の辺が半分だけ壊れたまま残る 2 つの経路を修正（[#99902](https://github.com/vercel/next.js/pull/99902)）

> [!quote] Before
> GC と永続キャッシュを両方有効にすると、`task TaskId N (invalidate cell dependents, MustExist): task is missing in memory or persistent storage` で panic することがあった。中断された GC の後にも eviction が削除済みのタスクを捨てていたこと、および GC で回収したタスクが復活したときに古い逆方向の辺（`cell_dependents` など）が残っていたことが原因。

> [!success] After
> スナップショットが中断された場合は eviction で削除済みのタスクを捨てず、復活したタスクに古い逆方向の辺が残らないようにした。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack: モジュール解決で realpath のエラーを無視（Node と同じ挙動に）（[#99951](https://github.com/vercel/next.js/pull/99951)）

> [!quote] Before
> realpath のエラー（シンボリックリンクの循環など）で解決を打ち切り、環境によっては Turbopack の内部エラーとして報告されていた。

> [!success] After
> Node と同じく、realpath のエラーは「見つからない」と同じに扱う。解決処理は呼び出し頻度が高く警告を出すとうるさくなるため、警告も出さない。`node_modules` が壊れている場合は `MissingNextFolderIssue` で案内される。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack: Node.js の子プロセスが接続できないときに対処の分かるエラーを表示（[#99887](https://github.com/vercel/next.js/pull/99887)）

> [!quote] Before
> 権限の限られたサンドボックス（Codex など）で `next` を起動して Node.js のワーカープロセスが Turbopack に接続できないと、「node process exited before we could connect to it with exit status: 0」と長い内部のデバッグ情報が並ぶ分かりにくい FATAL エラーになっていた。

> [!success] After
> 専用の終了コードで接続失敗を知らせ、対処の分かるエラーメッセージを表示する（このような環境自体はサポート対象外）。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### Turbopack のトレース: アロケーションのカウンターを Enter / Exit の行にまとめる（[#99778](https://github.com/vercel/next.js/pull/99778)）

> [!quote] Before
> トレースには Enter / Exit の前ごとに別の `AllocationCounters` 行が出力され、タグ・タイムスタンプ・スレッド ID が重複していた。この行が典型的なトレースの 66% を占めていた。

> [!success] After
> `AllocationCounters`（と未使用の `Allocation`）の行を削除し、Enter / Exit の行に `allocations` として持たせる。トレースサーバーと `turbo-trace-size` も対応した。

> [!warning] 互換性
> トレースの形式の互換性の無い変更。5 つの PR のスタックの最後でヘッダーを `TRACEv1` に上げ、古いトレースはエラーで拒否される予定。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### ビルド出力: 折りたたんだ生成パスの行に子のパスの記号を使う（[#99864](https://github.com/vercel/next.js/pull/99864)）

> [!quote] Before
> Cache Components・Partial Prefetching・`ensureStatic = 'navigation'` を使った catch-all ルートで、生成パスがすべて静的でも、`next build` のルート表の `[+N more paths]` の行がルートパターンの記号（◐ Partial Prerender）を引き継いでいた。

> [!success] After
> 折りたたんだパスの記号がすべて同じならその記号（○ Static など）を使う。混在する場合はルートパターンの記号のまま。ルートパターン自体の行は Partial Prerender のまま変わらない。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]、[[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]

### perf: ビルド出力のルート表の一時メモリを削減（[#99930](https://github.com/vercel/next.js/pull/99930)）

> [!quote] Before
> `printTreeView` が生成ルートの一覧を何度もコピーし、ルートごとに一時オブジェクトを作っていた。

> [!success] After
> プレビューを直接出力表に書き、並べ替えは数値のインデックスの配列で行う。ビルド出力は変わらない。5 万ルートの計測で 1 回あたりの一時ヒープの増加が 460 KB → 68 KB（順序維持）、4.53 MB → 2.14 MB（遅いルートを先に並べる場合）に減った（CPU 時間の改善はうたっていない）。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/ビルド・Turbopack|ビルド・Turbopack]]

### サーバーのエラー表示で、メッセージの行をスタックフレームとして解釈しない（[#99888](https://github.com/vercel/next.js/pull/99888)）

> [!quote] Before
> 複数行のメッセージを持つエラーをターミナルに表示すると、`at <unknown> (https://nextjs.org/docs/...)` や `at <unknown> (Turbopack is configured to ...)` のような偽のスタックフレームが末尾に出ることがあった。`error.stack` の先頭のメッセージまでスタックのパーサーに渡していたため。

> [!success] After
> `patch-error-inspect.ts` で、メッセージより後のスタックフレームの部分だけを解析する（自前で整形したスタックは最初のフレームの位置を記録し、それ以外は `name: message` の見出しを取り除く）。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/レンダリング・DevTools|レンダリング・DevTools]]

### エージェントによるアップグレードのテレメトリにメタデータを追加（[#99925](https://github.com/vercel/next.js/pull/99925)）

> [!quote] Before
> アップグレードの結果のイベントにバージョンや実行環境の情報が無く、失敗や結果の欠落をアップグレードの経路や環境ごとに比べられなかった。

> [!success] After
> 開始時のイベントにアプリの開始時の Next.js のバージョン・CLI の Node のバージョン・パッケージマネージャーとそのバージョン、CLI の結果に開始・承認された移行先のバージョン、エージェントの結果に報告時にインストールされている Next.js のバージョンを記録する。バージョンの取得に失敗しても警告だけでアップグレードは止めず、値は null になる。

📦 v16.5.0-canary.8 · トピック: [[repos/vercel-next.js/topics/AI-アップグレード|AIアップグレード]]、[[repos/vercel-next.js/topics/テレメトリ|テレメトリ]]

### リリースブランチをバージョン付きから固定の `releases/lts/*` に（[#99807](https://github.com/vercel/next.js/pull/99807)）

> [!quote] Before
> `create_release_branch` ワークフローとスクリプトが、リリースの系列ごとに `next-<major>-<minor>` ブランチを作り、それぞれの CI のフィルターを書き換えていた。

> [!success] After
> 長期の 2 つのブランチ `releases/lts/active`（現在のメジャー）と `releases/lts/maintenance`（1 つ前のメジャー）に置き換えた。安定版のリリース時に ref が自動で動く（patch は動かさない、minor はメジャーに応じて active か maintenance を新しいタグへ、major は maintenance が active の元の位置を引き継ぎ active が新しいタグへ）。タグから `Trigger Release` を起動するタグのみのリリースにも対応した。
