## 新機能

### `ensureStatic = "navigation"` の初期実装（[#99171](https://github.com/vercel/next.js/pull/99171)）

> [!tip] 何ができるようになったか
> `ensureStatic = "navigation"` を指定したルートでは、リクエストごとの計算が発生しないことを保証するため、すべてのプリレンダーがブロッキングになる。`output: "export"` と同様に、すべての params を `generateStaticParams` で指定する必要がある。
>
> - **制約**: プリレンダーしていない param に対してフォールバックと resume を返すことはしない。`generateStaticParams` が不完全・欠落している場合はエラーになる
> - **許可されるもの**: `use(io())` や `useSearchParams()` のようなクライアントだけの IO は従来どおり可能（フォールバック付きの HTML を返し、足りない部分はブラウザで描画）
> - **ビルド出力**: 最も汎用的なもの以外のフォールバックシェルを生成しない

### `navigation()` / `prefetch()` から `unstable_` 接頭辞を削除（[#99241](https://github.com/vercel/next.js/pull/99241)）

> [!tip] 何ができるようになったか
> `unstable_navigation` / `unstable_prefetch` の `unstable_` 接頭辞がコードベース全体で外され、`navigation()` / `prefetch()` という名前になった（`next/cache` の定義も変更）。

> [!warning] 移行が必要
> canary で `unstable_navigation` / `unstable_prefetch` を使っている場合は、`navigation` / `prefetch` に書き換える。

### create-next-app の推奨デフォルトにエージェントフィードバックを追加（[#99119](https://github.com/vercel/next.js/pull/99119)）

> [!tip] 何ができるようになったか
> `create-next-app` の対話式の推奨デフォルトに、実験的なエージェントフィードバック（`experimental.agentFeedback: true`）が含まれるようになった。
>
> - **使い方**: `--agent-feedback` / `--no-agent-feedback` で明示的に指定できる。カスタム設定を選んだ場合だけ質問され、既定は **Yes**
> - **非対話の場合**: CI や `--yes` などでは、`--agent-feedback` を付けない限り無効のまま
> - **無効化**: `experimental.agentFeedback: false` でいつでも無効にできる

> [!tip] 何ができるようになったか

## 変更・修正

### create-next-app で Cache Components を既定で有効に（[#99436](https://github.com/vercel/next.js/pull/99436)）

> [!quote] Before
> `create-next-app` の既定では Cache Components は無効だった。

> [!success] After
> 新しいアプリで移行しやすくするため、既定で Cache Components を有効にするようにし、ドキュメントも更新した。API だけのアプリは今回の変更の対象外。

📦 v16.4.0-canary.53 · トピック: [[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]

### プリレンダー時に HTTP ステータスコードを保持するように（[#99078](https://github.com/vercel/next.js/pull/99078)）

> [!quote] Before
> プリレンダーされるページが Suspense の中で `notFound()`・`unauthorized()`・`forbidden()`・`redirect()`・`permanentRedirect()` を投げても、正しい HTTP ステータスとリダイレクト先が設定されていなかった。

> [!success] After
> 正しいステータスと `location` を設定し、プリレンダーしたレイアウトと Suspense のフォールバックを残してクライアントが適切なエラー境界で回復できるようにした。リダイレクトはアクセス系フォールバックより優先され、同種の中では最初に起きたものが採用される。リクエスト時のストリーミングの挙動は変わらない。

📦 v16.4.0-canary.53 · トピック: [[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]

### カスタムキャッシュハンドラーが最初のリクエストで使われない不具合を修正（[#99372](https://github.com/vercel/next.js/pull/99372)）

> [!quote] Before
> 起動時のプリロードで、設定したハンドラーの読み込みが終わる前に組み込みハンドラーのマップが初期化され、その間に `'use cache'` に到達したリクエストが組み込みハンドラーを使ってしまうことがあった。

> [!success] After
> ハンドラーの登録が終わるまで待ってからレンダリングするようにした。ハンドラーの import に失敗した場合は、未処理の rejection にせずログに出す。

📦 v16.4.0-canary.53 · トピック: [[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]

### アダプターのデプロイで、未生成の閉じたルートでも Draft Mode を使えるように（[#99370](https://github.com/vercel/next.js/pull/99370)）

> [!quote] Before
> アダプターを使ったデプロイで、`dynamicParams = false`（App Router）や `fallback: false`（Pages Router）のページにビルドで生成されていない URL を Draft Mode で要求すると、プレビューではなく 404 を返していた。アダプターが `__prerender_bypass` と `__next_preview_data` の両方を要求していたため。

> [!success] After
> `__prerender_bypass` クッキーがビルドのプレビュー ID と一致すればルーティングするようにした。通常のリクエストは引き続き 404。Pages Router では従来のプレビューデータがあれば検証し、不正なものは拒否する。

### クライアントコンポーネントの読み込み計測を HTML レンダーごとに（[#99322](https://github.com/vercel/next.js/pull/99322), [#99426](https://github.com/vercel/next.js/pull/99426), [#99427](https://github.com/vercel/next.js/pull/99427)）

> [!quote] Before
> クライアントコンポーネントの読み込み時間のテレメトリは、プロセス全体のカウンターとリクエストボディの完了を基準にしており、重なったレンダーが混ざるうえ、HTML の生成とは関係のないライフサイクルを計測していた。また、トップレベル `await` を持つモジュールでは、`require()` が Promise を返した後の評価待ちが計測から漏れていた。

> [!success] After
> カウンターと報告のコンテキストを HTML を生成する各レンダーに限定し、SSR の前に計測を始め、React の準備完了（Node は `onAllReady`、Web は `allReady`）で終える（[#99322](https://github.com/vercel/next.js/pull/99322)）。HTML レンダーのスパンと読み込み計測を同じ SSR 完了コールバックで終えるようにし（[#99426](https://github.com/vercel/next.js/pull/99426)）、非同期モジュールの評価時間も計測に含める（[#99427](https://github.com/vercel/next.js/pull/99427)）。
