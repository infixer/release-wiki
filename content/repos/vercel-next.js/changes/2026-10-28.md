## 新機能

### Turbopack: サーバーのチャンクサイズを調整する `minServerChunkSize` / `maxMergeServerChunkSize`（[#100712](https://github.com/vercel/next.js/pull/100712)）

> [!tip] 何ができるようになったか
> `experimental.turbopackChunking` に、Node.js のサーバー側 JavaScript のチャンク化を調整する 2 つの実験的オプションが加わった。`minServerChunkSize` は本番のチャンカーが使う最小チャンクサイズ、`maxMergeServerChunkSize` はそれを超えるとほかのチャンクとマージしないサイズ。これまで `minChunkSize` / `maxMergeChunkSize` はクライアント側にしか効かず、サーバー側はハードコードされた値だった。
>
> - **使い方**: `experimental.turbopackChunking.minServerChunkSize` / `maxMergeServerChunkSize` を設定する。未設定なら従来の値（min `4000`、max merge `100000`）で、出力は変わらない
> - **対象**: Node.js のサーバーのチャンク化コンテキストの ECMAScript チャンクだけ（本番ビルドのみ）。Edge は制限が小さいため対象外で、従来の値（min `20000`、マージの上限なし）のまま
> - **嬉しい場面**: サーバーのチャンクを少なく大きくするか、重複を減らすかを調整したいとき

### next-bundle-optimizer にサーバー専用コードの漏えいチェックを追加（[#100330](https://github.com/vercel/next.js/pull/100330)）

> [!tip] 何ができるようになったか
> エージェント向けの next-bundle-optimizer は、クライアントのコードをサイズ順に並べるため、ブラウザに入るべきでない小さなモジュール（データベースのスキーマ、トークン署名のヘルパー、エージェントのシステムプロンプトなど）を見落としていた。手順 4 に、アナライザーのエクスポートからクライアントに届くすべてのモジュールを内容のヒューリスティクスで調べる、サイズに依存しないパスが加わった。
>
> - **出力**: 「Possible server-only leaks」の欄に、ルート・最短の import の連鎖・一致したヒューリスティクス・圧縮後のサイズを表示する（サイズのランキングには含めない）
> - **注意**: 該当したモジュールと import の連鎖は、どちらのモードでもエージェントが変更しない（移すかどうかは持ち主の判断）
> - 評価用に `agent-059-bundle-audit-server-leaks`（audit モード）・`agent-060-bundle-fix-server-leaks`（fix モード）を追加

### Agent Feedback のレポートを渡す内部 CLI `next internal agent-feedback`（[#100739](https://github.com/vercel/next.js/pull/100739)）

> [!tip] 何ができるようになったか
> Agent Feedback のレポートの引き渡しが、エージェントがホスト固有のブラウザ操作を探して実行することに依存していたため、ヘッドレス・サンドボックス・リモートのセッションで失敗することがあった。隠しコマンド `next internal agent-feedback [report]` が、エンコード済みの v5 レポートを受け取り、スキーマ全体を検証して、必ずレビュー URL を出力してから既定のブラウザを開こうとする。
>
> - **使い方**: レポートを位置引数か標準入力（16 KiB・5 秒まで）で渡す。`--dry-run` で検証と URL の生成だけ行う
> - **注意**: プロトコル用の内部コマンドで、semver の対象となる公開 CLI ではない
> - ブラウザを開けないときも出力した URL は残る。Agent Feedback のプロトコルと評価もこの CLI を使うように更新

### MPA の Server Actions の後に完全な HTML ドキュメントを描画する（[#100740](https://github.com/vercel/next.js/pull/100740)）

> [!quote] Before
> Cache Components のページへの MPA のフォーム送信（ハイドレーション前の送信など）で、プリレンダーの続きだけが返ることがあった。アクションは実行されるが、レスポンスに HTML ドキュメントが無く、返された `useActionState` の値も描画されなかった（[#99756](https://github.com/vercel/next.js/issues/99756)）。

> [!success] After
> MPA のフォーム送信では、プリレンダーが渡した RDC を保ったまま完全なドキュメントを描画する（既定のハンドラーがメモリにプリレンダーのエントリを持たないデプロイでも、通常の `'use cache'` の値が保たれる）。データを再検証しない送信でも描画フェーズを準備し、通常の not-found のレスポンスはルートレイアウトを含む。Vercel がアクション本体の前に渡す postponed state にも対応。

### FileSystemCache の再検証とエントリの時刻をモノトニッククロックで記録（[#100357](https://github.com/vercel/next.js/pull/100357)）

> [!quote] Before
> `FileSystemCache` はタグの再検証とキャッシュエントリの時刻を壁時計（`Date.now()`・ファイルの mtime）で付けていたが、#94457 以降 `areTagsExpired` はモノトニッククロック（`performance.timeOrigin + performance.now()`）と比べていた。壁時計が進んでいると再検証が未来の時刻になって無視され、`revalidateTag` の後も古いページが返り続けた（16.4.2 で壁時計が 5ms 進んだ状態だと、直後の 30 回の読み込みがすべて古いページ）。NTP・VM・WSL2 の時刻補正などで普通に起きる。

> [!success] After
> `revalidateTag` と `set()` はモノトニッククロックで時刻を付け、`set()` はその時刻をディスクにも保存する（`.meta` の `routeCacheLastModified`、fetch キャッシュのエントリの `lastModified`）。保存された時刻の無いファイル（`next build` や古い Next.js が書いたもの）は従来どおり mtime を使う。`cacheMaxMemorySize: 0` やメモリからの追い出しの後にディスクから読む場合に効く。
