## 新機能

### `next build --experimental-cpu-prof` が静的ワーカーの CPU プロファイルも書き出す（[#100614](https://github.com/vercel/next.js/pull/100614)）

> [!tip] 何ができるようになったか
> `next build --experimental-cpu-prof` で、静的ワーカーごとに `build-static-worker-*.cpuprofile` を書き出すようになった（これまではメインのプロセスと webpack のコンパイラーのワーカーだけ）。大きな App Router のビルドで遅くなりがちなページデータ・プリレンダーの段階をプロファイルできる。
>
> - **ファイル名**: `<name>-<timestamp>-<pid>.cpuprofile`（プロセス ID を含むので、同じ秒に保存したワーカーが上書きし合わない）
> - **仕組み**: プロファイル有効時の Next.js のワーカーは `SIGINT`・`SIGTERM` でプロファイルを同期的に保存してから同じシグナルで終了する。`NEXT_CPU_PROF` があるときは、ワーカーの終了を待ってから jest-worker の `end()` を呼び、強制終了で書き込みが途切れないようにする

## 変更・修正

### 静的から部分的なプリレンダーに再生成されたルートで、デプロイ先の RSC の応答が空になる問題を修正（[#101454](https://github.com/vercel/next.js/pull/101454)）

> [!quote] Before
> 完全に静的な Cache Components のルートが partial として再生成されると、アダプターのデプロイで空の RSC の応答が返っていた。ハンドラーがビルド時の `prefetchDataRoute` を信じて Flight のヘッダーを除いていたため、ナビゲーションが React #412 で失敗してドキュメントの読み込みに戻り、ランタイムのプリフェッチとランタイムのシェルもリクエストのデータを受け取れなかった。

> [!success] After
> minimal mode では、渡された postponed state があれば動的な RSC の描画を選び（ビルド時の静的な RSC の判定より優先）、Flight のヘッダーを保つ。新しい RSC を作り、渡された state の Resume Data Cache を再利用できる。`next start` での同じケースは #101357 が扱う。

📦 v16.5.0-canary.47 · トピック: [[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]

### バックグラウンドのプリレンダーが表の応答のステータスを変えないように（[#101295](https://github.com/vercel/next.js/pull/101295)）

> [!quote] Before
> 古い partial のプリレンダーのキャッシュを再利用するナビゲーションで、表の Flight の応答とバックグラウンドの再生成が同じ HTTP 応答を共有していた。バックグラウンドのリダイレクトが表の応答のステータスを変えてドキュメントのナビゲーションを強いたり、プリレンダーが古いドキュメントの応答の 404 を見て、成功した再生成の内容に `noindex` を入れたりしていた。

> [!success] After
> プリレンダーは明示的な初期ステータス（通常は 200、エラーページのルートはその意図したステータス）を受け取って自分で持ち、結果のメタデータでステータスを返す。描画の共有のコンテキストは HTTP 応答の全体ではなくステータスだけを公開する。動的な描画は引き続き実際の応答を使う。

📦 v16.5.0-canary.47 · トピック: [[repos/vercel-next.js/topics/キャッシュ・プリレンダリング|キャッシュ・プリレンダリング]]

### 同期的に例外を投げた fetch のキャッシュのロックを解放（[#101461](https://github.com/vercel/next.js/pull/101461)）

> [!quote] Before
> 不正な URL やリクエストのオプションで `originFetch` が同期的に例外を投げると、キャッシュのロックが残り、同じキャッシュキーの後続の fetch が待ち続けて、ページが元のエラーを捕まえていても静的生成がタイムアウトすることがあった。

> [!success] After
> `originFetch` を Promise のコールバックの中で呼び、同期的な例外も rejection としてロックを解放する既存のハンドラーに届くようにした（`patch-fetch.ts`）。

### ルートの予測で、並列ルートの params を URL から解決（[#101477](https://github.com/vercel/next.js/pull/101477)）

> [!quote] Before
> クライアントが学習したパターンからルートを予測するとき、1 つの並列ルートの枝（たいていは `children`）だけから params を集めていたため、スロットの catch-all のようにほかの枝にだけある param には古い値が残り、2 つの URL の params が混じった木になっていた。サーバーが別の木を描画してクライアントが 2 回目のリクエストで再試行し、上端へのスクロールが失われることがあった（`@modal/[...catchAll]` のパターンや #98073 のプリフェッチのループに影響）。

> [!success] After
> trie はパターンの選択だけに使い、各アクティブな枝がルートの発見と同じ規則で URL から自分の params を読む。URL に合わない枝があればサーバーに任せる。アクティブでない並列ルートは default のセグメントになる。#98073 のようにこれらのルートを予測対象から外さずに済む。

### dev overlay が npm レジストリのバージョン確認を待たない（[#100628](https://github.com/vercel/next.js/pull/100628)）

> [!quote] Before
> パッケージのレジストリが遅い・届かないと、Turbopack は HMR の `sync` を、Webpack・Rspack は hot-reloader の起動をバージョンの確認まで待っていた。遅れた `sync` が待つ前のエラーの状態を再生し、新しいビルドエラーを消すこともあった。

> [!success] After
> 確認を待たずに、インストール済みのバージョンと `unknown` の状態で `sync` を送り、結果が出たら `versionInfo` の HMR メッセージでバージョンの情報だけを更新する。Turbopack は `sync` を作る時点で issue を集める。

### `next/image` の歪みの警告を画像本来の縦横比で判定（[#101349](https://github.com/vercel/next.js/pull/101349)）

> [!quote] Before
> 描画した幅・高さを props と比べ、片方だけが変わったときに警告していたため、正しく切り抜いた画像・元の寸法が props と違う画像・小数の SVG の寸法で警告が出て、両方が変わった歪みは見逃していた。

> [!success] After
> 計算した `object-fit` が `fill` のときだけ、描画の縦横比を `naturalWidth` / `naturalHeight` と比べる（丸めの誤差は許容）。`fill` の prop の扱いは変わらない。警告は縦横比の不一致を説明し、`style` の prop のドキュメントにリンクする。

### turbo-tasks: `CellKey` を 1 ワードに詰めてメモリを削減（[#101393](https://github.com/vercel/next.js/pull/101393)）

> [!quote] Before
> `CellKey` は 16 バイト、キー付きのセルの依存は 24 バイトで、依存の辺ごとに 2 回保存される（1 つの `nft.json` のタスクが 550 万の dependents を持つアプリもある）。

> [!success] After
> `CellKey` を 1 つの `u64`（最上位ビットで種類を区別）にし、各項目を 16 バイトにした。計測したアプリでは `cell_dependents_keyed` が 415.0 MiB → 282.2 MiB、タスクのストレージの合計が 3990.9 MiB → 3747.9 MiB。永続キャッシュの形式が変わる（キャッシュはコミットごとにバージョン管理されている）。
