## 新機能

### Turbopack: `experimental.turbopackLazyDynamicImports` で遅延 `import.meta.glob` のマッチも遅延コンパイル（[#100523](https://github.com/vercel/next.js/pull/100523)）

> [!tip] 何ができるようになったか
> dynamic import の遅延コンパイル（`experimental.turbopackLazyDynamicImports`）を有効にすると、遅延（non-eager）の `import.meta.glob` のマッチも同じ扱いになり、各モジュールはそのサンクが初めて呼ばれたときにだけコンパイルされる。eager のマッチは変わらない。
>
> - **使い方**: `experimental.turbopackLazyDynamicImports` を有効にする
> - **嬉しい場面**: `import.meta.glob` で多数のモジュールにマッチさせているが、実際に使うのは一部だけのとき

### 開発時の遅延サーバー import をルートハンドラーと Pages に拡大（[#99541](https://github.com/vercel/next.js/pull/99541)）

### Turbopack の webpack ローダーに webpack の utils を追加（[#99826](https://github.com/vercel/next.js/pull/99826)）

> [!tip] 何ができるようになったか
> Turbopack で実行する webpack ローダー向けに、webpack 互換のユーティリティ（`webpack-loaders-utils.ts`）が加わった。webpack はハッシュ関数を AssemblyScript から wasm にして埋め込んでいるが、ここでは MD4・xxhash64 などを JS で実装している。PR の計測では、CSS の小さな入力では wasm とほぼ同等〜1.8 倍遅い程度で、Rust 実装より速かった。
>
> - **嬉しい場面**: ローダーの中で webpack の utils を使う webpack ローダーを Turbopack で動かしたいとき

### トレースのメモリサンプルにプロセスのメモリ使用量（RSS）を記録（[#99527](https://github.com/vercel/next.js/pull/99527)）

> [!tip] 何ができるようになったか
> `TurboMalloc::memory_footprint()` が加わり、トレースのメモリサンプル（`TraceRow::MemorySample`）に `memory_footprint` として OS が報告するプロセスのメモリ量が記録される。Linux は `/proc/self/statm` の常駐ページ数、macOS はアクティビティモニタの「メモリ」と同じ `phys_footprint`、Windows は `WorkingSetSize` を使い、それ以外（wasm など）では取得しない。
>
> - **嬉しい場面**: TurboMalloc が数えるメモリ（`memory`）や `memory_pressure` だけでは見えない、mimalloc の予約・mmap したファイル・ネイティブ依存などのオーバーヘッドや、実際の RSS のリーク・リグレッションをトレースで確かめたいとき

## 変更・修正

### Pages Router: ISR エントリのキャッシュ期間が再起動で失われる問題を修正（[#100495](https://github.com/vercel/next.js/pull/100495)）

> [!quote] Before
> 既定の `FileSystemCache` を使う Pages Router の ISR のエントリは、再検証の間隔をディスクに保存していなかった。サーバーを再起動するとキャッシュ期間が設定した `revalidate` ではなく 1 秒になり、生成済みのページがすぐに `STALE` 扱いになって、期待した `Cache-Control` ヘッダーも保たれなかった。

> [!success] After
> 書き込み時にキャッシュ期間を保存し、読み込み時に復元する。App Router 側の同じ問題を直した [#99289](https://github.com/vercel/next.js/pull/99289) を補う修正。

### ストリーミング中に積まれたキャッシュの再検証が失われる問題を修正（[#100448](https://github.com/vercel/next.js/pull/100448)）

> [!quote] Before
> 再検証の flush は、HTML ストリームの準備やルートハンドラーの実行の後、レスポンスボディのストリーミングが終わる前に行われていた。ストリーミング中に追加された作業は対象外になり、後からのキャッシュ再生成は `waitUntil` で守られず、後からのタグの無効化は送られなかった（[#99339](https://github.com/vercel/next.js/issues/99339)・[#99566](https://github.com/vercel/next.js/issues/99566)）。

> [!success] After
> レスポンスを閉じるときに flush する方式（[#99772](https://github.com/vercel/next.js/pull/99772) の提案）を、動的 HTML だけでなく Flight レスポンス・ルートハンドラー・ストリーミングする Server Actions にも広げた。`AfterContext` がハンドラーから戻る前に `waitUntil` の promise を登録し、クローズ時に新たに積まれた作業を flush する。このスナップショットは `after()` のコールバックより前に取られるので、コールバック内の無効化はコールバックの完了を待つ。

### OpenTelemetry: アダプターが例外を投げても middleware の instrumentation のスパンを残す（[#100552](https://github.com/vercel/next.js/pull/100552)）

> [!quote] Before
> Node.js の middleware / proxy の直接のエントリポイントでは、`instrumentation.ts` の登録のスパン（`load instrumentation module`・`register instrumentation`）を `Middleware.execute` のスパンの中で後から出す。middleware を実行する前にアダプターの準備が例外を投げる（設定したキャッシュハンドラーが投げるなど）と、これらのスパンはインスタンスが生きている間ずっと失われていた。`next start` / `next dev` は起動時に登録するので影響しない。

> [!success] After
> middleware のエントリのテンプレートがアダプターを `try/catch` で待ち、例外時にはスパンを出してから元の例外をそのまま投げ直す。この場合 middleware のスパンは無いので、呼び出し元のアクティブなコンテキスト（無ければルート）に出す。
