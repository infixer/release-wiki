## 変更・修正

### `RevalidateAtomicAccess` が TypedArray 要素の全バイトを検証するように（[#3926](https://github.com/tc39/ecma262/pull/3926)）

> [!quote] Before
> 長さ追従（length-tracking）の TypedArray が複数バイトの要素（`Int32Array`・`BigInt64Array` など）を持つとき、`Atomics` 関数の引数の変換中に元の `ArrayBuffer` が縮められ、対象要素の先頭はまだ範囲内だが末尾が新しい終端を超える場合でも再検証が通ってしまい、「arrayBuffer に十分なバイトがある」というアサーションが失敗する状態に到達できた。

> [!success] After
> `RevalidateAtomicAccess` が要素のすべてのバイトを考慮し、このような場合は再検証が失敗する（Normative。#3924 の修正）。

```js
const rab = new ArrayBuffer(12, { maxByteLength: 12 });
const ta = new Int32Array(rab); // 長さ追従。要素 1 はバイト 4..7
Atomics.and(ta, 1, { valueOf() { rab.resize(7); return 1; } });
```

PR 本文によると、要素単位でちょうど縮めた場合の既存の挙動と同様に、JavaScriptCore と V8 は（長さ追従の TypedArray で）`RangeError` ではなく `TypeError` を投げる点だけが異なり、Moddable XS は例外を投げずに処理を続けてしまう。test262 側は [tc39/test262#5106](https://github.com/tc39/test262/pull/5106)。
