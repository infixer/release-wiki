## 変更・修正

### base URL を設定したときもルートルールによるページのカバー判定を行う（[#36682](https://github.com/nuxt/nuxt/pull/36682)）

> [!quote] Before
> nitro はすべてのルートルールを base URL の下に登録するが、Nuxt がカバー判定で試すパスには base が付いていなかった。そのためビルド時に base URL を設定していると、ルートルールによる最適化が効かなかった。

> [!success] After
> base URL の下でもルートルールのカバー判定が当てはまるようになった（`route-coverage.ts` の修正）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### 中断した View Transition の `updateCallbackDone` の reject を処理する（[#36639](https://github.com/nuxt/nuxt/pull/36639)）

> [!quote] Before
> `experimental.viewTransition` を有効にしていると、クライアント側のナビゲーションが失敗したとき（`router.onError`・`app:error`・`vue:error`。例: ページの setup で `createError` を投げる）に `Uncaught (in promise) undefined` がログに出ていた。プラグインが `abortTransition()` で遷移を中断すると `updateCallbackDone` も reject されるが、`finished`・`ready` しか catch していなかった。

> [!success] After
> `updateCallbackDone` も既存のハンドラーと同じように catch する。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### ルートルールのキーと照合する前にページのパスをエンコードする（[#36683](https://github.com/nuxt/nuxt/pull/36683)）

> [!quote] Before
> `'/café/**': { ssr: false }` のようなルートルールがあっても、`/café/about` がクライアントバンドルから外されなかった（h3 と `markPagesCoveredByRouteRule` の間でパスの扱いが食い違っていたため、最適化が効かなかった）。

> [!success] After
> カバー判定の前に、各ページのパターンを h3 と同じ文字セットでエンコードする。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### メソッド付きのルートルールのキーに対応（[#36686](https://github.com/nuxt/nuxt/pull/36686)）

> [!quote] Before
> h3 は `'GET /admin/**': { appMiddleware: 'auth' }` のようなメソッド付きのキーを受け付け、nitro は実行時にリクエストのメソッドごとに適用するが、Nuxt 側ではこれを絶対パスのように扱っていた。

> [!success] After
> Nuxt 内でルートルールを扱うすべての箇所で、h3 の `parseRouteKey` と同じ方法でメソッドの接頭辞を解析する（nitro-server・pages・vite-server のルートルール処理を更新）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### nitro: サーバーのルートルールの照合で `sensitive` を考慮する（[#36693](https://github.com/nuxt/nuxt/pull/36693)）

> [!quote] Before
> `router.options.sensitive: false` のとき、`/Admin` は `/admin` と同じページを描画するのに、`/admin` 向けのサーバーのルートルール（`redirect`・`headers` など）が適用されなかった。

> [!success] After
> この場合もルートルールが大文字・小文字を区別せずに一致するよう、正規化を加えた。ただし h3 のデフォルトに合わせて `sensitive` は有効のままにすることが強く推奨されている。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### keyed function の自動キーとページの import 名を `rootDir` からの相対パスでハッシュする（[#36697](https://github.com/nuxt/nuxt/pull/36697)）

> [!quote] Before
> キーを渡さない `useAsyncData`・`useState` などの自動生成キーが、#33446（v4.3.0・v3.21.0）以降はファイルの絶対パスのハッシュになっていた。そのため同じコミットでもビルドする場所によってチャンクのハッシュや HTML が変わっていた。

> [!success] After
> 以前の `composable-keys` プラグインと同じく、`rootDir` からの相対パスをハッシュする。ビルドするディレクトリが違っても同じキーになる。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/データ取得|データ取得]]

### 正規表現で制約したパラメータのルートルールを、動的ページ全体のカバーとみなさない（[#36701](https://github.com/nuxt/nuxt/pull/36701)）

> [!quote] Before
> `'/foo/:x([a-z_]+)': { ssr: false }` のようなルールが、`pages/foo/[x].vue` 全体をカバーするとみなされ、`ssr: false` のバンドルから外す判定に使われていた（実際には `/foo/123` はこのルールに一致しない）。

> [!success] After
> 正規表現で制約したパラメータは動的なページのセグメントをカバーしないものとして扱う（カバー不足の側に倒す）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### ビルドキャッシュのハッシュに `shared/` を含める（[#36704](https://github.com/nuxt/nuxt/pull/36704)）

> [!quote] Before
> `experimental.buildCache` を使うと、`shared/` のファイルを編集してもキャッシュヒットして古いビルドが復元されることがあった。ハッシュの対象は各レイヤーの `srcDir` の下だけで、`app/` ディレクトリがある構成では `shared/` が `srcDir` の外にあったため。

> [!success] After
> レイヤーの shared ディレクトリ（`dir.shared`、デフォルト `shared`）を `rootDir` から解決し、`srcDir` の外ならもう 1 つの `cwd` としてハッシュする（`GetHashOptions['cwd']` は `string | string[]` を受け付ける）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### nuxt, vite: ビルドキャッシュのヒット時にクライアントビルドの状態を復元する（[#36692](https://github.com/nuxt/nuxt/pull/36692)）

> [!quote] Before
> `experimental.buildCache` のキャッシュヒット時はクライアントビルドを飛ばすが、SSR ビルドが読むクライアントビルドのメモリ上の状態（`ssr-styles` のマップ、`stable-entry` のエントリ名、生のクライアントマニフェスト）が復元されなかった。そのため、インライン化済みの CSS に `<link rel="stylesheet">` が残り、コールドビルドと HTML が異なっていた。

> [!success] After
> `@nuxt/kit/internal` に内部 API `addClientBuildState(key, { save, restore })` を追加し、`ssr-styles`・`stable-entry`・`client-manifest` の状態を登録して、キャッシュヒット時もコールドビルドと同じ HTML になる。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### 自動 import した `#app` のコンポーザブルを tree-shake する（[#36696](https://github.com/nuxt/nuxt/pull/36696)）

> [!quote] Before
> `optimization.treeShake.composables` のデフォルトは `#app` の下にだけ名前を挙げているが、自動 import はサブパス（`#app/composables/pages` など）から読み込むため、`definePageMeta`・`definePayloadReducer`・`definePayloadReviver`・`onPrehydrate` が tree-shake されなかった。v4.1.1 以降、すべてのページのチャンクに `definePageMeta()` の呼び出しと import が残っていた（4.x にも影響）。

> [!success] After
> tree-shake のプラグインが自動 import の登録を確認し、`#app` に挙げたコンポーザブルは自動 import 元のサブパスから読み込まれても tree-shake される。デフォルトは変わらず、`#app` から名前を外せば従来どおり対象外にできる。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### vite: `ServerEntryPlugin` に `serverEntry` を渡し、`ssr: false` のサーバーバンドルを小さくする（[#36699](https://github.com/nuxt/nuxt/pull/36699)）

> [!quote] Before
> nitro の Vite environment が有効なとき（Vite ビルドのデフォルト）、`ServerEntryPlugin` がアプリ全体のエントリを受け取り、サーバーは SPA のシェルしか返さないのにアプリ全体がサーバーバンドルに入っていた。

> [!success] After
> `serverEntry` を渡すようにした。12 レイヤーの `ssr: false` のアプリで、SSR environment は 5,332 モジュール・12.0 秒から 104 モジュール・0.3 秒に、ビルド全体は 30.6 秒から 15.1 秒になった。

### nitro: 互換スキャンで、エイリアスのファイルではなくモジュールの仮想モジュールをたどる（[#36687](https://github.com/nuxt/nuxt/pull/36687)）

> [!quote] Before
> Nitro 互換レイヤーがサーバービルドの到達するモジュールコードを調べるとき、`#meta/nitro` のような仮想モジュールを `resolveAlias` で解決していた。モジュールが `#meta` のエイリアスも定義していると、ディレクトリのエイリアスでは実際にはバンドルされないファイルを数えて誤った `NUXT_B9003` を出し、ファイルのエイリアスでは `ENOTDIR` で失敗していた（#36648）。

> [!success] After
> `registrationPaths` と `resolveScopeImport` で、仮想モジュールは id のまま返す（`isModuleVirtual` で判定し、関数のテンプレートも対象）。ビルドの挙動と一致する。

### vite: `fs.allow` の入れ子ディレクトリの除去を二乗の計算量で行わない（[#36702](https://github.com/nuxt/nuxt/pull/36702)）

> [!quote] Before
> `allowDirs` はコンポーネント・プラグイン・ミドルウェア・レイアウトのディレクトリごとに 1 件ずつ入り、大きなアプリでは数千件（多くは重複）になるが、入れ子の除去を全件どうしの比較で行い、重複の除去は最後だった。

> [!success] After
> 先に重複を除き、パスの深さ分の `Set` の検索で入れ子を除く `removeNestedDirs` ヘルパーを追加（結果は同じ）。5,000 コンポーネントのプロジェクトで、`build:before` から `vite:extend` までが 454 ms から 24 ms になった。

### vite: 引用符付きの `import.meta` キーを置換しない（[#36703](https://github.com/nuxt/nuxt/pull/36703)）

> [!quote] Before
> Vite は `@vite-ignore` の worker を `?worker_file&type=ignore` で配信し、`"import.meta.envName"` のような文字列キーを持つ env のプリアンブルを注入する。`nuxt:replace` がそのキーをテキスト置換して不正な JS（`""development""`）にし、dev で PARSE_ERROR になっていた（#36657）。

> [!success] After
> ignore 指定の worker のモジュールを置換の対象から外し、Vite に任せる。通常のモジュールでは引き続き `import.meta.*` の define が置換される。

### ESM の Vue をバンドルし、props・emits のキャッシュをリクエスト間で再利用する（[#36710](https://github.com/nuxt/nuxt/pull/36710)）

> [!quote] Before
> サーバー側で CJS 版の Vue が使われることがあり、Vue の機能フラグなどの最適化が効かず、CJS の interop ヘルパーも入っていた。コンポーネントの props・emits の正規化はリクエストごとに行われていた。

> [!success] After
> ESM のバンドラー向けビルドの Vue を強制し、Vue の重複インストールも防ぐ。nitro では `process.env.NODE_ENV` で dead-code elimination を有効にした。Vue の `propsCache`・`emitsCache` をリクエスト間で共有する。Nuxt UI のページで描画時間の中央値が約 20〜24% 短くなり、サーバーの JS も小さくなった（webpack は 2.87 MB → 1.54 MB など）。`optionsApi` を無効にすると webpack の SSR インライン化が動かなかった不具合も直した。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/サーバーレンダリング|サーバーレンダリング]]

### `navigateTo` がリダイレクトを返すのはミドルウェアの実行中だけにする（[#36650](https://github.com/nuxt/nuxt/pull/36650)）

> [!quote] Before
> `_processingMiddleware` はナビゲーションの開始時に立ち、`afterEach` / `onError` でしか消えなかった。ミドルウェアの実行後もナビゲーションが保留中のとき（遅い `beforeResolve`、非同期のページチャンクの読み込みなど）にコンポーネントから `navigateTo()` を呼ぶと、遷移せずにルートのオブジェクトを返し、ナビゲーションが黙って失われていた。

> [!success] After
> クライアントでは、Nuxt のミドルウェアのガードの直後に登録した `beforeEach` でフラグを消す（vue-router のプラグインとユニバーサルルーターの両方）。

> [!warning] 挙動の変更
> カスタムの `router.beforeResolve` や `onBeforeRouteUpdate` の中で `navigateTo()` を呼ぶと、リダイレクト先を返すのではなく新しいナビゲーションを始める。最終的に同じルートに着く。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### vite: サーバービルドで通常の style ブロックをコンパイルしない（[#36711](https://github.com/nuxt/nuxt/pull/36711)）

> [!quote] Before
> サーバービルドがすべてのコンポーネントの `<style>` ブロックをコンパイルしてから CSS を捨てていた。Nitro の Vite ビルダーでは、`.output` にコピーされない `.css` ファイルが `.nuxt/vite/services/ssr` に書き出されていた。`features.inlineStyles` では `?inline&used` から 2 回目のコンパイルがあり、どちらの設定でも最初のコンパイルは無駄だった。

> [!success] After
> `ssr` environment では、通常の style の import を 1 つの空の副作用なしモジュールに解決する。CSS Modules と `?inline` 付きのもの（インライン化・カスタム要素）は引き続きコンパイルされ、インライン化の挙動は変わらない。2,860 コンポーネントのアプリで、SSR のモジュール数が 6,727 → 5,332（インライン style 有効時）などに減った。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]
