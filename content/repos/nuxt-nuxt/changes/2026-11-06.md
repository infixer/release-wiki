## 新機能

### nitro: Nitro の rspack ビルダーに対応（[#36841](https://github.com/nuxt/nuxt/pull/36841)）

> [!tip] 何ができるようになったか
> nitro `3.0.261103-rc` に入った実験的な `rspack` ビルダーを、Nuxt を webpack・rspack でビルドするときに警告なしで使えるようになった。
>
> - **使い方**: `defineNuxtConfig({ builder: 'rspack', nitro: { builder: 'rspack' } })`
> - **変更点**: `[nitro] WARN The rspack builder ignores these rollupConfig / rolldownConfig options: tsconfig. Use rspackConfig instead.` の警告を出さないようにし、解決した `@rspack/core` のバージョンを nitro に渡して再インストールを求められないようにした
> - **嬉しい場面**: サーバー側も rspack でビルドしたいとき（ドキュメント `docs/2.directory-structure/1.server.md` に追記）

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### Rsbuild ビルダー `@nuxt/rsbuild-builder` を追加（[#36499](https://github.com/nuxt/nuxt/pull/36499)）

> [!tip] 何ができるようになったか
> 新しいビルダーパッケージ `@nuxt/rsbuild-builder` を追加し、`builder: 'rsbuild'` で有効にできる。これまでの rspack ビルダーは Rsbuild を dev サーバーとコンパイラーのライフサイクルにだけ使い、Rspack の設定は webpack のプリセットから作っていたが、新しいビルダーはビルドそのものを Rsbuild に任せる。
>
> - **使い方**: `defineNuxtConfig({ builder: 'rsbuild' })`
> - **中身**: `client` と `server` は Rsbuild の environment。エントリ・define・エイリアス・出力パス・ソースマップ・externals・SWC によるデコレーターと JSX・Lightning CSS と PostCSS による CSS・チャンク分割・dev サーバーと HMR を Rsbuild のオプションで扱い、Vue は `@rsbuild/plugin-vue` を使う。Nuxt 独自の処理は `processAssets`・`transform`・`modifyBundlerChain` などを使う Rsbuild のプラグインにした
> - **Rspack の設定のまま残るもの**: `modulesDir` からのパッケージ・ローダーの解決、`experimental.clientNodeCompat` の Node.js ポリフィル、webpack ビルダーと共有する SSR styles のプラグイン、`webpack-bundle-analyzer` によるバンドル分析
> - dev では Rsbuild の dev サーバーが Nuxt の dev サーバーの後ろでミドルウェアモードで動き、HMR のソケットは同じポートを使う（rspack ビルダーと同じ）

> [!warning] 移行が必要
> `@nuxt/rspack-builder` は非推奨になった（#35489 で Rsbuild の上に移したビルダー）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### `experimental.staticRoutes` でサーバーのルーターのマッチャーを使い回す（[#36867](https://github.com/nuxt/nuxt/pull/36867)）

> [!tip] 何ができるようになったか
> 既定では SSR のリクエストごとに新しい `Router` を作り、`createRouter` が `routes` から vue-router のマッチャーを作り直している（bench の `large` フィクスチャでは小さなページの描画時間の約半分）。`experimental.staticRoutes` を有効にすると、サーバーは `routes` の配列ごとに 1 つのマッチャーを作り、各リクエストの `createRouter` に渡す。
>
> - **使い方**: `experimental: { staticRoutes: true }`
> - **効果の例**（`large` フィクスチャ、8 接続）: `/` 1324 → 2700 req/s（+104%）、`/catalog/3` 1411 → 2932 req/s（+108%）、`/table` 247 → 292 req/s（+18%）、`/table/plain` 322 → 386 req/s（+20%）
> - **有効にしたときの制約**: `early404` も有効になる（レイヤーが明示的に `false` にしていなければ）。`router.addRoute`・`removeRoute`・`clearRoutes` は `NUXT_E2014` を投げ、`useRouter` の型からも外れる。`routes` を書き換える `router.options` ファイルはビルドエラー（`NUXT_B4027`）になる
> - **嬉しい場面**: ルートが多いアプリで SSR のスループットを上げたいとき（vuejs/router#2804 の続き）

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/ルーティング・レイアウト|ルーティング・レイアウト]]

### ビルドキャッシュのヒット時に復元した SSR ビルドを使い回す（perf）（[#36810](https://github.com/nuxt/nuxt/pull/36810)）

> [!quote] Before
> `experimental.buildCache` のヒット時にクライアントと SSR の出力を復元しても、nitro が SSR の environment をもう一度ビルドしていた（本番で約 4.4 秒）。キャッシュキーに nitro のオプションや SSR ビルドが読む仮想モジュールが入っていないため、単純に飛ばすのは安全ではない（`node-server` の後の `NITRO_PRESET=cloudflare-module nuxt build` でも同じキーになる）。

> [!success] After

> プロジェクトが `h3` を v1 に解決し、`nitroLegacy.h3` が無効なとき、`h3` から値を import しているサーバーのファイルを `NUXT_B9009` の警告で一覧にする（`nuxt/server` か `nitro/h3` から import するか、移行前に出すなら `nitroLegacy.h3` を有効にするよう案内）。アップグレードガイドも更新。

> [!warning] 移行が必要
> `h3` を依存から外し、`nuxt/server`（または `nitro/h3`）から import する。すぐに移行できない場合は `nitroLegacy.h3` を有効にすると h3 v1 のヘルパーに解決される。

### vite: エントリが必要とする静的 import をエントリと一緒にバンドル（perf）（[#36862](https://github.com/nuxt/nuxt/pull/36862)）

> [!quote] Before
> Nuxt UI のマーケティングページ（約 690 コンポーネント）では、最初に読む JS が多数の小さなチャンクに分かれていた（`/` で 18 ファイル・gzip 175.3 kB）。rolldown がエントリと遅延チャンクで共有するモジュール（vue など）を別の共通チャンクにすること、レイアウトの依存が使うページの組み合わせごとに共通チャンクに分かれることが原因。

> [!success] After
> `$initial` の印が付いたモジュールをエントリのチャンクに入れ、レイアウトが 1 つだけの app ではそのレイアウトの静的な依存を 1 つのチャンクにまとめる（`experimental.layoutChunk: false` で無効化。例では 6 ファイル・167.0 kB）。dev、クライアントのエントリが複数のとき、`codeSplitting`・`manualChunks`・`advancedChunks`・`inlineDynamicImports` を設定済みのときは行わない。初期の依存がエントリに入るため、初期のグラフが変わるとすべて再ダウンロードになる（キャッシュとのトレードオフ）。
