## 新機能

### `<NuxtErrorBoundary>` がサーバー側のエラーも捕捉（`experimental.ssrErrorBoundary`）（[#36990](https://github.com/nuxt/nuxt/pull/36990)）

> [!tip] 何ができるようになったか
> これまで `<NuxtErrorBoundary>` はクライアント側のエラーしか捕捉せず、SSR 中に投げたコンポーネントは `error.vue` まで素通りしていた。サーバーでも働くようになり、`<BrokenWidget>` がサーバーで投げても、レスポンスは `200` でページの残りはそのまま、その場所に `#error` スロットが描画され、クライアントも同じ状態（エラーの代替表示）でハイドレーションする。
>
> - **使い方**: `<NuxtErrorBoundary>` の中にコンポーネントを置き、`<template #error="{ error, clearError }">` で代替表示を書く（`error.status` を参照できる）
> - **有効化**: `experimental.ssrErrorBoundary`（`compatibilityVersion: 5` ではデフォルト有効）
> - **エラーの中身**: `createError` などの HTTP エラーは `status` と `data` を保つ。本番ではそれ以外のエラーはスロットに素の `500` として渡り、サーバーのエラーメッセージは HTML に出ない
> - **非推奨**: `retry-on-client` はマウント後にデフォルトスロットを描画し直す（`<NuxtClientFallback>` と同じ動き）ため、`<NuxtClientFallback>` は別コンポーネントとしては非推奨になった。両者は共通の SSR バッファのヘルパーを使い、クライアントフォールバックが入れ子の非同期コンポーネントを待たない問題も直った
> - **嬉しい場面**: ページの一部のウィジェットが SSR で失敗しても、ページ全体をエラーページにしたくないとき

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/コンポーネント・テンプレート|コンポーネント・テンプレート]]、[[repos/nuxt-nuxt/topics/サーバーレンダリング|サーバーレンダリング]]

### 完成した HTML 文書を受け取る `render:document` フック（[#36989](https://github.com/nuxt/nuxt/pull/36989)）

> [!tip] 何ができるようになったか
> Nuxt 5 でサーバーに依存せず使えるフックは `render:html` だけで、リスナーは登録順に動くため、後から登録したリスナー（アプリ自身の `server/plugins/` のファイルすべてを含む）が足したものは届かなかった。完成した文書を受け取る `render:document` フックが加わった（`@nuxtjs/critters` のように、ページ全体から使われているセレクターを調べて head やスタイルシートの link を書き換えるモジュール向け）。
>
> - **使い方**: レンダラープラグイン、または `useServerHooks()` で登録する（どのサーバービルダーでも動く）
> - **呼ばれる場合**: バッファしたページ・エラーページ・`ssr: false` のルートでは呼ばれる。ストリーミングの応答（完成した文書が無い）とサーバーコンポーネントでは呼ばれない。`@nuxt/vite-server` の静的な SPA の文書では `render:html` の後に呼ばれる（ビルドごとに 1 回、dev ではナビゲーションごと）
> - **性能**: レンダラーはリスナーが `html` を読んだときだけ文書をシリアライズするので、置き換えない限り応答はチャンクごとのエンコード（#36719）のまま
> - **嬉しい場面**: Nuxt 4 で `render:response` を使っていた処理を、Nuxt 5 で移植したいとき

### vite-server: サーバービルドにデプロイ先（`target`）を記録（[#36964](https://github.com/nuxt/nuxt/pull/36964)）

> [!tip] 何ができるようになったか
> `nuxt build` はサーバービルダーのデプロイ先を表示するが、値を入れていたのは nitro だけだった。`@nuxt/vite-server` でも、使っているデプロイ先のプラグインから `target` を決める（nuxt/cli#1671 と対になる変更）。
>
> - **判定**: デプロイ先のプラグイン無し → `node`、`@cloudflare/vite-plugin` → `cloudflare`、`build.enabled` 付きの `@netlify/vite-plugin` → `netlify`（無ければ dev のエミュレーションだけなので `node`）、`vite-plugin-vercel` → `vercel`、`@universal-deploy/vite` の node アダプター → `node`
> - **未定（`undefined`）**: `ssr` の入力を持つ知らないプラグイン、`ssr: false`、`nuxt generate`
> - **嬉しい場面**: vite-server の構成でも、ビルド時にどのデプロイ先向けかを確認したいとき

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

## 変更・修正

### `vue`・`vue-router` を `nuxt` の peer dependency に（破壊的変更）（[#36979](https://github.com/nuxt/nuxt/pull/36979)）

> [!quote] Before
> `nuxt` は `vue`・`vue-router` に直接依存しており、スターターにも入っているため、更新が重なると（特にモノレポで）プロジェクトの中に Nuxt のものと違うバージョンの `vue` が入りやすかった。

> [!success] After
> `vue`・`vue-router` を `nuxt` の peer dependency にした（`vue-router` は `pages/` のときだけ実行時に import するので省略可能な peer dependency）。起動時に両方が無ければインストールを促し、`vue` のバージョンが Nuxt の要求を満たすかも確認する。

> [!warning] 移行が必要
> プロジェクトの `package.json` に `vue`（`pages/` を使うなら `vue-router` も）が無ければ追加する。2023 年以降の新規プロジェクトには両方が入っているので、影響は少ない（アップグレードガイドにも追記）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### バンドルする Vue の import をすべて 1 つのコピーに解決（[#36978](https://github.com/nuxt/nuxt/pull/36978)）

> [!quote] Before
> Vite の `resolve.dedupe` は `vue` が Vite のルートから解決されるときだけ働くため、そうでないプロジェクト（モノレポなど）では Vue のコピーが重複することがあった。

> [!success] After
> Vue のランタイムのパッケージ（`vue`・`@vue/runtime-dom`・`@vue/runtime-core`・`@vue/reactivity`・`@vue/shared`・`@vue/server-renderer`・`@vue/runtime-vapor`）のバンドルされる import をすべて、Vue 自身の依存の連鎖をたどって Nuxt が解決したコピーに向ける（vite・webpack・rsbuild）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/モジュール解決・ビルド|モジュール解決・ビルド]]

### vite: 外部化した `shared/` の import を絶対パスのまま保つ（[#36973](https://github.com/nuxt/nuxt/pull/36973)）

> [!quote] Before

### vite: インライン style のためにクライアントと SSR のエントリを別々に追跡（[#37003](https://github.com/nuxt/nuxt/pull/37003)）

> [!quote] Before
> `features.inlineStyles` が有効で、モジュールがクライアントのエントリだけを差し替えると（`nuxt-booster` がクライアントの `input.entry` をラッパーに替えるなど）、サーバー描画の HTML にグローバルな CSS がまったく入らなかった。

> [!success] After
> クライアントと SSR のエントリを別々に追跡し、サーバーで style を抽出するときはクライアントのエントリをエントリ単位の CSS の元として扱う。

### ペイロードのキーをソートして決定的にシリアライズ（[#36982](https://github.com/nuxt/nuxt/pull/36982)）

> [!quote] Before
> ペイロードのキーは非同期処理が終わった順に追加され、devalue の出力は挿入順に従うため、同じデータでも描画ごとに `_payload.json` のバイト列が変わった（npmx.dev で 15645 B と 15683 B）。内容から作る ETag が一致せず、ISR の書き込みや CDN のキャッシュのミスが増えていた。

> [!success] After
> ペイロードをシリアライズするときに `data`・`state`・`once`・`_errors` のキーをソートする（性能への影響は誤差の範囲）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/サーバーレンダリング|サーバーレンダリング]]

### perf: キャッシュするルートのペイロード URL にビルド ID を付けない（[#36983](https://github.com/nuxt/nuxt/pull/36983)）

> [!quote] Before
> ペイロードの URL にはすべて `?_b=<buildId>` が付き、クエリ文字列ごとにキャッシュ・CDN のエントリが分かれるため、デプロイのたびに前のビルドのクライアントがペイロードを生成し直させていた。

> [!success] After
> キャッシュするルート（`isr`・`swr`・`cache`）では、クライアントとサーバー描画の preload の link の両方で `_b` を付けない（これらのルートではペイロードがデプロイ中にも変わり、サーバーは `_b` を取り除いており、ペイロード自体が持つ `buildId` を `isOutdatedPayload` で確認しているため）。

⏳ 未リリース · トピック: [[repos/nuxt-nuxt/topics/サーバーレンダリング|サーバーレンダリング]]、[[repos/nuxt-nuxt/topics/プリフェッチ・ナビゲーション|プリフェッチ・ナビゲーション]]

### vapor コンポーネントから `<ClientOnly>` の fallback スロットを描画（[#36991](https://github.com/nuxt/nuxt/pull/36991)）

> [!quote] Before
> 最新の Vue 3.6 RC では、vapor コンポーネントの中の `#fallback` スロット付き `<ClientOnly>` が SSR で `TypeError: _push is not a function` になっていた（サーバーレンダラーが vapor のスロットを 2 引数の関数で包み、`h` で描画するとそれを関数型コンポーネントとして扱うため）。

### クエリをルーターと同じ方法で解析・シリアライズ（[#36988](https://github.com/nuxt/nuxt/pull/36988)）

> [!quote] Before
> 一部の処理がルーターではなく `ufo` でクエリを扱い、vue-router と結果が違った。ミドルウェアの `navigateTo('/search?flag', { replace: true })` が `/search?flag=` になり、外部 URL への `navigateTo` のオブジェクト指定（`query: { q: '', path: 'a/b' }`）が `?q&path=a%2Fb` になっていた。外部 URL を指すオブジェクトの `to` の `<NuxtLink>` と、その custom スロットの `route.query`（`?flag` が `null` でなく `''`）も同様。

> [!success] After
> `#build/pages` から `parseQuery`・`stringifyQuery` を公開し、ルーターと同じもの（`pages/` があれば vue-router のもの、または `router.options` の上書き。無ければ `ufo`）を使う。

### `ssrRoutes` に情報を落とさない rou3 のパターンを出力（[#36997](https://github.com/nuxt/nuxt/pull/36997)）

> [!quote] Before
> `ssrRoutes` を作るときに `(...)` と `?` をすべて取り除いていたため、npmx ではリクエストの多くが `/__fallback` 関数に誤って振り分けられていた（例: `/x/:id?` → `/x/:id`、`/:slug(.*)*` → `/**:slug`）。

> [!success] After
> `vueRouterToRou3` で、まとめたり展開したりせずに作る。パラメータは名前を保ち、1 つのページのパスは 1 つのパターンになる（例: `/x/:id?` → `/x/:id?`、`/:slug(.*)*` → `/:slug(.*)`）。
