## 変更・修正

### `--changed` の絞り込み後にセットアップファイルが再実行されない問題を修正（[#11621](https://github.com/vitest-dev/vitest/pull/11621)）

> [!quote] Before
> 影響を受けたモジュールをたどる処理が、テストファイルとセットアップファイルをファイルパスで取得していたため、モジュールグラフにそのパスがモジュールの url として残り、`isolate: false` のワーカーがセットアップファイルを無効化しなかった（#11586）。

> [!success] After
> ワーカーが import するのと同じ url を使ってたどる。fs のモジュールキャッシュには url を保存しないようにしたので、5.0.4・5.0.5 で書かれたキャッシュも回復する。

⏳ 未リリース · トピック: [[repos/vitest-dev-vitest/topics/テストの絞り込み|テストの絞り込み]]、[[repos/vitest-dev-vitest/topics/キャッシュ|キャッシュ]]

### 静的な収集でも fs のモジュールキャッシュを使う（[#11622](https://github.com/vitest-dev/vitest/pull/11622)）

> [!quote] Before
> 静的な収集（`experimental.preParse`、`parseSpecifications`、typecheck）は `transformRequest` でテストファイルを変換していたため、fs のモジュールキャッシュを読まず、テストファイルをファイルパスで登録していた。

> [!success] After
> 影響を受けたモジュールをたどる処理と同じく、変換サービス（transform service）を使う（#11621 の上に積んだ変更）。

⏳ 未リリース · トピック: [[repos/vitest-dev-vitest/topics/キャッシュ|キャッシュ]]

### 並行する import にも同じモックを返す（[#11623](https://github.com/vitest-dev/vitest/pull/11623)）

> [!quote] Before
> モックファクトリーの実行中に始まった import で正しくモックが返らないことがあった（#7040）。ファクトリーの中からの import かどうかは、import 元の共有コールスタックの印で判定していた。automock・スパイされたモジュールを並行して import すると、2 つ目の import は中身が入る前の automock のオブジェクトを受け取っていた。

> [!success] After
> ファクトリーの実行中に始まった import は完了を待って同じモックを受け取り、元のモジュールを受け取るのはファクトリーの中からの import だけになった（判定は `AsyncLocalStorage` で行う）。モックを待つモジュールをファクトリーが import した場合は、通常の import の循環と同じく途中までの export を受け取り、止まらなくなった。並行する import は、`resolveMocks` が登録中のモックや、automock・スパイの完了も待つ。

⏳ 未リリース · トピック: [[repos/vitest-dev-vitest/topics/モック|モック]]

### 終了処理中に保留中の console のログで失敗しないように（[#11619](https://github.com/vitest-dev/vitest/pull/11619)）

> [!quote] Before
> #9727 以降 `onUserConsoleLog` は await される呼び出しになったため、ワーカーの終了中に送られたログが拒否され、未処理のエラーとして報告されていた（#11153）。

> [!success] After
> その時点でメッセージは送信済みなので、ワーカーは終了処理による拒否を無視する。

⏳ 未リリース · トピック: [[repos/vitest-dev-vitest/topics/ランタイム|ランタイム]]

### browser: トレースの位置は最初のフレームだけソースマップで解決（[#11613](https://github.com/vitest-dev/vitest/pull/11613)）

> [!quote] Before
> トレースビューで各ステップの位置を求めるとき、使うのは最初の使えるフレームだけなのに、サーバーがスタックの全フレームをソースマップで解決し、その間ブラウザが待っていた。コストはスタックの深さに比例した（Firefox ではエントリごとに約 40 フレーム）。

> [!success] After
> 解決でき、かつ除外されない最初のフレームで止める。Playwright の `browser.trace` のアクションの位置も同じ方法で求めているため、同じ変更が入った。`traceView: true` で `expect.element(...).toBeVisible()` を 200 回呼ぶ例では、Chromium が 544ms → 349ms、Firefox が 5674ms → 326ms になった。

⏳ 未リリース · トピック: [[repos/vitest-dev-vitest/topics/ブラウザモード|ブラウザモード]]
