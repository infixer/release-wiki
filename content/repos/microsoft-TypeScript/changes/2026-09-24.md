## 新機能

### `createSourceFile` / `createSourceFileFromFile` を tsgo に移植（[#64216](https://github.com/microsoft/TypeScript/pull/64216)）

> [!tip] 何ができるようになったか
> TS API の `createSourceFile` / `createSourceFileFromFile` が tsgo（TypeScript 7 のネイティブコンパイラ）側の API に移植された（#63875 の一部）。
>
> - **使い方**: `createSourceFile(fileName: string, sourceText: string, options?: CreateSourceFileOptions)` / `createSourceFileFromFile(file: DocumentIdentifier, options?: CreateSourceFileOptions)`
> - **嬉しい場面**: API でソースファイルを直接生成したいとき

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/プログラム的API|プログラム的API]]

### プリンターをトップレベル API に移動し `printFile` を追加（[#64320](https://github.com/microsoft/TypeScript/pull/64320)）

> [!tip] 何ができるようになったか
> プリンター機能はスナップショットの状態を使っていなかったため、スナップショットからトップレベルの API に移動し、`printFile` メソッドとして呼べるようになった。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/プログラム的API|プログラム的API]]

### API ノードに `childrenIter` メソッドを追加（[#64302](https://github.com/microsoft/TypeScript/pull/64302)）

> [!tip] 何ができるようになったか
> コールバック方式の `forEachChild` に代わる、ジェネレーターベースの `childrenIter()` メソッドが API のノードに追加された。
>
> - **使い方**: `for (const n of node.childrenIter()) { ... }` のように、async 関数やジェネレーター関数の中で子ノードを列挙できる
> - **嬉しい場面**: 非同期・ジェネレーターコンテキストで木を再帰的にたどりたいとき

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/プログラム的API|プログラム的API]]

### コード生成をすべてインクリメンタルキャッシュ対応に（[#64331](https://github.com/microsoft/TypeScript/pull/64331)）

> [!tip] 何ができるようになったか
> リポジトリ内のすべてのコード生成にインクリメンタルキャッシュのラッパーが付き、キャッシュが再利用できる場合は `generate` サブタスクの時間を最大 80% 短縮できるようになった。
>
> - **嬉しい場面**: エージェントがファイルを変更したかどうかにかかわらず、念のため `generate` 系のタスクを繰り返し実行するような場面

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/開発ツールとCI|開発ツールとCI]]

### モジュール解決をオーバーライドする API を追加（[#64299](https://github.com/microsoft/TypeScript/pull/64299)）

> [!tip] 何ができるようになったか
> API プログラムでモジュール解決をオーバーライドする方法が追加された（[#64069](https://github.com/microsoft/TypeScript/issues/64069)）。
>
> - **使い方**: `using resolver = api.createModuleResolver(compilerOptions)` で独立したモジュールリゾルバーを作り、`resolver.resolveModuleName(name, containingDirectory, moduleKind, { snapshot? })` でホストのファイルシステムや既存のスナップショットに対して解決できる。`moduleResolutions` オプションで、モジュール名・ディレクトリ・モードごとに解決結果を静的に指定することもできる（`fallback: "resolve"` で指定外はデフォルトの解決に委譲、`"unresolved"` で未解決扱いにできる）
> - **嬉しい場面**: API 利用者がモジュール解決の挙動を自分でカスタマイズしたいとき

### `api.updateSnapshot()` を `createSnapshot` / `snapshot.update` に置き換え（[#64204](https://github.com/microsoft/TypeScript/pull/64204)）

> [!quote] Before
> API は「最新のスナップショット」を追跡しており、`api.updateSnapshot()` でプログラムを更新していた。プログラム作成時に `oldProgram` を渡してインクリメンタルに更新することもできた。

> [!success] After
> `api.updateSnapshot()` を廃止し、LSP モード専用の `api.getCurrentLanguageServerSnapshot(changes?)` と、常に使える `api.createSnapshot(changes?)` に置き換えた。任意のスナップショットから `snapshot.update(changes)` で新しいスナップショットを作れる。`changes` には `createPrograms`（プログラムの追加）・`reconfigurePrograms`（ルートファイル・オプション・参照の変更）・`ensurePrograms`（指定したプロジェクト、または `true` で全プロジェクトを最新化）を渡せる。

> [!warning] 移行が必要
> `oldProgram` オプションは廃止された。代わりにファイルの変更を通知したうえで `ensurePrograms` を使ってインクリメンタルに更新する必要がある。

### `tsc -b` のビルドスケジューリングを依存の深さ順に変更（[#64220](https://github.com/microsoft/TypeScript/pull/64220)）

> [!quote] Before
> `tsc -b` はプロジェクトを参照の深さ優先順で各ビルダーに割り当てており、長い依存チェーンの根本を担当したビルダーはチェーン全体の処理が終わるまでアイドル状態になっていた。19,430 個の composite project、依存の深さ 124 段のモノレポでは、32 個のビルダーのうち平均で約 13 個しか稼働していなかった（[#64222](https://github.com/microsoft/TypeScript/issues/64222)）。

> [!success] After
> `computeScheduleOrder()` がトポロジカル順序を依存の深さで安定ソートするようにし（依存のないプロジェクトから順に）、ビルダーはその順序でプロジェクトを受け取るようになった。ビルダーが深さ k のプロジェクトを担当する時点で、それより浅いプロジェクトはすべて着手済みになるため、上流プロジェクトを待つアイドル時間を減らせる。`--verbose`/`--dry` の出力順は変わらない。

### ローカライズ・vendoring タスクをコード生成キャッシュの対象に追加（[#64392](https://github.com/microsoft/TypeScript/pull/64392)）
