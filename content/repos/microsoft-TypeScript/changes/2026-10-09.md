## 新機能

### API: ベータ版リリースに向けた整理（[#64681](https://github.com/microsoft/TypeScript/pull/64681)）

> [!tip] 何ができるようになったか
> プログラム的 API をベータ版として公開する準備として、モジュールの公開範囲と名前を整理した。
>
> - モジュールの export から `/unstable` の接頭辞を外した
> - `"typescript/ast"` から `factory` を export する
> - プロファイリング用のヘルパーを含む `api.internal` 名前空間を `api.debug` に改名
> - `snapshot.internal.formatNodeForInsertion` を `languageService.formatNodeForInsertion` に移動
> - `api.createBuildOrchestrator` は当面 `@internal` 扱いにし、`--stripInternal` でコンパイルする

> [!warning] 移行が必要
> `/unstable` 付きのパスからの import、`api.internal`、`snapshot.internal.formatNodeForInsertion` を使っているコードは新しい名前に書き換える。`@deprecated` だった関数・メソッドは削除された。`api.createBuildOrchestrator` は型定義から外れる（`@internal` と `--stripInternal`）。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/プログラム的API|プログラム的API]]

### VS Code 拡張が API クライアントのモジュールを公開（[#64647](https://github.com/microsoft/TypeScript/pull/64647)）

> [!tip] 何ができるようになったか
> VS Code 拡張には、他の拡張が実行中の TypeScript の LSP サーバーに API クライアントで接続する仕組みが既にあったが、クライアントとサーバーはバージョンを揃える必要がある。ユーザーはワークスペースの TypeScript や複数の同梱版から LSP サーバーを選べるため、拡張が正しいバージョンの API クライアントを解決して渡せるようにした。
>
> - **使い方**: 他の拡張は `import type { ExtensionAPI } from "typescript/vscode"` を型のためだけ（devDependency）に使い、API クライアント自体は拡張から受け取る
> - **嬉しい場面**: これまでは拡張自身が依存する `typescript/async` の `API` を使っていたため、サーバーとバージョンが食い違う接続になり得た

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/プログラム的API|プログラム的API]]、[[repos/microsoft-TypeScript/topics/言語サービス|言語サービス]]

## 変更・修正

### 宣言の出力で再 export するモジュールを索引化し、インクリメンタルの再ビルドを大幅に高速化（[#64469](https://github.com/microsoft/TypeScript/pull/64469)）

> [!quote] Before
> 広く import されるモジュールを（コメントだけでも）編集すると、最初のインクリメンタル再ビルドが `noEmit` でもフルチェックより遅くなった（#64464）。依存ファイルのシグネチャ計算のための宣言出力で、`getAlternativeContainingModules` がシンボルごとにプログラム内のすべての外部モジュールの export を走査していた。

> [!success] After
> チェッカーが初回の利用時に「解決済みの export 先 → それを export する外部モジュール」の索引を 1 つ作り、そこから答える。結果は以前の走査と同じ。issue の再現（9,066 ファイル）では、コメントだけの編集後の最初の再ビルドが 45.7 秒から 3.5 秒になった。通常の宣言出力も速くなる。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/ビルドとファイル監視|ビルドとファイル監視]]、[[repos/microsoft-TypeScript/topics/型チェッカー・コンパイラ|型チェッカー・コンパイラ]]

### シンボルのデータ部分を共有し、インスタンス化したシンボルを 96 バイトから 24 バイトに（[#64691](https://github.com/microsoft/TypeScript/pull/64691)）

> [!quote] Before
> チェッカーでインスタンス化したシンボルは、元のシンボルと同じ大きさ（96 バイト）を持っていた。

> [!success] After
> `Symbol` をヘッダー部分とデータ部分に分けた（通常は一緒に確保される）。チェッカーでインスタンス化したシンボルは元のシンボルとデータ部分を共有し、24 バイトになった。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/型チェッカー・コンパイラ|型チェッカー・コンパイラ]]

### 計算されたプロパティ名を、親の文法エラーに関係なく常にチェック（[#64674](https://github.com/microsoft/TypeScript/pull/64674)）

> [!quote] Before
> 親に文法エラーがあると計算されたプロパティ名がチェックされず、診断が不安定になっていた。`skipLibCheck` を多用すると `.d.ts` の作者から見えなくなることもあった。

> [!success] After
> 計算されたプロパティ名を常にチェックし、診断が安定する（enum の計算された名前での非推奨参照・import した値などのテストを追加）。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/型チェッカー・コンパイラ|型チェッカー・コンパイラ]]

### 名前空間の束縛を持たない deferred import を拒否（[#64640](https://github.com/microsoft/TypeScript/pull/64640)）

> [!quote] Before
> 名前空間の束縛を持たない deferred import が拒否されていなかった（#64627）。

> [!success] After
> 文法チェックで新しい診断メッセージとしてエラーを報告する。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/型チェッカー・コンパイラ|型チェッカー・コンパイラ]]

### 不正な分割代入の emit でのクラッシュを修正（[#64651](https://github.com/microsoft/TypeScript/pull/64651)）

> [!quote] Before
> クラスフィールドや ES デコレータの変換が、不正な分割代入のノードにも適用され、正しいソースを前提にした assert でクラッシュしていた（#64458 で報告）。

> [!success] After
> その assert を削除し、不正な部分木を受け入れる（似たコードパスの既存の方針に合わせた）。#63972・#63973・#64472 を置き換える修正。

⏳ 未リリース · トピック: [[repos/microsoft-TypeScript/topics/型チェッカー・コンパイラ|型チェッカー・コンパイラ]]

### デコレータ付きクラスで重複したプライベート名があると emit がクラッシュする問題を修正（[#64670](https://github.com/microsoft/TypeScript/pull/64670)）

> [!quote] Before
> デコレータ付きクラスでプライベート名が重複していると、クラスフィールドの変換でクラッシュしていた（#64665）。

> [!success] After

### プログラムの無い推論プロジェクトで `workspace/symbol` がクラッシュする問題を修正（[#64642](https://github.com/microsoft/TypeScript/pull/64642)）

> [!quote] Before

> [!success] After
