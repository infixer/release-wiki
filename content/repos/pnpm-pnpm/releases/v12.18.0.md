## 要点

- **platform variants**（`serverType: pnpr` と宣言したレジストリが必要）: `pnpm pack` が `publishConfig.variants` の項目ごとにアーカイブを作り、プラットフォームのバリアントは `<name>-<version>~<tag>.tgz`。`pnpm pack --variant <target>` でその target の項目だけ、`pnpm pack --json` は各アーカイブの `integrity` と `size` を出す
- `pnpm publish` が `publishConfig.variants` を公開する。参照する公開要求の前にすべてのアーカイブを上げる。ほかのレジストリへのバリアントの公開は、`any` を対象にするアーカイブだけを公開する `--no-variants` が無ければ拒否
- `pnpm publish --upload-variant <target>` が 1 つの項目のアーカイブをレジストリのステージの領域に上げて `<target>=<integrity>` を出し、`pnpm publish --variant-integrity <target>=<integrity>` でほかのジョブが上げたアーカイブからバージョンを公開する（`--recursive` では `<name>~<target>=<integrity>`）
- `pnpm publish -r --batch` は各パッケージのアーカイブを個別の要求で上げ、レジストリが持っているものは飛ばすので、一括の要求が公開するアーカイブとともに大きくならない（256 を超えるパッケージの一括は従来どおりインライン）。`publishConfig.variants` を持つパッケージも一括で公開できる（本文はここで切れている）
- **エージェントスキル**: 依存のスキルへのリンクをスキルの名前だけで付ける（`@acme/kit` の `skills/auth/` は `.claude/skills/pnpm-@acme+kit-auth` ではなく `.claude/skills/auth`）。次のインストールで古い名前のリンクを置き換え、リンクしたスキルを各ディレクトリの `.gitignore` の `# pnpm` ブロックに並べる（[#17455](https://github.com/pnpm/pnpm/discussions/17455)）。同じ名前のスキルがあるとき・名前が使われているときは `pnpm-<package>-<skill>` でリンクする（以前はインストールが失敗）
- `pnpm approve` が、複数のスキルを持つパッケージでどのスキルをリンクするかを尋ね、`permissions.<pkg>.skills: [guide, migrate]` のように記録する。初めてスキルを承認するときは、リンク先のエージェントのディレクトリも尋ねて `skills.dirs` に記録する。`skills/engineering/implement/SKILL.md` のようなカテゴリのディレクトリの中のスキルも `skills/` から 3 階層までリンクする
- 概要の説明によると、ダウンロードした tarball からのオフラインのインストール用の `pnpm store add` が加わり、繰り返しのインストールと `verifyDepsBeforeRun` が変わっていないワークスペースのプロジェクトの `package.json` を読まなくなり、peer 依存の解決のいくつかの不具合が直った
