## 要点

- `pnpm deploy` が、ソースにリンク先の無いプロジェクトのシンボリックリンク（ビルド後に消した `node_modules` へのリンクなど）を残す。以前は `ENOENT` で失敗していた（[#17571](https://github.com/pnpm/pnpm/issues/17571)）
- `bundledDependencies` とビルドスクリプトを持つパッケージを副作用キャッシュから戻しても bundled 依存を保つ（[#17523](https://github.com/pnpm/pnpm/issues/17523)）。`pnpm install` が、前の `pnpm install --no-runtime` で飛ばしたランタイムをリンクする（[#17542](https://github.com/pnpm/pnpm/issues/17542)）
- `bin` のパスに余分な親ディレクトリの区切り（`../dist/cli.js` など）があるパッケージのコマンドが欠けない（パッケージの中に解決する）（[#17586](https://github.com/pnpm/pnpm/issues/17586)）。POSIX のシェルのシムはパスをクォートする。`extendNodePath` を変えた後の繰り返しの `pnpm install` が bin のシムを書き直す（以前は「Already up to date」）
- `excludeLinksFromLockfile` と `linkWorkspacePackages` がオンで、素のバージョンの範囲や `catalog:` でワークスペースのパッケージに依存するとき、`pnpm install --frozen-lockfile` が自分の書いた lockfile を受け付ける（以前は `ERR_PNPM_OUTDATED_LOCKFILE`）
- `*` の依存をプレリリースの `latest` に解決した lockfile を、`--frozen-lockfile`・`pnpm approve-builds`・`pnpm rebuild` が受け付ける（[#17594](https://github.com/pnpm/pnpm/issues/17594)）。既定のレジストリのパッケージは、`npmjs` などの接頭辞が `registry` を指していても素の lockfile のキーのまま（[#17575](https://github.com/pnpm/pnpm/issues/17575)）
- プロジェクトごとの lockfile のとき、ルートの `overrides` の相対パスをワークスペースのルートから解決する（[#17691](https://github.com/pnpm/pnpm/issues/17691)）。optional の peer の提供元が無いとき、peer の重複排除が直接と推移的な経路で同じ依存を別々のコピーにしない（[#17666](https://github.com/pnpm/pnpm/issues/17666)）
- `devEngines.runtime` などの `>=26.13` のような Node.js のバージョンの範囲を、満たす最新の安定版に解決する（本文はここで切れている）
- 概要の説明によると、ワークスペースでの `pnpm link` と、`verifyDepsBeforeRun` が不要なインストールを始める問題も直った
