## 要点

- **セキュリティ**: content encoding の多すぎるレジストリの応答で pnpm が落ちなくなった（undici 7.30.1。[GHSA-xjj6-f33q-929c](https://github.com/advisories/GHSA-xjj6-f33q-929c)）
- `pnpm install` のワーカーのプールと既定の `workspaceConcurrency` を、コンテナの CPU の上限（Kubernetes の CPU の制限など）に合わせる。4 CPU の上限で数百の CPU のホストの CI では、数百のワーカーを作ってメモリを使い切っていた（[#17382](https://github.com/pnpm/pnpm/issues/17382)）
- 繰り返しの `pnpm install` が次の設定の変更に応じる（それまでは「Already up to date」）: `storeDir`・`virtualStoreDir`（`node_modules` を作り直す）、`virtualStoreDirMaxLength`（仮想ストアのディレクトリの名前を変える）、`dangerouslyAllowAllBuilds` をオン（飛ばしたビルドを実行）、`trustLockfile` をオフ（lockfile を確かめる）
- **`node-linker` が `node_modules` の記録と違うと `pnpm add`・`remove`・`update` は失敗する**。ワークスペース全体の `pnpm install` は新しい `node-linker` で作り直し、一部のプロジェクトに絞ったインストールは失敗する（[pnpm/tasks#203](https://github.com/pnpm/tasks/issues/203)）
- 一部のプロジェクトに絞ったインストールは、`nodeLinker`・`hoistPattern`・`publicHoistPattern`・ストア・仮想ストアが違う `node_modules` では失敗する（それまでは作り直して、選ばなかったプロジェクトの依存を失っていた。[pnpm/tasks#217](https://github.com/pnpm/tasks/issues/217)）
- `patchedDependencies` のあるワークスペースで、前回が別のメジャーバージョンの pnpm でも近道を使う。ワークスペースのパッケージの `bin` が変わったら bin をリンクし直し（[#17324](https://github.com/pnpm/pnpm/issues/17324)）、名前を変えたり消したりした `bin` の項目のシムを `node_modules/.bin` から消す（[pnpm/tasks#211](https://github.com/pnpm/tasks/issues/211)）
- `nodeLinker: hoisted` で途中で止まったインストールが、置き換え中のパッケージを次回に信じさせない
- リリースノートの本文は途中で切れている
