## 新機能

### `rust-toolchain.toml` が指定する Rust ツールチェーンをインストール（[#16741](https://github.com/pnpm/pnpm/pull/16741)）

> [!tip] 何ができるようになったか
> `cargo.enabled` のとき、`pnpm install` が rustup のツールチェーンファイル（`rust-toolchain.toml`、または古い形式の `rust-toolchain`）を読み、そこに書かれたツールチェーンをインストールする。Python のインタプリタを用意する仕組みと同じ考え方。
>
> - **探し方**: 各 Cargo のマニフェストから上へたどって最も近いツールチェーンファイル（チェックアウトより上は見ない）。ファイルが正で、`rust@runtime:` の指定や `devEngines.runtime` のエントリは無い
> - **チャンネル**: 正確なバージョン（`1.95.0`）、マイナーの系列（`1.95`）、`stable`・`beta`・`nightly`、日付付きのチャンネル。`profile`（`minimal` か `default`。`rust-docs` は除く）・`components`・`targets` に従う。`path` を指定したファイルや `complete` などの他の profile は rustup に任せる
> - **信頼性**: チャンネルのマニフェストを埋め込みの Rust のリリース署名鍵で検証し、各コンポーネントのアーカイブを署名済みマニフェストの SHA-256 と照合する。ミラーが古い署名済みリリースにすり替えることはできない。`tools.rust.mirror` はグローバル設定からだけ受け付ける

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/Rust-ツールチェーン|Rust ツールチェーン]]

### `cargo`・`rustc` のシムがプロジェクトのツールチェーンで動く（[#16748](https://github.com/pnpm/pnpm/pull/16748)）

> [!tip] 何ができるようになったか
> `pnpm shim add rust` で、プロジェクトごとにツールチェーンを切り替える `cargo`・`cargo-clippy`・`cargo-fmt`・`clippy-driver`・`rustc`・`rustdoc`・`rustfmt` のシムを追加できる（`globalShims` の `rust` キーに記録）。それまでは `pnpm run`・`pnpm exec` などでしか使われなかった。
>
> - **どのツールチェーンか**: 作業ディレクトリから上へたどって最も近い `rust-toolchain.toml`（または `rust-toolchain`）を rustup と同じように読む
> - **初回に自動インストール**: pnpm の状態ディレクトリにある信頼済みの設定（`global-shim-rust`）でインストールし、プロジェクトが取得元のストアを差し替えることはできない
> - **実行のしかた**: ツールチェーンの `bin` を `PATH` の先頭にし、`RUSTUP_TOOLCHAIN` も設定する

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/Rust-ツールチェーン|Rust ツールチェーン]]

### `pnpm add rust`・`pnpm add -g rust` で Rust ツールチェーンを入れる（[#16756](https://github.com/pnpm/pnpm/pull/16756)）

> [!tip] 何ができるようになったか
> `rust` が、`node` が Node.js ランタイムを指すのと同じく Rust ツールチェーンを指すようになった（npm の `rust` パッケージではない）。バージョンは Rust のリリースチャンネルで、`rust` だけなら `stable`。
>
> - **`pnpm add rust@1.95`**: プロジェクトを支配する `rust-toolchain.toml` の `channel` を設定する（無ければプロジェクトに作る）。ファイルの他の部分やコメントは残し、失敗したら元に戻す。`package.json` には何も書かない。`cargo.enabled` ならツールチェーンもインストールして `.pnpm/rust` にリンクする。`-r`/`--filter` では使えない
> - **`pnpm add -g rust@stable`**: シムが使うストアにツールチェーンを入れ、`pnpm shim add rust` と同じシムを書き、チャンネルをグローバルの bin ディレクトリに記録する。プロジェクトの `rust-toolchain.toml` があればそちらが優先される

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/Rust-ツールチェーン|Rust ツールチェーン]]

### 依存パッケージのエージェントスキルをリンクし、`permissions` 設定を追加（[#16744](https://github.com/pnpm/pnpm/pull/16744)）

> [!tip] 何ができるようになったか
> pnpm v12 が [pnpm/rfcs#35](https://github.com/pnpm/rfcs/pull/35)（依存パッケージのエージェントスキル）と、[pnpm/rfcs#36](https://github.com/pnpm/rfcs/pull/36)（パッケージごとの `permissions`）の後方互換な部分を実装した。
>
> - **見つけ方**: インストール時に、各プロジェクトの直接依存（`--prod` などの依存グループの指定に従う）の `skills/<name>/SKILL.md` を探す。ワークスペースに同じレジストリパッケージの複数バージョンがあれば最も新しいものを使う
> - **承認**: 承認されていないパッケージは `.modules.yaml` に保留として記録し、`pnpm approve` を案内する通知を出す。保留のスキルでインストールは失敗しない
> - **リンク先**: 承認したスキルを `pnpm-<pkg>-<skill>` として、ルートにある `.*/skills` ディレクトリと、環境から分かるエージェントのディレクトリ（無ければ作る）にリンクする。`skills.dirs` で上書きでき、`[]` で無効になる
> - **後片付け**: `pnpm-*` の `.gitignore` を書き、自分が作ったリンクだけを置き換え・削除する。他のものがあれば `ERR_PNPM_AGENT_SKILL_PATH_OCCUPIED`、置き場所が無ければ `ERR_PNPM_NO_AGENT_SKILLS_DIR` で失敗する

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/エージェントスキル|エージェントスキル]]

### 再帰実行の出力でスクリプトの色を保ち、制御文字を取り除く（[#16694](https://github.com/pnpm/pnpm/pull/16694)）

> [!tip] 何ができるようになったか
> `pnpm -r run`（`--stream`・`--parallel`、接頭辞付きの `-r exec`、パイプラインのタスクも）がプロジェクト名の下に出す出力の見た目を改善した。
>
> - **色（v12）**: パイプで受ける子プロセスの多くは色を切っていたが、pnpm の出力が色付きのとき `FORCE_COLOR=1` を設定する。既存の `FORCE_COLOR` は残し、`--color=never`・`NO_COLOR`・ndjson・silent では設定しない
> - **表示（v12）**: 長い色付きの行を見た目の幅で切り、`\r` の進捗バーは最後のフレームだけ出す。カーソル移動や OSC のリンクなどの制御文字は捨て、色の残る行の末尾でリセットする
> - **修正（v12）**: bail 時に `[ELIFECYCLE] …` の行が別のプロジェクトのブロックに紛れ込んでいた問題も直した

### `@pnpm/napi` の `rebuild` が `skipIfHasSideEffectsCache` を受け付ける（[#16751](https://github.com/pnpm/pnpm/pull/16751)）

> [!tip] 何ができるようになったか
> pnpm v11 の `rebuild` にあった `skipIfHasSideEffectsCache` を `@pnpm/napi` にも追加した（teambit/bit が使っている）。副作用キャッシュにビルド結果があるパッケージはスクリプトを再実行せず、キャッシュのビルド結果をスロットに戻す。

### pnpr: npm の team API で管理者がチームを管理（[#16725](https://github.com/pnpm/pnpm/pull/16725)）

> [!tip] 何ができるようになったか
> pnpr の実行時管理の計画（pnpm/tasks#111）の第 1 段階。管理者ロール（`auth.admins`）と、レジストリごとの `teamsManagedBy: config | api` を追加した（既定の `config` は従来どおり）。
>
> - **使い方**: `api` のレジストリでは、管理者が `pnpm team create/destroy/add/rm` を使える
> - **仕組み**: チームの名簿をホスト型ストア（`.team-rosters/v0/<registry>.json`）に compare-and-set で保存し、各レプリカが変更後 10 秒以内に読み直す。`team:` のアクセストークンは常に最新の名簿を見る
> - **Web UI 向け**: レジストリ一覧（`GET /-/pnpr/v0/registries`）が `admin` と `teamsManagedBy` を返し、CORS で `PUT`・`POST`・`DELETE` を許可する

### pnpr: 管理者用のアカウント管理 API（[#16729](https://github.com/pnpm/pnpm/pull/16729)）

> [!tip] 何ができるようになったか
> 第 2 段階。`auth.admins` の管理者が `/-/pnpr/v0/admin/users` でアカウントを一覧・作成・パスワード変更・削除（全トークンを失効）でき、アカウントのトークンの一覧と個別の失効もできる。
>
> - **対応バックエンド**: htpasswd・libsql・PostgreSQL・MySQL
> - **嬉しい場面**: 管理者が作るアカウントは `max_users` を無視するので、セルフ登録を無効にしたまま人を追加できる

### pnpr: 管理者用のパッケージルール API（[#16732](https://github.com/pnpm/pnpm/pull/16732)）

> [!tip] 何ができるようになったか
> 第 3 段階。`rulesManagedBy: api` のホスト型レジストリでは、設定をデプロイし直さずに管理者がルールを変えられる。
>
> - **使い方**: `GET`/`PUT`/`DELETE` `/-/pnpr/v0/admin/rules/{ecosystem}/{name}`。`PUT` は保存済みの変更を本文で置き換え、`DELETE` は変更を捨てて設定のルールに戻す
> - **範囲**: 変えられるのは既定の `access` と、宣言済みパターンごとの `access`/`publish`/`unpublish`。パターン自体はルーティングに使うので設定に残る（誰が何をできるかは変えられるが、どのレジストリが配るかは変わらない）

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: OIDC のグループからレジストリのチームに参加させる（[#16735](https://github.com/pnpm/pnpm/pull/16735)）

> [!tip] 何ができるようになったか
> 第 4 段階。`auth.oidc[].login.groups.teams` で、ID トークンの claim（既定 `groups`）のグループをレジストリのチームに対応付ける。
>
> - **挙動**: ブラウザのセッションの間（最長 1 時間）だけチームのメンバーになり、名簿には書かない。ID プロバイダでグループから外すと次のサインインで反映される
> - **範囲**: グループ由来のメンバーシップは、同じユーザー名のパスワードログインや `npm token` には及ばない

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: ルール変更を `If-Match` で条件付きに（[#16739](https://github.com/pnpm/pnpm/pull/16739)）

> [!tip] 何ができるようになったか
> パッケージルールの管理 API に楽観的並行制御を加えた。リセットが別の管理者の変更を消してしまうというレビュー指摘への対応。
>
> - **使い方**: `GET` が保存済みの変更のバージョンを本文の `version` と `ETag` で返す。`PUT`・`DELETE` に `If-Match` を付けると、その後に変更されていれば **412**（`precondition_failed`）で何も変えない
> - **互換性**: `If-Match` なしなら従来どおり最後の変更が勝つ

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: `npm access grant`/`revoke` をルールに対応付け（[#16740](https://github.com/pnpm/pnpm/pull/16740)）

> [!tip] 何ができるようになったか
> `rulesManagedBy: api` のレジストリで、`npm access grant`・`npm access revoke`・`npm access list packages <scope:team>` が使える。
>
> - **挙動**: grant は `access` に `team:<team>` を足し、`read-write` なら `publish` にも足す。revoke は `access`・`publish`・`unpublish` から外す。変更には管理者と、名簿にあるチームが必要
> - **制限**: `packages:` に名前で宣言したパッケージだけが対象。`@acme/*` のようなパターンだけが該当するパッケージは 400 になる。`api` 管理でないレジストリは 403（`rules_config_managed`）

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: SCIM でアカウントを無効化（[#16742](https://github.com/pnpm/pnpm/pull/16742)）

> [!tip] 何ができるようになったか
> pnpm/tasks#111 の最後の項目として、SCIM 2.0 のデプロビジョニングに対応した。
>
> - **使い方**: `auth.scim.token`（32 文字以上、`${VAR}` 置換可）を設定すると `/-/pnpr/v0/scim/v2` が有効になる。`Users` の一覧（`filter=userName eq "..."`）・`POST`・`GET`・`PUT`・`PATCH`・`DELETE` などに対応
> - **無効化したとき**: 保存済みのトークンを失効させ、パスワードのアカウントを消し、OIDC のブラウザセッションを破棄する。他のレプリカのセッションも TTL 内に使えなくなる。`DELETE` したユーザー名は再び `POST` されるまで拒否される

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: Web UI を `/-/ui/` で配信（[#16769](https://github.com/pnpm/pnpm/pull/16769)）

> [!tip] 何ができるようになったか
> pnpr が自分のオリジンの `/-/ui/` で Web UI を配るようになり、UI 側で CORS やサーバーの URL の設定が要らなくなった。UI は別の npm パッケージ `@pnpm/pnpr-ui`（`@pnpm/pnpr` の任意の peer 依存）。
>
> - **使い方**: `pnpm add -g @pnpm/pnpr,@pnpm/pnpr-ui`
> - **設定**: `ui.enabled`（既定 `true`）と `ui.dir`。`dir` が無ければ pnpr のパッケージの隣の `@pnpm/pnpr-ui` を探す
> - **配信**: `index.html` に相対の `<base>` を足すので、深いルートでの再読み込みやパスの接頭辞の後ろに置いた pnpr でも動く。CSP でスクリプトとリクエストを pnpr のオリジンに限る

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### TLS の不完全な切断で終わるメタデータの本文を受け付ける（[#16708](https://github.com/pnpm/pnpm/pull/16708)）

> [!quote] Before
> TLS を傍受するプロキシの後ろで、v12 の `pnpm view`（と `pnpm update` の解決）が `ERR_PNPM_RESOLVING_NPM_RESOLVER_BODY_READ_ERROR ... peer closed connection without sending TLS close_notify` で失敗した。プロキシが `Content-Length` もチャンク形式も無い本文を、`close_notify` なしの切断で終えていた。

> [!success] After
> `Content-Length` も chunked も無い応答に限り、切断前に受け取ったバイトを本文として使う（Node.js と同じ）。長さが決まった本文が途中で切れた場合は従来どおり失敗する。
