### `pnx --package=rust@<channel>` で特定の Rust リリースのツールを実行（[#16784](https://github.com/pnpm/pnpm/pull/16784)）

> [!tip] 何ができるようになったか
> `cargo.enabled` のとき pnpm 12.11 は `pnpm run` でリンクした Rust ツールチェーンを `PATH` に置くため、`cargo +nightly-2026-08-27 build` のような rustup の `+toolchain` が本物の cargo に届いて失敗していた。`cargo` の名前を奪わずに、1 回のコマンドだけ別のリリースを選べるようになった。
>
> - **使い方**: `pnx --package=rust@nightly-2026-08-27 cargo build --target wasm32-wasip1-threads`
> - **仕組み**: `pnx node@22` と同じくリリースをストアに入れ、その `bin` を `PATH` の先頭にして実行する。`RUSTUP_TOOLCHAIN` も設定する。作業ディレクトリを支配するツールチェーンファイルの profile・components・targets と、`--target` 引数のターゲットを入れる
> - **注意**: `rust` だけなら `stable`。チャンネルでないもの、ツールチェーンのツールでないコマンドは通常のレジストリの経路のまま

📦 v12.11.2 · トピック: [[repos/pnpm-pnpm/topics/Rust-ツールチェーン|Rust ツールチェーン]]

### `https://registry.npmjs.com/` を npm レジストリの別名として扱う（[#16780](https://github.com/pnpm/pnpm/pull/16780)）

> [!tip] 何ができるようになったか
> `.com` を使うスコープのルートでは OIDC トークンの audience が `npm:registry.npmjs.com` になり、npm に 401 で拒否されていた。共通の URL 正規化が、リクエストとトークン交換の前に正規の `https://registry.npmjs.org/` を選ぶ。
>
> - **認証情報・TLS のキー**: どちらのホスト名の設定も正規のレジストリに届く。明示的な `.com` のキーは元のスコープのまま。URL スコープの環境変数の認証情報では明示的な `.org` のキーが優先
> - **変わらないもの**: HTTP のエンドポイント、カスタムポート、サブパス、クエリ、紛らわしいホスト。生のダウンロード URL の認証は実際の宛先に限る

### pnpr: Web UI から OIDC でサインイン（[#16774](https://github.com/pnpm/pnpm/pull/16774)）

> [!tip] 何ができるようになったか
> pnpr の Web UI のサインイン（pnpm/tasks#113）のサーバー側。UI（`@pnpm/pnpr.apps.pnpr-web` 0.2.5）にパスワードのフォームと OIDC プロバイダーごとのボタン、サインアウトが入り、トークンはタブの `sessionStorage` に置く。
>
> - **`GET /-/pnpr/v0/sign-in`**: ブラウザでのサインインに使える OIDC プロバイダーの一覧
> - **`/-/oidc/{provider}/login?return=ui`**: コールバックが 1 回限り・1 分で失効するコードを HttpOnly の Cookie に入れて UI に戻す。トークンもコードも URL に出ない。Web UI を配信していなければ 400
> - **`POST /-/oidc/handoff`**: Cookie のコードを `{"token", "expires"}` に 1 回だけ引き換える
> - パスワードのサインインは npm のログインのエンドポイント（`PUT /-/user/org.couchdb.user:<name>`）を使う

### `addMissingPeerTypes` 設定を追加（[#16810](https://github.com/pnpm/pnpm/pull/16810)）

> [!tip] 何ができるようになったか
> 有効にすると、依存の peer `X` ごとに `@types/X` も任意の peer にする（パッケージが既に宣言していなければ。Yarn の `normalizePackage` と同じ規則）。`enableGlobalVirtualStore` では `next` などがプロジェクトの外にあり、TypeScript が peer の型を見つけられなかった問題への対応（[#15689](https://github.com/pnpm/pnpm/discussions/15689)）。
>
> - **使い方**: `pnpm-workspace.yaml` に `addMissingPeerTypes: true`
> - **既定は無効**: スナップショットのキーが変わるため、マシンごとに違いうる仮想ストアの種類とは結び付けない
> - **lockfile**: 有効なときだけ `settings.addMissingPeerTypes` として記録。切り替えると解決し直し、frozen install は記録と違う lockfile を拒否する。pnpr にも送る

### pnpr や Turborepo のリモートキャッシュでビルド結果を共有（[#16812](https://github.com/pnpm/pnpm/pull/16812)）

> [!tip] 何ができるようになったか
> 1 つの `remoteCache` 設定で、依存のビルドの副作用と `pnpm pipeline` のタスク結果をマシン間で共有できる。転送先は pnpr サーバーか、Turborepo Remote Cache API を話すサーバー（Vercel Remote Cache やセルフホスト）。
>
> - **形式**: タスク結果は共通のアーティファクトプロトコルの `workspace-task` アーティファクト。P-256 で署名したエンベロープで、依存のビルドと同じ `trustedKeys` で検証する（秘密鍵を持つマシンだけが他が使う結果を公開できる）
> - **Turborepo API**: pnpr のルートを写す形で保存する。条件付き作成ができないので、後の公開が前のものを置き換える
> - **嬉しい場面**: CI と開発機で同じタスクやネイティブ依存のビルドを繰り返したくないとき

### config 依存をプロジェクトの依存と同じ規則で保存・更新（[#16816](https://github.com/pnpm/pnpm/pull/16816)）

> [!tip] 何ができるようになったか
> `pnpm add --config` と `pnpm update` が config 依存を通常の依存と同じように扱う（[#16814](https://github.com/pnpm/pnpm/issues/16814)）。
>
> - **`pnpm add --config <pkg>@latest`**: 名指ししたパッケージを解決し直す（以前は lockfile に古いバージョンがあるとそれを保った）。`savePrefix`/`saveExact` に従い `^1.2.0` のような範囲を保存する
> - **`pnpm update`**: セレクタなしなら全部、名前・パターンがあれば一致するものを範囲内で更新。`--latest` で範囲を超える。dist-tag を追う宣言はタグを保ち lockfile だけ動く
> - **対象外**: `--interactive`・`--patches`・`--no-save`・`--filter`・依存グループのフラグ・バージョン付きのセレクタ

⏳ 未リリース（v12.12.0 のリリースノートに記載）· トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### `tool:` プロトコルを受け付ける（[#16838](https://github.com/pnpm/pnpm/pull/16838)）

> [!tip] 何ができるようになったか
> [`tool:` プロトコルの RFC](https://github.com/pnpm/rfcs/pull/37) の最初の後方互換な段階。pnpm v12 は `runtime:` を受け付ける場所すべてで `tool:` を受け付け、`runtime:` は別名として残る。
>
> - **使い方**: `pnpm add bun@tool:1.3.0`、`pnx node@tool:22`、`pnx yarn@tool:4`、`pnpm add -g yarn@tool:4`（Node.js・Bun・Deno・Yarn）
> - **lockfile**: `tool:<spec>` と `runtime:<spec>` は双方向に同じとみなされ、frozen install はどちらの書き方でも受け付ける。pnpm が書く指定子は `runtime:` のままなので、以前の pnpm でも `--frozen-lockfile` が通る
> - **今後**: lockfile のキーを `tool:` にする変更などは RFC の後の段階。v12.12.1 のリリースノートによると、名前付きレジストリを `tool` と呼ぶことはできなくなった

⏳ 未リリース（v12.12.1 のリリースノートに記載）· トピック: [[repos/pnpm-pnpm/topics/ランタイム管理|ランタイム管理]]

### `pnpm dist-tag` が OIDC 認証に対応（[#16840](https://github.com/pnpm/pnpm/pull/16840)）

> [!tip] 何ができるようになったか
> 信頼された CI のジョブが、npm トークンを保存せずに `latest`・`next` などのタグを管理できる（npm/cli#10038 と同じ機能）。
>
> - **対象**: v12 の `pnpm dist-tag add`・`rm`・`ls`。publish のログインの処理を使い、CI ジョブの ID をそのパッケージ用の一時トークンに交換する。トークンはメモリにだけ置き、`.npmrc` に保存しない
> - **フォールバック**: OIDC が使えない・拒否されたら設定済みの認証情報を使う
> - **v11・v12 共通**: 注入された `NPM_ID_TOKEN` は `aud` クレームが選んだレジストリと一致するときだけ使う。違えば `ERR_PNPM_ID_TOKEN_REGISTRY_AUDIENCE_MISMATCH` を警告して設定済みの認証情報に戻る
> - v12.12.1 のリリースノートによると、パッケージの trusted publishing の設定で「Allow npm dist-tag」を有効にする

⏳ 未リリース（v12.12.1 のリリースノートに記載）· トピック: [[repos/pnpm-pnpm/topics/パック・公開|パック・公開]]

### git 依存をビルドするツールを lockfile に記録（`lockBuildTools`、のちに取り消し）（[#16845](https://github.com/pnpm/pnpm/pull/16845)）

> [!tip] 何ができるようになったか
> [RFC 21（locked build environments）](https://github.com/pnpm/rfcs/pull/21) の第 1 段階として、実験的な `lockBuildTools: true` を追加した。有効なら、git 依存を準備するパッケージマネージャーと Node.js を lockfile に記録し、以降のインストールは記録した integrity で検証したそのツールで準備する。
>
> - **lockfile**: 新しい `tool:` のキー接頭辞と、スナップショットの `buildDependencies` フィールド。`settings.lockBuildTools` も記録し、切り替えると frozen install は `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`

> [!warning] 取り消し
> 同じ期間に [#16859](https://github.com/pnpm/pnpm/pull/16859)（revert）でこの変更は取り消された。

> [!success] After
> 先に拒否を確かめ、拒否されていないパッケージにだけフラグを適用する。

> [!warning] 移行が必要
> pnpm v11 の挙動（フラグがすべてを許可する）からの変更で、v11 は変わらない。フラグと拒否を併用していて拒否したパッケージもビルドしたいなら、`allowBuilds` の `false` を外す。

### `pnpm deploy --legacy` で `workspace:` の peer をワークスペースから入れる（[#16808](https://github.com/pnpm/pnpm/pull/16808)）

### 読めない設定があっても固定した pnpm に切り替える（[#16826](https://github.com/pnpm/pnpm/pull/16826)）

> [!quote] Before
> どちらの CLI も、プロジェクトが固定した pnpm に切り替えるか決める前に設定をすべて読み込んでいた。グローバルの `config.yaml`・`.npmrc`・`_auth`・（v11 では）`pnpm-workspace.yaml` に実行中の pnpm が拒否する設定があると、`pnpm --version` を含むすべてのコマンドが止まり、その設定を理解する新しい pnpm が動けなかった。

> [!success] After
> 読み込みに失敗したら、読めないものだけを除いて読み直す（v11・v12）。v12 の `Config::skip_unreadable_settings` はすべての読み込み元を対象にし、グローバルの `config.yaml` と `pnpm-workspace.yaml` は単体で解析できる設定を残す。読める読み込み元はすべて適用されるので、マシンの `pmOnFail`・レジストリ・認証情報・プロキシは失われない。`_auth` は後の pnpm が加えるフィールドを許容し、リモートキャッシュのトークンは認証の設定に置く（PR タイトルより）。

⏳ 未リリース（v12.12.0 のリリースノートに記載）· トピック: [[repos/pnpm-pnpm/topics/ランタイム管理|ランタイム管理]]、[[repos/pnpm-pnpm/topics/設定|設定]]

### `pnpm deploy` がリンクしたワークスペースパッケージの peer を親の提供するバージョンに結び付ける（[#16809](https://github.com/pnpm/pnpm/pull/16809)）

> [!quote] Before
> `injectWorkspacePackages` なしの `pnpm deploy` は、リンクしたワークスペースパッケージの peer をデプロイするグラフの解決に結び付け、グラフに複数のバージョンがあると `ERR_PNPM_DEPLOY_AMBIGUOUS_PEER` で失敗した（pnpm 12.11.2・11.28.5 とも、[#16807](https://github.com/pnpm/pnpm/issues/16807)）。

> [!success] After
> injected なインストールと同じく、グラフを上へたどって最も近い、その peer に依存する祖先（デプロイするプロジェクトを含む）から結び付ける。提供元が 1 つなら確定し、複数あるときだけ従来のエラー。v11・v12 とも修正。

⏳ 未リリース（v12.12.0 のリリースノートに記載）· トピック: [[repos/pnpm-pnpm/topics/パック・公開|パック・公開]]
