## 新機能

### `pnpm pack` が `publishConfig.variants` のアーカイブを作る（[#17657](https://github.com/pnpm/pnpm/pull/17657), [#17678](https://github.com/pnpm/pnpm/pull/17678)）

> [!tip] 何ができるようになったか
> platform variants の RFC の pnpm 側（パック）。`package.json` の `publishConfig.variants` に、アーカイブ 1 つにつき 1 項目（`targets`・`files`・必要なら `manifest` の上書き）を書くと、`pnpm pack` がその数だけアーカイブを作る。
>
> - **名前**: プラットフォームのバリアントは `<name>-<version>~<tag>.tgz`。tag は targets をバイト順に並べて `+` でつないだもの（例: `linux-x64+linux-x64-musl`）。`targets: ["any"]` の項目はほかのすべてのホスト向けのアーカイブで、無ければ `any` のアーカイブの無いバージョンになる
> - **事前の確認**: 各 target は `any` か正規のプラットフォームの tag。近い綴りがあればエラーで示す（`linux-x64-gnu` → `linux-x64`、`linux-x64-napi8-musl` → `linux-x64-musl-napi8`）。同じ target の重複は不可、`any` は単独で書く
> - **使い方**: `pnpm pack --variant <target>` でその target を含む項目のアーカイブだけを作る
> - **`pnpm pack --json`**（#17678）: 書いたアーカイブごとに `integrity`（SHA-512、SRI 形式）と `size`（バイト）を出す。バリアントは `tag` も付く。dry run では出さない。複数のマシンからの公開で、アーカイブを再びハッシュせずに integrity で参照できる

### `pnpm publish` がプラットフォームのバリアント付きで 1 つのバージョンを公開（[#17658](https://github.com/pnpm/pnpm/pull/17658)）

> [!tip] 何ができるようになったか
> `publishConfig.variants` を持つパッケージは、`serverType: pnpr` と宣言したレジストリへ、すべてのアーカイブを 1 つのバージョンとして公開する。
>
> - **流れ**: すべてのアーカイブを integrity で先にステージし（`HEAD`、無ければ `PUT`）、その後で通常の `PUT <registry>/<name>` の文書を送る。文書は `any` のアーカイブを `<name>-<version>.tgz`、各バリアントを `<name>-<version>~<tag>.tgz` として `integrity`・`length` で参照する
> - **ほかのレジストリ**: バリアントの公開は dry run でも拒否する（バリアント無しで公開したバージョンには後から足せないため）。`pnpm publish --no-variants` なら `any` のアーカイブだけを公開する
> - `--dry-run` はすべての確認を行い、何も送らない
> - `pnpm pack`・`pnpm publish` は、宣言についての RFC の警告をマニフェストから出す

### 複数のマシンからバリアントを上げ、integrity で公開する（[#17659](https://github.com/pnpm/pnpm/pull/17659)）

> [!tip] 何ができるようになったか
> CI のマトリクスのジョブごとにアーカイブを作り、リリースのジョブでまとめて公開できる。
>
> - **`pnpm publish --upload-variant <target>`**: そのマシンで target の項目のアーカイブを作り、`PUT /-/pnpr/v0/artifacts/blob?integrity=…` で上げる（`HEAD` で確かめず、再実行で上げ直す）。stdout には `<target>=<integrity>` だけを出す（`--json` なら名前・バージョン・各アーカイブの tag・targets・integrity）。何も公開せず、`--provenance` は拒否する。繰り返し指定でき、`any` は `any` のアーカイブ
> - **`pnpm publish --variant-integrity <target>=<integrity>`**: リリースのジョブで項目ごとに 1 回指定する。`--recursive` では `<name>~<target>=<integrity>`。アーカイブは作らず、マニフェストは宣言から作る
> - **嬉しい場面**: ネイティブのバイナリをプラットフォームごとのランナーでビルドしてから 1 つのバージョンとして公開したいとき

### provenance を全アーカイブの 1 つの文で署名し、再実行の公開をリリースレコードで確かめる（[#17660](https://github.com/pnpm/pnpm/pull/17660), [#17683](https://github.com/pnpm/pnpm/pull/17683)）

> [!tip] 何ができるようになったか
> - **provenance**（#17660）: `--provenance` でバリアント付きのバージョンを公開すると、文の subject を公開するすべてのアーカイブ（各 `.tgz` の SHA-512 付き）にする。`any` のアーカイブはバージョンの PURL、バリアントは `variant` の修飾子（`+` は `%2B`）付きの PURL。ほかのジョブが上げたアーカイブは `--variant-integrity` の integrity で名指しする
> - **再実行の確認**（#17683）: provenance を署名し直す再実行は pnpr から `409`（公開済み）を受ける。pnpm は、バージョンのリリースレコード（`<name>/<version>+r0`）のバリアントの tag の集合と各 `.tgz`、署名するなら `/-/npm/v1/attestations/<name>@<version>` の文の subject、公開で付ける dist-tag がこの実行の内容と一致するときだけ公開済みとして成功にする。違えば `ERR_PNPM_PUBLISHED_RELEASE_DIFFERS`（違うアーカイブ・無い文・dist-tag を示す）。`serverType: pnpr` のレジストリでステージしない公開が `409` を受けたときだけ確かめる

### `pnpm -r publish --batch` がバリアント付きのパッケージも公開（[#17680](https://github.com/pnpm/pnpm/pull/17680)）

> [!tip] 何ができるようになったか
> これまで拒否していた `publishConfig.variants` を持つパッケージを、`serverType: pnpr` のレジストリへ一括公開できる。コミットの前に各パッケージのアーカイブ（バリアントを含む）をステージし、integrity で参照する。
>
> - `--upload-variant` でほかのジョブが上げたアーカイブは、何かを上げる前に `HEAD` で確かめる。すべてのレジストリのグループの確認が済んでから公開するので、アーカイブが欠けていれば何も公開しない

### pnpr: バリアントを tag で名付けたアーカイブから見つける（[#17648](https://github.com/pnpm/pnpm/pull/17648)）

> [!tip] 何ができるようになったか
> バリアントを tag そのもの（`+` を含む）で名付け、添付の `<basename>-<version>~<tag>.tgz` だけから見つける。
>
> - 要求の `versions[<version>].pnprVariants` は不要に。バリアントの添付は `data` の隣に（ステージ済みなら単独で）`.tgz` の `integrity` を書く。integrity の無い `~<tag>` の添付や、要求に無いバージョンを名指す添付は拒否

> - 自由形式の label は廃止。label 付きで保存したバリアントは移行しない（pnpr は 1.0 前）

### pnpr: provenance がバージョンのすべてのアーカイブを名指ししているか確かめる（[#17651](https://github.com/pnpm/pnpm/pull/17651)）

> [!tip] 何ができるようになったか
> バージョンの `.sigstore` バンドルの DSSE の封筒から in-toto の文（v1 か v0.1）を読み、主の `.tgz`（バージョンの PURL）と各バリアントの `.tgz`（`variant` 修飾子付きの PURL）の subject が SHA-512 付きで揃っていなければ `400` で拒否する。

> - **嬉しい場面**: provenance の外でアーカイブがバージョンに入り込まないようにする

### pnpr: `any` のアーカイブの無い、バリアントだけのバージョンを受け付ける（[#17654](https://github.com/pnpm/pnpm/pull/17654)）

> [!tip] 何ができるようになったか
> `any` を対象にする項目の無い公開（`dist` も通常の添付も無く、`~<tag>` の添付だけ）を受け付ける。
>
> - 送られたマニフェストと各バリアントは URL のパッケージとバージョンのキーに一致する必要がある。リビジョン用の `+r<N>` のキーは拒否。バリアントの名前・バージョン・peer をマニフェストと照合する
> - npm の文書が `dist.tarball` で指す最小のアーカイブを pnpr が生成する。`package.json` は名前・バージョンと、バリアントの `os`・`cpu`・Linux の `libc` の和集合（`libc` の無い Linux は glibc 扱い、`wasm32` のバリアントがあれば 3 つとも省く）。tar のヘッダー固定・gzip の mtime 0 で決定的に作る

### pnpr: documents のメタデータのバックエンドを削除（[#17641](https://github.com/pnpm/pnpm/pull/17641)）

> [!tip] 何ができるようになったか
> メタデータは SQL だけになった（既定はストレージのディレクトリの SQLite、または `metadata.url` の `sqlite:`・libSQL）。documents だけが使っていた公開のジャーナルなども削除。

> [!warning] 移行が必要
> `metadata.backend` を（値に関わらず）書いた設定は拒否され、エラーは `metadata.url` を案内する。パッケージをホストする `s3:` のストアで `metadata.url` が無い場合、これまではバケットの documents に戻っていたが、拒否されるようになった（libSQL の URL を案内）。パッケージをホストしない tier（アーティファクトだけのものなど）はメタデータの URL が不要なまま。

### pnpr: ホスト型のアーカイブを内容アドレスで保存し、柵付きのオンライン GC（[#17717](https://github.com/pnpm/pnpm/pull/17717)）

> [!tip] 何ができるようになったか
> libSQL でコミットを拒否された公開のアーカイブ（#17674）が残り、レプリカが公開し続ける間は回収できなかった。アーカイブを公開時のファイル名で保存していたため、削除が同じキーを使う後の公開と競合しえた。
>
> - **保存のモデル**（SQL のスキーマ `0.2`）: アーカイブを `<integrity>.<n>`（バイト列の識別と世代番号）で保存。同じバイト列は組織とエコシステムごとに 1 回だけ（バージョン・パッケージ・イメージのリポジトリをまたいで）。`blobs` が integrity ごとの現在の世代と状態（`live`・`reclaiming`・`gone`）を、`artifact_blobs` が公開したファイルと integrity の対応を持つ
> - **公開**: `live` の世代は再利用してアップロードしない。無い・回収済みの integrity は次の世代として上げる
> - tarball・バリアント・attestation・PyPI・Cargo・OCI の URL は変わらない

### `supportedArchitectures` が求めるバリアントをストアに取得・リンク（[#17684](https://github.com/pnpm/pnpm/pull/17684), [#17707](https://github.com/pnpm/pnpm/pull/17707), [#17735](https://github.com/pnpm/pnpm/pull/17735)）

> [!tip] 何ができるようになったか
> platform variants の RFC の `supportedArchitectures` の規則の実装。
>
> - **取得**（#17684、📦 v12.18.0）: `supportedArchitectures` があると、一覧のプラットフォームに合う各バリアントと、リンクできるバリアントが無いプラットフォーム向けの `any` のアーカイブも、リンクせずにストアに取得する。`current` はホスト、`os`/`cpu`/`libc` の形は値のすべての組み合わせ。設定が無ければ従来どおりリンクするアーカイブだけ
> - **リンク**（#17707、⏳ 未リリース）: `supportedArchitectures` が `current` 以外のプラットフォームをちょうど 1 つ挙げると、そのプラットフォームのバリアントと、そのバリアントが宣言する依存をリンクする。別のマシン向けの `node_modules` を用意するため。挙げたプラットフォームが書いていない floor・ABI はリンクでは満たさない扱い（`linux-x64` は glibc 2.28 を要るバリアントではなく本来のアーカイブ、`linux-x64-manylinux_2_28` ならそのバリアント）
> - **ほかのプラットフォームの依存もストアへ**（#17735、⏳ 未リリース）: すべてのインストールと `pnpm fetch` が、一覧のプラットフォームが保つアーカイブとその依存のパッケージをストアに入れる（リンクはしない）。仮想ストアを作った後の 1 回のパスで行うので、`supportedArchitectures` に足したプラットフォームは次のインストールで拾われる

### プロジェクトごとの lockfile のワークスペースでも、繰り返しのインストールを記録から判定（[#17671](https://github.com/pnpm/pnpm/pull/17671)）

> [!tip] 何ができるようになったか
> `sharedWorkspaceLockfile: false` の最新のワークスペースで、`pnpm install` が各プロジェクトのインストールを走らせず、ファイルが変わっていないプロジェクトの `package.json` も読まずに終わる。
>
> - プロジェクトを読まずに列挙し（`--workspace-packages` に従う）、各プロジェクトの状態の記録からマニフェストを作り直して、ループの実行と同じ確認をする
> - 1 つでも判定できないプロジェクトがあれば、従来どおりループでインストールする

### `pnpm peers check` が宣言されていない必須の peer の提供元を知らせる（[#17677](https://github.com/pnpm/pnpm/pull/17677)）

> [!tip] 何ができるようになったか
> `autoInstallPeers: false` と `dedupePeerDependents: true` のとき、プロジェクトやその依存の祖先が宣言していない提供元から解決された必須の peer について、`pnpm peers check` が助言を出す（pnpm/pnpm#17673）。
>
> - 有効なワークスペースのルートの提供元（別名・リンクを含む）は宣言とみなす。optional・非互換の peer には出さない
> - JSON の出力では `undeclared` の配列に入る。終了コード・インストール時の診断・`strictPeerDependencies`・解決したグラフは変わらない

📦 v12.18.0 に収録 · トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]、[[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### optional の peer をプロジェクト自身のグラフだけから解決（`projectScopedOptionalPeers`）（[#17726](https://github.com/pnpm/pnpm/pull/17726)）

> [!tip] 何ができるようになったか
> `autoInstallPeers: true` で、欠けた optional の peer が、別のワークスペースのプロジェクトだけが依存するバージョンから解決されることがあった（`app` の本番のグラフに `tooling` の `webpack-cli` の依存が入り込む例）。
>
> - **修正（v11・v12）**: `dedupePeerDependents: false` なら optional の peer はプロジェクト自身の依存のグラフ（と `resolvePeersFromWorkspaceRoot` のときのワークスペースのルート）からだけ来る
> - **新しい設定（v12 のみ）**: `projectScopedOptionalPeers: true` で、`dedupePeerDependents` をオンのまま同じ規則にする。必須の peer は引き続きプロジェクトをまたいで再利用する。有効なときは lockfile の `settings` に記録する。次のメジャーで既定にしてから設定を削除する予定

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]、[[repos/pnpm-pnpm/topics/設定|設定]]

### `pnpm fund` を追加（[#17755](https://github.com/pnpm/pnpm/pull/17755)）

> [!tip] 何ができるようになったか
> v12 の CLI に `npm fund` と同じように動く `pnpm fund` を追加（pnpm/pnpm#7354、閉じられた #15850 を引き継いだもの）。
>
> - **使い方**: `pnpm fund` は最初の funding の URL ごとにパッケージをまとめた npm と同じツリー、`--json` は `npm fund --json` の形式
> - `pnpm fund <pkg>` は、インストールした最新のバージョンの `<pkg>`（または `.` のようなパスのプロジェクト）の funding の URL を開く。複数あれば番号付きで並べ、`--which <n>` で選ぶ。無ければ `ERR_PNPM_NO_FUNDING`
> - `-r`・`--filter` で選んだ各プロジェクトについて報告（`sharedWorkspaceLockfile: false` も可）。再帰の `--json` はプロジェクトごとの報告の配列

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]
