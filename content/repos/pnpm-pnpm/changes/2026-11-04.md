### pnpr: ホスト型パッケージのメタデータを SQL データベースに保存（SQLite が既定、libSQL にも対応）（[#17551](https://github.com/pnpm/pnpm/pull/17551), [#17578](https://github.com/pnpm/pnpm/pull/17578), [#17583](https://github.com/pnpm/pnpm/pull/17583)）

> [!tip] 何ができるようになったか
> SQL metadata storage の RFC の実装。パッケージのメタデータ（バージョン・承認したマニフェスト・タグとその履歴・README など）を、アーカイブのストレージから分けて SQL のテーブルに行として保存する。バージョンのマニフェストと README は追記のみで、変えようとすると `409 version_already_published`。
>
> - **設定**: `metadata` ブロックでデータベースを URL で指定する（`url: sqlite:<path>`、相対パスは設定ファイルのディレクトリ基準）。最初に入った `backend`・`path` のキーは #17578 で廃止された（pnpr は 1.0 前）
> - **既定**: ファイルシステムのホスト型ストアは SQLite（`<storage>/.metadata/metadata.sqlite`）が既定に。従来の documents の方式は、メタデータの URL の無い `s3:` のストアなどで `backend: documents` を明示したときだけ使う
> - **libSQL**: `url: libsql://…`（自前の sqld なら `http(s)://`）と `authToken`・`replicaPath`・`syncInterval` で、複数の pnpr のインスタンスが Turso などの 1 つのメタデータのデータベースを共有できる。読み取りは埋め込みのレプリカから行い、更新の前の読み取りや認可は primary に向ける
> - **拒否する設定**: `s3:` と `sqlite:` の組み合わせ、未知のスキーム、空のパスは設定の読み込み時にエラー
> - バックアップのガイドに SQLite のデータベースの扱い（SQLite のバックアップ API での複製・復元）が加わった

### pnpr: SQLite での公開を原子的・冪等にコミット（[#17553](https://github.com/pnpm/pnpm/pull/17553)）

> [!tip] 何ができるようになったか
> atomic workspace publication の RFC の一部。SQL のメタデータを使うとき、1 つの要求で公開するすべての文書を 1 つの `BEGIN IMMEDIATE` のトランザクションでコミットする。
>
> - **途中までの公開が起きない**: 別の書き手が違う中身で押さえているスロットがあれば、メタデータをコミットする前に要求全体が `409` で失敗する。組織をまたぐ要求は拒否
> - **読み手**: 1 回の一括公開の全体か、何も見えないかのどちらか
> - **冪等**: 結果を同じトランザクションで `publication_outcomes` に記録し、再送には同じ結果を返す
> - Cargo・PyPI・OCI の公開と、承認待ちの公開の承認も同じコミットの経路を通る

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: 公開したマニフェストをアーカイブの `package.json` と照合（[#17552](https://github.com/pnpm/pnpm/pull/17552)）

> [!tip] 何ができるようになったか
> Publish-time manifest verification の RFC（pnpm/rfcs#47・#60）の実装。ホスト型の公開で、送られた各バージョンのメタデータをアーカイブの中の `package.json` と比べ、食い違えば拒否する。配るのはアーカイブに書かれた内容。
>
> - **比べる項目**（`npm-install-manifest/1`）: `name`・`version`・依存のマップ・`peerDependenciesMeta`・`bundleDependencies`・`os`/`cpu`/`libc`・`engines`・`bin`（`directories.bin` を展開）・暗黙の `node-gyp rebuild` を含むライフサイクルスクリプト・`hasInstallScript`・`hasShrinkwrap`
> - **アーカイブの読み取り**: 危険なパスのエントリ、マニフェストに展開される 2 つのエントリ（大文字小文字だけ違うものを含む）、リンクのマニフェストなどを拒否する
> - 共通の JSON のフィクスチャで挙動を定義しており、pnpm v12 のインストール時の確認でもコードとフィクスチャを使い回せる

### リリースレコードの信頼の基礎: C2SP の透明性ログと DSSE の文（[#17554](https://github.com/pnpm/pnpm/pull/17554), [#17555](https://github.com/pnpm/pnpm/pull/17555)）

> [!tip] 何ができるようになったか
> release records の RFC の基礎になる 2 つのクレートを追加した。
>
> - **`pnpm-transparency-log`**（#17554）: Go の checksum database と同じ C2SP の形式（signed-note の鍵、tlog-checkpoint の署名と `CheckpointPolicy::verify`、tlog-cosignature の Ed25519 の連署、tlog-tiles のタイル、証明）。ログの鍵の閾値と witness の定足数で検証する。witness の無いポリシー（私設レジストリ）も可
> - **`pnpm-release-record`**（#17555）: 保存したバイト列そのものからレコードの中核の項目（`schema`・`purl`・`revision`・`interpretation`）を読み、SHA-512 のダイジェスト（`sha512-<base64>`）で識別する。npm・Cargo・PyPI のファイル・OCI のタグの PURL、DSSE の文、TUF のログのポリシー。`wasm32-wasip1` でもビルドできる

### pnpr: ホスト型のバージョンをリリースレコードと一緒に受け入れ、透明性ログで配る（[#17601](https://github.com/pnpm/pnpm/pull/17601), [#17602](https://github.com/pnpm/pnpm/pull/17602), [#17603](https://github.com/pnpm/pnpm/pull/17603), [#17604](https://github.com/pnpm/pnpm/pull/17604)）

> [!tip] 何ができるようになったか
> release records の RFC のステップ 1・2 の実装（SQL のメタデータを使うとき）。
>
> - **レコードの受け入れ**（#17601）: 公開した npm のバージョンごとに、検証したマニフェストとアーカイブから `schema`・`purl`・`revision`・`interpretation`・`inputs`（`.tgz`、`package.json`・`npm-shrinkwrap.json` のダイジェストとパス）を持つレコードを作り、バージョンと同じトランザクションで追記のみの `release_records` テーブルに入れる。プラットフォームのバリアントごとにも `inputs` を持つ
> - **ログへの記録**（#17602）: 受け入れと同じトランザクションで `log_entries` に項目を追加し、`Storage::integrate_log` で C2SP のタイル化したログに統合して、署名したチェックポイントを書く。タイルとチェックポイントはホスト型ストアの `.transparency-log` に置く（バケットから配れる）。バージョンを消してもログの項目は残る
> - **配信**（#17603）: `<base>/-/log/checkpoint`・`<base>/-/log/tile/<L>/<N>`・`<base>/-/log/tile/entries/<N>` と、`<base>/<name>/<version>+r<revision>/evidence`（レコード・包含証明・文・Sigstore のバンドル）。全パッケージの名前が載るエントリのバンドルは、組織の全パッケージを読める人だけに配る
> - **受け入れの文への署名**（#17604）: `releaseRecords.statementSigningKey` を設定すると、evidence にレジストリの in-toto の受け入れの文（述語 `https://pnpm.io/pnpr/acceptance/v1`）を DSSE で署名して載せる。読むたびに SQL のレコードから署名するので、鍵を替えても移行は要らない

### pnpr: リリースノートの保存と配信（[#17557](https://github.com/pnpm/pnpm/pull/17557)）

> [!tip] 何ができるようになったか
> release notes の RFC の pnpr 側（npm のルート）。SQL のメタデータを使うときだけ有効で、使わないとノート付きの公開は `400` で拒否する。
>
> - **保存**: パッケージのバージョンか公開（publication）ごとに `notes` テーブルに保存し、変更はすべて `note_history` に残る（編集・削除を戻せる）。対象の無いノートは `404`
> - **内容の制限**: UTF-8 で 64 KiB まで。LF・TAB 以外の制御文字、CR、双方向の上書き文字は不可
> - **公開と一緒に送る**: 単独の npm の公開文書の `notes` はそのバージョンのノート、一括公開の本文の `notes` は公開のノート

### pnpr 独自のパッケージ文書（split packuments）（[#17556](https://github.com/pnpm/pnpm/pull/17556)）

> [!tip] 何ができるようになったか
> split packuments の RFC のステップ 1〜4。integrity-addressed patch revisions の RFC のリビジョンの項目も pnpr 独自の形式に移した。
>
> - **pnpr**: `Accept: application/vnd.pnpr.install-v2+json` に独自の文書（`Vary: Accept`）で答える。バージョンごとに `deprecated`・`trust`・`revision`・公開時刻、完全な項目には `integrity`・`fileCount`・`unpackedSize`・`requiresBuild`・`bins`・`manifest` を持つ
> - **分割**: 文書が閾値（既定 64 KiB）を超えると、選ばれそうなバージョン（dist-tag の指す先と、メジャーごと（1.0 未満はマイナーごと）の最新）だけがマニフェストを持つ。分割は読むたびに文書から決め、どこにも記録しない
> - 変更ファイルには pnpm の CLI の `cache` コマンドのリリースレコードの処理なども含まれる

### パッケージのバージョンのプラットフォーム別バリアント（[#17559](https://github.com/pnpm/pnpm/pull/17559)）

> [!tip] 何ができるようになったか
> platform variants の RFC の、共通のタグのクレート・pnpr 側・pnpm の解決・lockfile・インストールの部分。バリアントは pnpr 独自のパッケージ文書（#17556）でだけ表す。
>
> - **`pnpm-platform-variants` クレート**: `os`・`cpu`・musl・glibc の下限（`manylinux_2_28`）・macOS/Windows の下限・`napi<N>`・`node<N>`/`electron<N>`・`wasm32` のプラットフォームのタグ。バリアントのタグは各プラットフォームのタグを並べて `+` でつなぐ
> - **選び方**: ネイティブを `wasm32` より上に、制約の数・glibc と OS の下限・ABI の完全一致 > N-API > 無し・最も高い N-API の順で順位を付け、同順位はエラー
> - **リンクと取得**: ホストの下限や ABI が分からないときは、リンクでは満たさない扱い、別のプラットフォーム向けの取得では満たす扱い
> - **pnpr**: 公開ではバリアントごとに `.tgz` の integrity で参照する

### pnpr: アーカイブを integrity で先に上げ、一括公開で参照する（[#17608](https://github.com/pnpm/pnpm/pull/17608), [#17610](https://github.com/pnpm/pnpm/pull/17610)）

> [!tip] 何ができるようになったか
> atomic workspace publication の RFC の「アーカイブをコミットの前に 1 つずつ integrity で上げる」部分のサーバー側。
>
> - **上げる**（#17608）: `PUT /-/pnpr/v0/artifacts/blob?integrity=<sha512-…>` で呼び出したアカウント用にアーカイブを 1 つ置き、`HEAD` で置いてあるか（とサイズ）を確かめる（`/npm/` の下にも）。integrity と `Content-Length` が合わなければ `400 EINTEGRITY`。置き場所はホスト型ストアの `.staged-archives/<principal digest>/` で、どのルートからも配らない。同時に受け取るのはサーバー全体で 4 件まで
> - **参照する**（#17610）: npm の公開文書の添付に `"data"` の代わりに `"integrity"` を書くと、置いたアーカイブを使う（`PUT /<name>` と `PUT /-/pnpr/v0/publish`）。置いていない・期限切れのアーカイブがあれば要求全体を `400` で失敗させ、一括公開の何も公開しない。再送は記録した結果で答える

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### `pnpm publish -r --batch` が pnpr にアーカイブを先に上げてからコミット（[#17611](https://github.com/pnpm/pnpm/pull/17611)）

> [!tip] 何ができるようになったか
> `serverType: pnpr` と宣言したレジストリへの `pnpm publish -r --batch` で、各パッケージのアーカイブを `HEAD` で確かめ、無いものだけを 2 件ずつ `PUT` で上げてから、添付に `integrity` を書いた一括公開を送る。
>
> - **失敗したとき**: 上げる段階の失敗（`ERR_PNPM_BATCH_PUBLISH_STAGING_FAILED`）はコミットの前なので何も公開されず、再実行では足りない分だけを上げる
> - 257 件以上の一括公開とほかのレジストリは従来どおり本文にアーカイブを含める。単独のパッケージの公開は変わらない

### エージェントスキルの一部だけの承認、カテゴリのディレクトリ、名前の衝突時の代わりの名前（[#17533](https://github.com/pnpm/pnpm/pull/17533)）

> [!tip] 何ができるようになったか
> pnpm v12 のエージェントスキルに 3 つの機能が加わった。
>
> - **一部だけ承認**: 承認したパッケージが複数のスキルを持つと、`pnpm approve` がチェックリストを出す。結果は `pnpm-workspace.yaml` の `permissions.<pkg>.skills: [guide, migrate]` に記録し、載せなかったスキルはリンクせず、再び尋ねない。`skills: true` は今後のバージョンも含めすべて承認
> - **カテゴリ**: `skills/` の下を 3 階層まで探す（例: `skills/engineering/implement/SKILL.md`）。カテゴリの下のスキルも、権限を取り消せば正しくリンクを外す
> - **代わりの名前**: スキルは自身の名前でリンクするが、承認した 2 つのパッケージが同じ名前のスキルを持つときや、その名前が pnpm 以外のファイル・ディレクトリで埋まっているときは、自動で `pnpm-` で始まる名前に切り替える

### 繰り返しの `pnpm install` が変わっていない `package.json` を読まない（[#17625](https://github.com/pnpm/pnpm/pull/17625), [#17637](https://github.com/pnpm/pnpm/pull/17637)）

> [!tip] 何ができるようになったか
> pnpm/tasks#256 のフェーズ 1・2。最新の状態のワークスペースでの繰り返しの `pnpm install` は、前回のインストール以降にファイルが変わっていないプロジェクトの `package.json` を読まない。
>
> - **記録**（#17625）: ワークスペースの状態の `validation` に `manifestFiles` を加え、各プロジェクトのマニフェストのファイル名と stat（mtime・ctime・サイズ）を記録する。#17637 で、確認が読む値（`name`・`version`・`bin`、各依存のマップ、peer 依存（URL の指定は `*` に）と `optional`、`directories.bin`・`publishConfig.directory`）も記録するようにした
> - **近道**（#17637）: プロジェクトのディレクトリを並べて各マニフェストを stat し、すべてのプロジェクトで記録した stat が一致して信頼できるときは、記録から作った代わりのマニフェストで判定する
> - `SOURCE_DATE_EPOCH` のもとでは記録しない。pnpm v11 は未知の `validation` の項目を無視する

### `verifyDepsBeforeRun` の確認も変わっていない `package.json` を読まない（[#17647](https://github.com/pnpm/pnpm/pull/17647)）

> [!tip] 何ができるようになったか
> pnpm/tasks#256 のフェーズ 3。`verifyDepsBeforeRun` を設定した `pnpm run`・`pnpm exec` は、1 つの lockfile がワークスペースを覆い、状態にマニフェストの記録があるとき、記録した stat が変わっていないプロジェクトについて記録から作った代わりのマニフェストで確認する。
>
> - 代わりのマニフェストでの「最新」の判定だけを採用し、それ以外やレコードが使えないプロジェクトがあれば、ファイルを読む確認に回る
> - プロジェクトごとの lockfile では従来どおりファイルを読む

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/タスク実行・並行処理|タスク実行・並行処理]]

### `pnpm store add` でダウンロード済みの tarball からストアを温める（[#17409](https://github.com/pnpm/pnpm/pull/17409)）

> [!tip] 何ができるようになったか
> `pnpm store add` が別の方法でダウンロードしたパッケージの tarball を受け付け、その中のレジストリのパッケージを `pnpm install --offline --frozen-lockfile` で入れられるようにストアを準備する（pnpm/pnpm#2978 の要望）。
>
> - **使い方**: `pnpm store add ./tarballs/*.tgz` の後に `pnpm install --offline --frozen-lockfile`
> - **嬉しい場面**: flatpak-builder や Nix のように、事前に全ソースを取得してからネットワーク無しでビルドする環境（これまで flatpak-builder-tools はストアの形式を Python で再実装していた）
> - **仕組み**: tarball は 1 回だけ取り込み、ストアの索引の別名で tarball の sha512・sha1・中の tar のハッシュ（`lockfile.integrityTarget: tar` 用）と `name@version` から引けるようにする

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/ストア|ストア]]

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]

### 単一プロジェクトの `version` を上げても依存の確認でインストールし直さない（[#17561](https://github.com/pnpm/pnpm/pull/17561)）

> [!quote] Before
> 1 つのプロジェクトだけのリポジトリで `version` を上げただけで、`verifyDepsBeforeRun` が「The workspace structure has changed since last install」と報告し、スクリプトの前にインストールを走らせていた。v12 ではインストールの近道でも解決し直していた。

> [!success] After
> プロジェクトのバージョンは、ワークスペースに複数のプロジェクトがあるときか、`linkWorkspacePackages` が `deep` のときだけ比べる（pnpm/pnpm#17560）。v11・v12 の両方で修正。

### v12 の既定のストアの場所をワークスペースのルートから決める（[#17472](https://github.com/pnpm/pnpm/pull/17472)）

> [!quote] Before
> 既定のストアの場所を、コマンドを実行したディレクトリから探していた。ホームのストアへのアクセスが制限された環境で、メンバーのプロジェクトから `pnpm add` するとルートのインストールと違うストアを選び、`ERR_PNPM_UNEXPECTED_STORE` で失敗していた。

> [!success] After

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/ストア|ストア]]

### `pnpm deploy` がリンク先の無いプロジェクトのシンボリックリンクを残す（[#17572](https://github.com/pnpm/pnpm/pull/17572)）

> [!quote] Before
> ソース側でリンク先が存在しないプロジェクトのシンボリックリンク（`node_modules` 無しで復元したビルドの Next.js の `.next/node_modules` の別名など）を、v12 は黙って落とし、v11 は `ENOENT` で失敗していた。

> [!success] After
> deploy の `Internal` のポリシーでは、元のリンクの文字列のままディレクトリのリンクとして作り直し、deploy が出力先に入れる依存を指すようにする（pnpm/pnpm#17571）。パッケージのルートの外を指すリンクは引き続き拒否する。v11 の importer は `imported` のポリシーでもぶら下がったリンクを省くようになった。
