## 新機能

### 実験的な `loaded` リンカーを追加（[#16482](https://github.com/pnpm/pnpm/pull/16482)）

> [!tip] 何ができるようになったか
> pnpm v12 に実験的な `nodeLinker: { type: loaded }` のインストールが加わった。互換性のあるパッケージは、検証済みのコンテンツアドレス可能ストア（CAS）の blob から直接読み込まれる。`nodeLinker.excluded` に挙げたパッケージとその依存ツリー全体は、通常のグローバル仮想ストア（GVS）のエントリを使う。
>
> - **使い方**: `pnpm-workspace.yaml` で有効にし、必要なら `nodeLinker.excluded` にパッケージ名を並べ、あとは通常の install・run・exec を使う
> - **仕組み**: pnpm がランタイムのマニフェストを生成し、単独で動くローダーを書き出し、JavaScript の実行ファイルのシムを作り、スクリプトと子プロセスにローダーをプリロードする。`pnpm store prune` は使用中の CAS の blob と実体化した GVS のツリーを残す
> - **条件**: Node.js 26.10.0 以上が必要。オプトインかつ実験的。パッチを当てたパッケージは自動で実体化し、ビルドが必要なパッケージは明示的に選ぶ（ビルドの承認は通常どおり）。モードを切り替えるときは既存の `node_modules` を削除する必要がある。楽観的な再インストールの近道は無効になる
> - **後続**: 凍結したストアでのインストールと、使われない GVS エントリの削除を修正（[#16600](https://github.com/pnpm/pnpm/pull/16600)）。v12.10.1 では生成ファイルを `node_modules` に置くよう変わった（[[repos/pnpm-pnpm/releases/v12.10.1|v12.10.1]]）

### 解決に関わる設定を lockfile に記録（[#16591](https://github.com/pnpm/pnpm/pull/16591)）

> [!tip] 何ができるようになったか
> オプトインの設定 `lockfile.includeResolutionSettings`（既定は `false`）を有効にすると、`pnpm-lock.yaml` の `settings` に解決結果を左右する設定（`autoDedupe`・`dedupeInjectedDeps`・`dedupePeerDependents`・`linkWorkspacePackages`）を記録する。どのマシンでも、lockfile がどの設定で作られたかが分かる。
>
> - **使い方**: `pnpm-workspace.yaml` に `lockfile:` のセクションを書き、`includeResolutionSettings: true` を指定する（`sideEffectsCache` と同じくセクションも受け付ける）
> - **挙動**: 記録と異なる値で動かすと lockfile は古いとみなされ、`pnpm install` は解決し直し、`--frozen-lockfile` は `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` で失敗する。`settings` のキーはアルファベット順に書かれ、オプトインしない lockfile は変わらない
> - **嬉しい場面**: v12.10.0 のリリースノートによると、`autoDedupe` を記録した lockfile はどのマシンの後続のインストールでも再利用されるため、`pnpm install --frozen-lockfile` の後の `pnpm run` がもう一度インストールを始めなくなる

### 依存の検証とパッケージの扱いをまとめて強化（[#16613](https://github.com/pnpm/pnpm/pull/16613)）

> [!quote] Before
> config 依存はレジストリと照合せずにインストールされ、`pnpm audit signatures` は lockfile の integrity と結び付いていなかった。大きなアーカイブのメタデータや公開用マニフェストを上限なくメモリに読み込み、エスケープすると区別できない URL 依存どうしが同じ仮想ストアのディレクトリを共有することがあった。

> [!success] After
> config 依存は npm レジストリから解決する必要があり、インストール・再リンクが必要なときだけレジストリと照合する（インストール済みなら余分なリクエストは無い）。パッケージの展開とデプロイのパスを閉じ込め、大きなアーカイブのエントリをストリーミングし、アーカイブのメタデータと公開用マニフェストのバッファに上限を設ける。`pnpm audit signatures` を lockfile の integrity に結び付け、`+`・`#`・`:`・`?` などでエスケープがあいまいになる URL・パスの依存だけディレクトリ名にハッシュを付け、`pnpm licenses` の端末出力を無害化する。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/セキュリティ|セキュリティ]]

### `pnpm run` の正規表現のセレクタで ECMAScript の構文を受け付ける（v12、[#16606](https://github.com/pnpm/pnpm/pull/16606)）

> [!quote] Before
> v12 は `pnpm run "/<regex>/"` を Rust の `regex` クレートでコンパイルしていたため、先読みや後方参照（`/^hello:(?!b).*$/` など）が使えず、リテラルのスクリプト名として扱われて `ERR_PNPM_NO_SCRIPT` で失敗していた（v11 では動いていた）。

> [!success] After
> ECMAScript の正規表現エンジン `regress` でコンパイルし、構文と意味を v11 に合わせる。スクリプト名は JavaScript の `RegExp` と同じく UTF-16 のコード単位で照合する。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/タスク実行・並行処理|タスク実行・並行処理]]

### `pnpm dlx --package=<pkg>` をコマンドなしで実行したときのエラーを明確に（v11、[#16306](https://github.com/pnpm/pnpm/pull/16306)）

> [!quote] Before
> v11 の `pnpm dlx --package=<pkg>` はコマンドが無くてもパッケージをインストールし、空のコマンドを実行しようとしてクラッシュしていた。

> [!success] After
> 何もする前に `ERR_PNPM_DLX_MISSING_COMMAND`（`'pnpm dlx' requires a command to run`）で失敗する（v12 と同じ）。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]

### 対話的な `pnpm audit --fix` の Patched 列が保存スタイルに従う（[#13215](https://github.com/pnpm/pnpm/pull/13215)）

> [!quote] Before
> 対話的な `pnpm audit --fix` の選択画面は、`saveExact`・`savePrefix` に関係なく修正版を `^X.Y.Z` と表示しており、`pnpm-workspace.yaml` に書かれる override と食い違っていた。

> [!success] After
> v11・v12 とも、`saveExact: true` や `savePrefix: ''` なら `X.Y.Z`、`~` なら `~X.Y.Z`、`=` なら `=X.Y.Z`、それ以外は `^X.Y.Z` と、書き込まれる override と同じ形で表示する。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]

### ワークスペースの `resolutions` の警告が `pnpm-workspace.yaml` の `overrides` を案内（v11、[#11868](https://github.com/pnpm/pnpm/pull/11868)）

> [!quote] Before
> ルート以外のワークスペースパッケージに `"resolutions"` があると、「ワークスペースのルートで `resolutions` を設定せよ」と警告していたが、pnpm v11 はルートの `resolutions` も読まないため、従っても解決しなかった。

### `loaded` リンカーの凍結ストアでのインストールと GVS の削除を修正（[#16600](https://github.com/pnpm/pnpm/pull/16600)）

> [!quote] Before
> `storeDir` がプロジェクト内の隠しでないディレクトリだと、`pnpm store prune` がストア自体を走査して使われない GVS のスロットを残していた。`frozenStore: true` の loaded のインストールも、プロジェクトの登録を書き込もうとしていた。

> [!success] After
> プロジェクトの走査と依存の巡回から正規のストアのルートを除き、loaded のマニフェストが参照するルートは残す。`frozenStore: true` ではプロジェクトの登録の書き込みを省く（書き込めるストアでは引き続き登録が必要）。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/loaded-リンカー|loaded リンカー]]
