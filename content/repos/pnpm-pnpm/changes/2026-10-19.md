### `pnpm-workspace.yaml` の設定を `include` で別ファイルに分ける（[#16967](https://github.com/pnpm/pnpm/pull/16967)）

> [!tip] 何ができるようになったか
> [config fragments RFC](https://github.com/pnpm/rfcs/blob/main/text/0000-config-fragments.md) を pnpm v12（Rust 版のみ）に実装した。ルートの `pnpm-workspace.yaml` の設定を、別の YAML ファイルや config 依存に任せられる。
>
> - **使い方**: ルートの `pnpm-workspace.yaml` の `include` に、ローカルの `./`・`../` の `.yaml`/`.yml` ファイルか宣言済みの config 依存を書き、任せる設定の一覧か `'*'` を対応付ける（config 依存は一覧が必須）。カタログは `catalog`・`catalogs.<name>`・`catalogs` で選ぶ
> - **相対パス**: 取り込んだファイルの中の相対パス（パスの設定、`packages` のグロブ、`pnpmfile`、`patchedDependencies`、スラッシュを含む `scriptShell`、カタログと `overrides` の `file:`/`link:`/パスの指定子）はそのファイルから測る（RFC からの変更点で、pnpm/rfcs#40 で提案中）。`patch-commit` などは持ち主のファイルからの相対パスで書くので、`patches/patches.yaml` に `foo@1.0.0: foo@1.0.0.patch` と書ける
> - **持ち主は 1 つ**: 一覧に書いた設定は、ファイルに書かれていなくてもそのファイルのもの。重なると `ERR_PNPM_DUPLICATE_SETTING`、任されていない設定は `ERR_PNPM_SETTING_NOT_DELEGATED`

### `lockfile.integrityTarget: tar` で tar のハッシュを固定し、リビジョンを tar のダイジェストで指す（[#17092](https://github.com/pnpm/pnpm/pull/17092)）

> [!tip] 何ができるようになったか
> [Tar integrity for every source](https://github.com/pnpm/rfcs/blob/main/text/0000-tar-integrity-for-every-source.md) と pnpm/rfcs#42 のリビジョンの変更を実装した。
>
> - **使い方**: `lockfile.integrityTarget: tar`（pnpm v12、オプトイン）。`pnpm-lock.yaml` の tarball のエントリ（レジストリのパッケージ、`tarball:` の URL、`file:` の tarball）が、展開前の tar のハッシュを固定する。lockfile には `settings.integrityTarget: tar` と記録される
> - **挙動**: 別の対象の lockfile で frozen install すると `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`。それ以外の install は解決し直してすべてのハッシュを書き直す。lockfile のバージョンは上げない
> - `.tgz` から展開したストアの行は `tarIntegrity` を記録し、新しい別名の表（`package_index_alias`、files レイアウトでは `index-aliases/`）で tar のキーからも引ける（pnpm v11 は読まない）。`pnpm audit signatures` は tar の固定を署名済みの `.tgz` の integrity に結び付ける
> - **リビジョン（pnpm v12 と pnpr）**: 元のもの（`revision: 0`）を含めてすべてのリビジョンを明示し、tar のダイジェストで指す

### zstd の content coding で tar を配るレジストリからインストール（[#17054](https://github.com/pnpm/pnpm/pull/17054)）

> [!tip] 何ができるようになったか
> [pnpm/rfcs#39](https://github.com/pnpm/rfcs/pull/39)（zstd tarballs through tar integrity）を pnpm v12 と pnpr に実装した。レジストリは各パッケージを `.tgz` の中身の非圧縮の tar として HTTP の content coding（zstd か gzip）で配り、メタデータでその tar のハッシュを固定する。圧縮は転送の詳細になり、lockfile のハッシュ・署名・provenance は圧縮後のバイト列に依存しない。
>
> - **`serverType: pnpr`**: `<registry>/<name>@<version>` のレイアウトを宣言し、lockfile には引き続き tarball の URL を書かない
> - **復号**: tarball の要求では `Content-Encoding` をそのまま受け取り、pnpm が自分で復号して zstd のウィンドウを 8 MiB（RFC 9659）に制限する。先頭のバイトが gzip なら `.tgz`、それ以外は tar として扱い、ハッシュは復号後の内容にかかる
> - **上限**: 新しい設定 `maxTarballUnpackedSize`（4 GiB）。tar ではさらに `dist.unpackedSize` までに制限し、ヘッダーと読み飛ばすエントリは 256 MiB まで、終端の後ろは 10 KiB のゼロまで。空の本文は失敗にする

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/インストール|インストール]]、[[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### `maxTarballUnpackedSize` を pnpm v11 と zip のアーカイブにも適用（[#17014](https://github.com/pnpm/pnpm/pull/17014)）

> [!tip] 何ができるようになったか
> [#17054](https://github.com/pnpm/pnpm/pull/17054) で pnpm v12 に入った展開後のサイズの上限を pnpm v11 に持ち込み、pnpm v12 が展開する zip にも適用した（pnpm/tasks#81、GHSA-8phr-vrxr-cgqc の gzip 解凍爆弾のうち [#16613](https://github.com/pnpm/pnpm/pull/16613) で残っていた部分）。
>
> - **pnpm v11**: アーカイブの通常ファイルのエントリが宣言するサイズをヘッダーを読むたびに足し、`maxTarballUnpackedSize` を超えると `ERR_PNPM_TARBALL_TOO_LARGE`（設定名・既定値 4 GiB・エラーコードは v12 と同じ）。メモリ上・gzip・bzip2 のストリームのどれも対象で、再試行しない。ランタイムを入れる zip も同じ上限
> - **pnpm v12**: zip のエントリごとの上限に加えて、合計も tarball と同じ `TarLimits` で数える
> - どちらも、無視する zip のエントリは解凍せずに飛ばし、数えない

### 公式 Docker イメージに Alpine 版（[#17069](https://github.com/pnpm/pnpm/pull/17069)）

> [!tip] 何ができるようになったか
> `ghcr.io/pnpm/pnpm` に、musl 版のリリース tarball から作る `<version>-alpine`・`<major>-alpine`・`alpine` のタグ（`linux/amd64`・`linux/arm64`）を追加した。
>
> - **使い方**: `COPY --from=ghcr.io/pnpm/pnpm:12-alpine /opt/pnpm /opt/pnpm` のあと `/opt/pnpm/pnpm` を `/usr/local/bin/pnpm` にリンク（同梱の node-gyp が `dist/` にあるので `/opt/pnpm` ごとコピーする）
> - **嬉しい場面**: `node:*-alpine` に `curl https://get.pnpm.io/install.sh | sh` で入れていて、CI の同時実行で 403 を受けるとき（pnpm/pnpm#16973）。x64・arm64 の musl tarball があるリリース（v12）だけで作る
> - **タグの付け方の変更**: `latest`・`<major>` が古いバージョンに戻らないよう、ビルドは正確なバージョンのタグだけを付け、最後に `latest`/`alpine` は全体で最も高い安定版、`<major>`/`<major>-alpine` はそのメジャーで最も高いバージョンに付ける（これまでは `latest` が 11.28.6 を指していた）

### pnpr: packument のキャッシュ用ヘッダーと条件付き要求（[#16962](https://github.com/pnpm/pnpm/pull/16962)）

> [!tip] 何ができるようになったか
> packument の応答に `ETag`・`Vary: Accept`・`Cache-Control` を付け、`If-None-Match`・`If-Modified-Since` に `304 Not Modified` で応える（pnpm/tasks#131 の C10）。
>
> - `ETag` は描画した packument の本文から求める強い ETag。`If-None-Match`（RFC 9110 の弱い比較）が `If-Modified-Since` より優先
> - 公開の packument は `Cache-Control: public, max-age={ttl}`（upstream の maxage か設定の `packument_ttl`）。非公開・呼び出し元ごとの応答は `private, no-store` のまま

### pnpr: `npm login`・`pnpm login` の Web ログインで SSO（[#16969](https://github.com/pnpm/pnpm/pull/16969)）

> [!tip] 何ができるようになったか
> OIDC のログインプロバイダーを設定すると、npm の Web ログイン（`/-/v1/login`）でブラウザの SSO から認証できる。
>
> - `POST /-/v1/login`（と `POST /~{registry}/-/v1/login`）: `login:` のある OIDC プロバイダーが無ければ `404`（従来の CouchDB 認証に戻れる）。あれば `202` で `loginUrl`・`doneUrl` を返す
> - `GET /-/v1/login/start`: プロバイダーが 1 つならそこへリダイレクト、複数なら選択画面
> - `GET /-/v1/login/poll/{session}`: 待機中は `202` と `Retry-After: 1`、認証後は `200` で `{"token": "<token>"}`

### pnpr: パッケージの所有者・メンテナーと tombstone（[#17060](https://github.com/pnpm/pnpm/pull/17060)）

### pnpr: すべてのエコシステムをそれぞれの接頭辞で配る（破壊的変更）（[#17087](https://github.com/pnpm/pnpm/pull/17087)）

> [!tip] 何ができるようになったか
> 設定したエコシステムの数にかかわらず、npm は常に `/npm/`（名前付きレジストリは `/npm/~<name>/`）、Cargo は `/cargo/`、Python は `/pypi/`、イメージは `/oci/` で配る（pnpm/tasks#131 の A1）。既定のイメージレジストリはホストのルートの `/v2/` でも応える。`/-/ping`・`/-/pnpr/v0/`・アカウントのエンドポイントはルートのまま。
>
> - **これまで**: npm だけのサーバーは `/` で配り、2 つ目のエコシステムを設定すると `/npm/` へ移っていたため、`.npmrc` のレジストリ URL・lockfile の tarball の URL・名前付きレジストリの URL・OIDC のワークロードの publish のパスが壊れていた
> - 読み取り専用トークンの許可リストが npm の audit のエンドポイントを npm の接頭辞の下でも認めるようになった
> - `/metrics` は `Accept` ヘッダーで npm パッケージ `metrics` に切り替わらなくなった（パッケージは `/npm/metrics`）

> [!warning] 移行が必要
> npm だけの pnpr を `/` で使っていた場合、レジストリの URL は `/npm/` の下になる。

### pnpr: ホスト型ストアのレイアウトを衝突しない形に（破壊的変更）（[#17100](https://github.com/pnpm/pnpm/pull/17100)）

> [!tip] 何ができるようになったか
> パッケージ・org・文書・blob が衝突しないホスト型ストアのレイアウトと、レイアウトの印・更新用のコマンドを実装した（pnpm/tasks#131 の A4 のストレージのレイアウト部分）。
>
> - **これまでの衝突**: org `acme` とパッケージ `acme` が同じディレクトリで、パッケージ `acme` の unpublish で org の名前空間ごと消えていた。グループ化したレジストリの暗黙の org（`cargo~internal`）が npm のパッケージ名として有効、S3 で `~` がエンコードされて OCI の掃除が効かない、など
> - **新しいレイアウト**（ディスクでもバケットでも同じ）: `layout.json`（`{"layout": 1}`）、org の無いレジストリは `default/packages/<name>/document.json` と `blobs/<file>`、org ごとに `orgs/<org>/packages/...`
> - **名前のエンコード**: 名前・org・ファイル名は 1 つのセグメント。`[a-z0-9._-]` 以外は `!` と 16 進 2 桁（`@scope/pkg` は `!40scope!2fpkg`）。macOS・Windows で大文字小文字だけ違う名前も分かれる

> [!warning] 移行が必要
> ホスト型ストアのレイアウトが変わり、レイアウトの印（`layout.json`）と更新用のコマンドが加わった。既存のホスト型ストアを使っている場合は新しいレイアウトへの更新を確認する。
