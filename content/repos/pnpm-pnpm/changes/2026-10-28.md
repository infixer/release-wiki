### pnpr: ストレージのレコードのキーとドットディレクトリの名前を正規化（[#17357](https://github.com/pnpm/pnpm/pull/17357)）

> [!tip] 何ができるようになったか
> pnpm/tasks#213 の一部。pnpr のストレージのレコードのキー・upstream のキャッシュのキー・ドットディレクトリの名前をそろえた。
>
> - **レジストリのレコード**: `.team-rosters`・`.rule-overrides` のレコードを、`pnpr.yaml` のトップレベルで宣言したレジストリでも常に `<ecosystem>/<local_name>.json` に保存する。レジストリをトップレベルの `registries:` と `<ecosystem>:` のブロックの間で動かしてもパスが変わらない（`legacy_key` のフォールバックは削除）
> - **tombstone**: `.tombstones/<ecosystem>/<scope>/<name>.json` の 2 段のレイアウトに（スコープなしの npm パッケージは `@/`）
> - **upstream のキャッシュ**: `upstream` を `<ecosystem>/<local_name>` に正規化し、置き場所を動かしてもキャッシュのダイジェストが変わらない
> - **名前空間**: 内部の名前空間から余分な `/v0`・`/v1`・`pnpr-` の接頭辞を外した

## 変更・修正

### pnpr: 1 つの URL に向けた複数のレジストリの接頭辞を保つ（[#17339](https://github.com/pnpm/pnpm/pull/17339)）

> [!quote] Before
> pnpr への解決の要求では、レジストリの宣言が URL ごとに 1 つの `prefix` しか持てなかった。2 つの接頭辞（例: `namedRegistries` の `zeta` と `work`）を同じ URL に向けると、小さい方しかサーバーに届かず、`zeta:^1.0.0` の依存の解決や、既存の `foo@zeta:1.0.0` の lockfile の項目が失敗した。

> [!success] After
> 要求のプロトコルに `prefix` と並ぶ `aliases` の一覧が加わり、v11・v12 の両方のクライアントが送り、サーバーが検証して振り分ける（`pnpm-workspace.yaml` には書けず、新しい設定ではない）。v11 の設定の読み込みでは、`prefix: __proto__` の `registries` の項目が黙って捨てられることもなくなった。

📦 pnpr@0.1.0-alpha.17 · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]、[[repos/pnpm-pnpm/topics/設定|設定]]

### `pnpm add -T` をあいまいとして拒否（[#17333](https://github.com/pnpm/pnpm/pull/17333)）

> [!quote] Before
> `pnpm add` には `--save-types` と `--tilde` の両方があり、どちらも短縮形に `-T` を求めているが、どちらのものかは決まっていなかった。

### `pnpm store prune` がプロジェクトで使っているパッケージを消さない（[#17327](https://github.com/pnpm/pnpm/pull/17327), [#17379](https://github.com/pnpm/pnpm/pull/17379)）

> [!quote] Before
> prune はストアのファイルのハードリンクが 1 本なら未使用と判断していた。ビルドやパッチを当てるパッケージ（`clone-or-copy` で取り込む）や、`packageImportMethod: copy`・macOS の clone で入れたパッケージは、使用中でもリンクが 1 本なので消され、次のインストールで再ダウンロードになっていた（CI でキャッシュを保存する前に prune すると、毎回同じパッケージが消えていた）。

> [!success] After
> 登録された各プロジェクトのインストール済みの `node_modules/.pnpm/lock.yaml` を読み、ストアの索引の行のファイル（side-effects の項目も含む）をすべて残す。パッチ・ビルド・コピー・clone したパッケージや `node@runtime:` も対象。lockfile や行が無いときは従来のハードリンクの判定に戻る。v11・v12 の両方を修正。続く #17379 で、`sharedWorkspaceLockfile: false` のワークスペースの `packageConfigs.<project>.modulesDir` も見て lockfile を探すようにした。

📦 pnpr@0.1.0-alpha.17 · トピック: [[repos/pnpm-pnpm/topics/ストア|ストア]]

### 名前付きレジストリの指定の optional 依存を、lockfile にあれば飛ばさない（[#17365](https://github.com/pnpm/pnpm/pull/17365)）

> [!quote] Before
> 解決に失敗した optional 依存は、lockfile に合う項目が無ければ飛ばされる。この確認は素の semver の範囲しか受け付けず、`work:^1.0.0` のような名前付きレジストリの接頭辞の指定は、lockfile に `foo@work:1.2.0` があっても常に飛ばされ、lockfile の項目も消えていた。

> [!success] After

### hoisted のインストールが途中で止まっても、置き換え中の場所を次回に信じない（[#17370](https://github.com/pnpm/pnpm/pull/17370)）

> [!quote] Before
> `nodeLinker: hoisted` では、前回の `.modules.yaml` の `hoistedLocations` にある場所を、`package.json` のバージョンが合えば再利用する。置き換えの途中でインストールが止まると古い記録が残り、変更（パッチの編集など）を元に戻すと、次のインストールが半分置き換えたファイルを再利用していた。

### スコープを別のレジストリに向けたら、レジストリを持たない lockfile のキーを解決し直す（[#17373](https://github.com/pnpm/pnpm/pull/17373)）

> [!quote] Before
> `@scope/a@1.0.0` のような素の lockfile のキーはレジストリを記録しないので、スコープの振り分けを別のレジストリに変えても lockfile は新しいままとされ、固定したバージョンを新しいレジストリから古い integrity で取りに行って失敗していた（v11・v12）。

> [!success] After
> lockfile を解決したときのスコープの振り分け（`registryRoutes`）をワークスペースの状態に記録する。振り分けが変わったスコープの素のキーは、解決するインストールでは古いとみなし、範囲から新しいレジストリで解決し直す。`pnpm install --frozen-lockfile` は記録どおり入れる。振り分けの変更は繰り返しのインストールの近道と `verify-deps-before-run` でも設定の変化として扱う。既定のレジストリの変更は（ミラーの切り替えが多いため）記録しない（pnpm/tasks#209）。

### macOS で並列実行中に pnpm を kill すると一部のスクリプトが残る問題を修正（[#17377](https://github.com/pnpm/pnpm/pull/17377)）

> [!quote] Before
> macOS には `pipe2` が無く、Rust の std は `pipe()` の後で `FD_CLOEXEC` を付ける。並列実行で別のスレッドがその間にスクリプトを fork すると、グループの watchdog のパイプをスクリプトが受け継ぎ、pnpm を kill しても watchdog が入力の終わりを受け取れず、プロセスグループを kill しなかった。

> [!success] After
> プロセス全体の `RwLock` を設け、スクリプトの spawn は共有で、watchdog の spawn は排他で取る（スクリプトは今までどおり並行して起動できる）。watchdog がスクリプトの出力のパイプを受け継ぐこともなくなった（v12 のみ。Linux は影響なし。pnpm/tasks#216）。

### 絞り込んだインストールで配置の設定が変わっていたら失敗させる（[#17380](https://github.com/pnpm/pnpm/pull/17380)）

> [!quote] Before
> 一部のワークスペースのプロジェクトに絞った `pnpm install` が、配置の設定の変化に気付くと共有のルートの `node_modules` を消し、選んだプロジェクトだけをリンクし直していた。選ばなかったプロジェクトは依存を失っていた。

> [!success] After
> modules ディレクトリを作り直すのはすべてのプロジェクトをインストールするときだけ。絞り込んだインストールは変化に応じたエラー（`ERR_PNPM_NODE_LINKER_DIFF`・`ERR_PNPM_HOIST_PATTERN_DIFF`・`ERR_PNPM_PUBLIC_HOIST_PATTERN_DIFF`・`ERR_PNPM_VIRTUAL_STORE_DIR_MAX_LENGTH_DIFF`・`ERR_PNPM_UNEXPECTED_STORE` など）で、何も消さずに失敗する。v12 では `add`/`remove`/`update` と同じ経路になり、`UnsafeFilteredModulesDir` のエラーは削除した。

> [!warning] 移行が必要
> 設定を変えた後に絞り込んだインストールが失敗したら、ワークスペース全体で `pnpm install` を実行して `node_modules` を作り直す。

### コンテナの cgroup の CPU の上限でワーカーの数を決める（[#17385](https://github.com/pnpm/pnpm/pull/17385)）

> [!quote] Before
> pnpm 11 はワーカーのプールと既定の `workspaceConcurrency` を `os.availableParallelism()`（CPU のアフィニティの数）から決めていた。233 CPU のノードで 4 CPU の Kubernetes の制限のコンテナでは、インストールごとに 232 のワーカーを作り、メモリを使い切っていた（pnpm/pnpm#17382）。

> [!success] After
> 新しいパッケージ `@pnpm/os.available-parallelism` が cgroup の CPU の上限を自分で読み（v2 は階層をすべてたどり、`/proc/self/mountinfo` からマウントを調べる）、アフィニティの数をその上限で抑える。既定の `workspaceConcurrency` にも効く。上限の無いホストでは上限を設けない。

### git 依存の Cargo のビルド用にローダーのランタイムを含め、zstd を更新し、ストアの索引の初期化の競合を修正（[#17388](https://github.com/pnpm/pnpm/pull/17388)）

> [!quote] Before
> Git リポジトリを Cargo の依存にすると、`pnpm-deps-restorer` が `include_str!` するローダーのバンドルが無くてコンパイルできなかった。圧縮の依存に脆弱性があり、SQLite の journal mode の初期化が並行すると、インストールが空のストアの索引で終わることがあった。
