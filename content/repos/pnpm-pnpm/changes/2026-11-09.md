## 新機能

### loaded リンカーが一時ディレクトリでビルドし、ストアに残せるパッケージを増やす（[#17318](https://github.com/pnpm/pnpm/pull/17318)）

> [!tip] 何ができるようになったか
> loaded リンカーで、条件を満たすパッケージ（副作用キャッシュに一致する項目があるものを含む）をコンテンツアドレス可能ストアに置いたまま使えるようになった。
>
> - **ビルド**: 副作用キャッシュの読み書きが有効なとき、承認済みでキャッシュに無いパッケージを一時ディレクトリでビルドし、互換性のある結果をストアから読み込む。ファイルを変えないビルドもキャッシュする
> - **自動で実体化**: ネイティブアドオン・キャッシュされたシンボリックリンク・パッチ・ランタイムの要件・ファイルシステムへのアクセスが検出されたパッケージと、その依存。副作用キャッシュから除外したパッケージは従来どおりプロジェクトごとにビルドする
> - **注意**: 計算した import や生成したファイルシステムのアクセスは検出できないことがあるので、そうしたパッケージは除外する

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/loaded-リンカー|loaded リンカー]]

### `pnpm store add` がローカルの tarball を並行で取り込み、ディレクトリも受け付ける（[#17880](https://github.com/pnpm/pnpm/pull/17880)）

> [!tip] 何ができるようになったか
> - **1 回の読み込み**: これまで `pnpm store add <file.tgz>` は tarball を 3 回読んでいた（解決時のメタデータ・`sha512`/`sha1` の計算・ストアへの展開）。展開しながら `sha1`・`sha512`・`tar_integrity` を求めるようにした
> - **並行**: パッケージを順に処理するループをやめ、`networkConcurrency` の数まで並行で取り込む。ローカルの tarball を開く処理は展開後の処理用のセマフォで制限し、メモリとファイル記述子の上限を抑える
> - **ディレクトリ**: `pnpm store add ./tarballs` のように、ディレクトリから `.tgz`・`.tar.gz`・`.tar` を再帰的に探して取り込む

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/ストア|ストア]]

### NetBSD x64 のビルド済み CLI バイナリ（[#17830](https://github.com/pnpm/pnpm/pull/17830)）

> [!tip] 何ができるようになったか
> `netbsd-x64` 向けの CLI バイナリを、NetBSD 10.2 の VM の中でネイティブにビルドして配布する。`cross` の NetBSD のイメージ（NetBSD 9 の sysroot）ではリンクできなかったため（クローズされた #17817 のパッケージングを引き継いだ）。NetBSD 向けには CLI だけを公開し、NAPI のアドオンは出さない。リリースでは VM の中で `pnpm --version` を確かめる。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/ランタイム管理|ランタイム管理]]

### pnpr: メタデータを PostgreSQL・MySQL に置ける、スキーマの移行を 1 つに（[#17874](https://github.com/pnpm/pnpm/pull/17874), [#17881](https://github.com/pnpm/pnpm/pull/17881)）

> [!tip] 何ができるようになったか
> - **PostgreSQL・MySQL**（#17874）: パッケージのメタデータを、アカウント・トークンと同じ PostgreSQL・MySQL に保存できる。1 つの `database.url` で両方のデータベースを選ぶ。書き込みは serializable のトランザクション（競合時は再試行）、読み取りは repeatable read のスナップショット。libSQL では認証とメタデータに別々のローカルのレプリカのファイルを使う。MySQL ではメタデータのキーは 512 バイトまで（超えると切り詰めずに拒否）
> - **移行**（#17881）: メタデータの `schema_version` と認証の `auth_schema_migrations` を、前方向だけの番号付きの移行と 1 つの `schema_migrations` の表にまとめた（メタデータの 24 表と認証の 3 表）。1.0 のスキーマを手順 1 とする。2 つのレプリカが同時に起動しても二重に移行しないよう書き込みのロックを取る。MySQL では中断した手順を安全にやり直せる

> [!warning] 移行が必要
> `database.url` が、これまで別々だった `backend` と `metadata` のブロックを置き換える（#17874）。`schema_migrations` の無いデータベース（`schema_version`・`auth_schema_migrations` を持つものなど）は、1.0 前と同じく作り直しが必要として拒否される（#17881）。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: OCI のアップロードのチャンクの上限を知らせる `oci.chunkMaxBytes`（[#17794](https://github.com/pnpm/pnpm/pull/17794)）

> [!tip] 何ができるようになったか
> `oci.chunkMaxBytes`（正の値、既定は無し）を設定すると、OCI のアップロードの開始・進行の応答に `OCI-Chunk-Max-Length` を付ける。アップロードの扱いと blob 全体の上限は変わらない。
>
> - **注意**: このヘッダーは OCI 1.1 に入っていない提案で、Docker・Podman にレイヤーを分割させることはできない（Podman が使う containers/image は 1 回の PATCH で送る）。Cloudflare のガイドに、Cloudflare Containers の外に TLS のプロキシの後ろで pnpr を置くべき場合を書いた

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### optional の peer の候補が持ち込む必須の peer も確かめる（[#17770](https://github.com/pnpm/pnpm/pull/17770), [#17788](https://github.com/pnpm/pnpm/pull/17788)）

> [!quote] Before
> 足りない optional の peer をワークスペースのほかの場所で解決したバージョンで補うとき、候補自身の peer は確かめていたが、一緒に自動で入る必須の peer は確かめていなかった。`web` が `A` と `react@18` に依存し、`A` の optional peer `B` が必須の peer `react-native`（`react@^19` を求める）を持つと、`web` に `B`・`react-native` が補われ、`react` の peer が満たされなくなっていた。

> [!success] After
> 必須の peer の連鎖を、必須の peer の hoist が選ぶバージョンでたどり、満たされない peer が残るなら `B` を補わない（#17770）。ワークスペースでまだ解決されておらずレジストリの範囲から解決される必須の peer も、グラフに加えずに解決してその peer を確かめる（#17788）。v11（TypeScript）と v12（Rust）の両方。
