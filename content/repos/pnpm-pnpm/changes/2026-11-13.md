## 新機能

### `lockfile.format: v13` がディレクトリの依存の入力を記録（[#17930](https://github.com/pnpm/pnpm/pull/17930)）

> [!tip] 何ができるようになったか
> 実験的な v13 の lockfile に、ローカルのディレクトリの依存の指定（フックを通した指定）・依存のメタデータ・マニフェストの出どころを記録し、lockfile が最新かどうかの確認でそれを比べる（pnpm/tasks#228）。記録の無い項目には従来の確認を使う。
>
> - **使い方**: `lockfile.format: v13` のまま `pnpm install`
> - **挙動**: v12.20.0 のリリースノートによると、frozen install はロックしたバージョンがまだ満たしていても、変わった指定を拒否する

⏳ 未リリース（v12.20.0 のリリースノートに記載） · トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### `pnpm store add` が tarball の URL・git の依存も lockfile の項目で引けるように（[#18000](https://github.com/pnpm/pnpm/pull/18000)）

> [!tip] 何ができるようになったか
> `pnpm store add <file.tgz>` で取り込んだ tarball を、`--dir` のインストールが読む lockfile の `packages` の項目のうち `integrity`（sha512・sha1・tar のハッシュ。項目が持つ最も強いアルゴリズムだけ）が一致するものの `<integrity>\t<pkg_id>` のキーでも引けるようにする。
>
> - **嬉しい場面**: `is-odd@https://registry.yarnpkg.com/...tgz` のような tarball の URL の依存や、ホストのアーカイブの URL で記録される git の依存でも、`pnpm install --offline --frozen-lockfile` が `ERR_PNPM_NO_OFFLINE_TARBALL` で失敗しない。flatpak-builder-tools や Nix のようなサンドボックスのビルダーが、ストアの行を自分で書かなくてよい

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/ストア|ストア]]

### pnpr: lockfile の形式と解決の設定をクライアントと取り決める（[#18020](https://github.com/pnpm/pnpm/pull/18020)）

> [!tip] 何ができるようになったか
> pnpm と pnpr のリゾルバーの食い違いに気付けるようにした（1.0 の前）。
>
> - **未知のフィールドを拒否**: npm・Cargo・Python の解決の要求で、未知のフィールドは `400`・`ERR_PNPR_UNSUPPORTED_REQUEST_FIELD`（pnpm v11 が送る `nodeVersion`・`os`・`arch` は受け付ける）
> - **lockfile の形式**: `acceptedLockfileFormats` は `pnpm-lock/9.0`・`cargo-lock`・`pylock` のような形式名に。解決の `done` フレームは `lockfileFormat` を持ち、Rust のクライアントは `pnpm-lock/9.0` 以外を拒否
> - **キープアライブ**: ストリームの解決は 15 秒ごとに `progress` フレームを送る。フレームの仕様は `endpoints.md` に記載
> - **ローカルへのフォールバック（pnpm v12）**: サーバーがどちらかの拒否のコードで断ると、`pnpm install`・`pnpm update` は警告を出してローカルで解決する（Cargo・Python も同様）

### pnpr: レジストリのグラフをメタデータのデータベースに置く `registriesManagedBy: api`（[#18036](https://github.com/pnpm/pnpm/pull/18036)）

> [!tip] 何ができるようになったか
> レジストリ・upstream・パッケージの claim・チーム・アクセスリスト・`defaultRegistry`・`routes.public` を、`pnpr.yaml` ではなくメタデータのデータベースの版付きの文書に置ける。各レプリカは設定のデプロイなしで揃う。
>
> - **管理 API**: `GET`/`PUT /-/pnpr/v0/admin/registries`、`GET`/`PUT`/`DELETE /-/pnpr/v0/admin/registries/{name}`、`GET /-/pnpr/v0/admin/registry-revisions[/{version}]` と `POST .../{version}/restore`。書き込みは `If-Match`（不一致は 412）と `?dryRun=true`（検証と変わるレジストリ名の差分）
> - **CLI**: `pnpr registries export`・`pnpr registries import [--dry-run]`（GitOps 向けにオフラインで動く）
> - **権限**: 新しい `auth.registryAdmins` が構造（レジストリ・upstream・claim・restore）を変えられ、`auth.admins` はチームとアクセスリストの編集
> - **既定**: ファイルのモードのままで挙動も同じ（レジストリの管理のエンドポイントは 403 `ERR_PNPR_REGISTRIES_CONFIG_MANAGED`）

> [!warning] 移行が必要
> `teamsManagedBy` と `rulesManagedBy` は削除され、データベースのモードにまとめられた。保存済みの名簿とルールの変更は移行されずに捨てられる（pnpr の実験的な系列への破壊的変更）。

### pnpr: 既定のアカウントとトークンをメタデータのデータベースに置く（[#18012](https://github.com/pnpm/pnpm/pull/18012)）

> [!tip] 何ができるようになったか
> 単一インスタンスの pnpr が `users.json`・`tokens.db`（どちらも無ければメモリ）に持っていたアカウントとトークンを、メタデータのデータベース（SQLite）に移し、既定の構成で保存先を 1 つにした。トークンの照会はデータベースを読むので、別のプロセスでの失効（動いているサーバーの横での `pnpr add-user` のパスワードのリセットなど）も次の要求から効く。
>
> - **CLI**: `pnpr import-htpasswd` はメタデータのデータベースに 1 つのトランザクションで取り込み（dry run はロールバック）、`--target` は無くなった。共有のデータベースの設定では拒否

> [!warning] 移行が必要
> 設定の `auth.users.file` と `auth.tokens.file` は無くなった（`auth.tokens` には `defaultLifetime`・`maxLifetime` が残る）。

### pnpr: トークンの既定と最大の有効期間（[#17997](https://github.com/pnpm/pnpm/pull/17997)）

> [!tip] 何ができるようになったか
> パスワードのログイン（`PUT /-/user/{name}`）や `POST /-/npm/v1/tokens` のトークンの有効期間の設定を追加。
>
> - `auth.tokens.defaultLifetime`（既定 `90d`）— ログインのトークンと、`expires`・`expires_in` を送らずに作ったトークンの有効期間
> - `auth.tokens.maxLifetime`（既定なし）— 上限。より後の期限を求めたトークンは上限まで短くし、応答の `expires` に示す
> - どちらも `1m` 以上で、短い値・読めない値は設定の読み込みで失敗。OIDC のブラウザのセッションには効かない

> [!warning] 移行が必要
> これまで期限の無かったパスワードのログインのトークンと期限なしで作ったトークンは、90 日で使えなくなる。期限なしの `npm token create` で作った CI のシークレットは入れ替えるか、明示の `expires` を付けて作る。変更前に発行したトークンは保存済みの期限のまま。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: アカウントの状態・トークンの接頭辞・トークンのスキーマを整理（[#17996](https://github.com/pnpm/pnpm/pull/17996)）

> [!tip] 何ができるようになったか
> v1 のスキーマの凍結に向けて `users`・`tokens` のスキーマとトークンの形式をまとめた。
>
> - **`users`**: `users.bcrypt_hash` の目印の文字列（削除の `"!"`、パスワードなしの `"*"`、`"{SHA}..."`）をやめ、`status`（`active`/`deactivated`/`deleted`）・`credential_kind`（`none`/`bcrypt`/`sha1`）・NULL を許す `password_hash`・`created_at`（ミリ秒）・`status_revision` を持つ（SQLite/libSQL・PostgreSQL・MySQL・JSON）
> - **アカウントの使える・使えない**: `users.status` で決める。SCIM の無効化・再有効化は世代の順に適用し、無効化ではトークンを原子的に失効
> - **トークンの形式**: 個人の bearer トークンを `pnpr_<base62 の 43 文字><CRC-32 の 6 文字>`（54 文字）で発行して見分けやすくした。照会は SHA-256 のハッシュなので、既存のトークンもそのまま使える

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: SCIM のアカウントを OIDC の subject に結び付け、アクセスの確認を統一（[#17991](https://github.com/pnpm/pnpm/pull/17991)）

> [!tip] 何ができるようになったか
> `login.scim` を有効にすると、確認済みの OIDC の subject を SCIM の `externalId` に結び付け、ユーザーごとの `login.users` の項目なしでサインインできる。見つからない・曖昧・無効化されたアカウントは拒否し、ディレクトリを持てる OIDC プロバイダーは 1 つだけ。結び付けが変わると既存のセッションを失効する。
>
> - **アーティファクトの所有者**: `artifacts.owners` のルールに `team:<registry>:<teamId>` を書ける。ルールが参照するチームは team API で削除できない
> - **アクセスの確認**: リゾルバー・アーティファクト・パイプラインは認証のミドルウェアが決めた呼び出し元を使う。資格情報・パッケージのルール・所有・チーム・upstream・アーティファクト・管理者の組み合わせ方を説明するアクセスのガイドを追加

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: 管理 API のユーザーを ID で指定し、`POST /admin/users` で作成（[#17993](https://github.com/pnpm/pnpm/pull/17993)）

> [!tip] 何ができるようになったか
> - `POST /-/pnpr/v0/admin/users`（`{"name", "password"}`）でアカウントを作る（`maxUsers` を超えても作れる）。`201` と `{"id", "name"}`、名前が使われていれば `409`

> - 監査のイベント `user.create`・`user.password_update` に `user_id` が入る

### pnpr: Cloudflare のキャッシュをレジストリの変更の後に無効化（[#17950](https://github.com/pnpm/pnpm/pull/17950)）

> [!tip] 何ができるようになったか
> 匿名の公開のメタデータと tarball を Cloudflare のキャッシュから配り、レジストリに問い合わせないようにする。ホスト型のパッケージの変更はデータベースの書き込みと原子的にパッケージのパージを予約し、実行時のポリシーの変更はデプロイ全体のパージを予約する。未送信のパージは再起動をまたいで残る。
>
> - **Worker の例**: エントリを元の要求の開始から最大 5 分キャッシュし、古い応答には戻らない。認証付きの要求と非公開の応答は共有キャッシュを通らない
> - **使うには**: 新しい pnpr、Cloudflare のゾーンのトークン、Worker の更新が要る

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### `workspace:` のパスの root の `overrides` を推移的な依存にも適用（[#17947](https://github.com/pnpm/pnpm/pull/17947)）

> [!quote] Before
> `workspace:./packages/foo` のような相対の `workspace:` のパスの root の `overrides` は、レジストリのパッケージのようにファイルシステムのディレクトリを持たないマニフェストの依存には効かなかった（pnpm/tasks#270）。

> [!success] After
> ディレクトリの無いマニフェストでは workspace の root を基準に絶対の `workspace:` のパスとして書き換え、対象はワークスペースのパッケージのまま（その `catalog:` の依存も解決できる）。両方のリゾルバーが絶対の `workspace:` のパスをディレクトリとして読む。

### git の依存の指定で npm の `::` 区切りを受け付ける（[#17976](https://github.com/pnpm/pnpm/pull/17976)）

> [!quote] Before
> フラグメントを `&` でしか分けず、`gitlab:gitlab-org/cli#v1.124.0::path:internal/commands` の `v1.124.0::path:internal/commands` を 1 つの ref として読んで「Could not resolve ... to a commit」で失敗していた。

> [!success] After
> TypeScript・Rust の両方の CLI で `&` と `::` で分ける（`github:owner/repo#semver:^1.0.0::path:packages/foo` など）。ref は `:` を含めないので、既存の指定の意味は変わらない。

### 最も高い一致の peer の結合を semver の範囲に限る（[#17753](https://github.com/pnpm/pnpm/pull/17753)）

> [!quote] Before
> 最も高い一致で peer をまとめるとき（`autoInstallPeersFromHighestMatch`）、semver ではない指定（パス・別名・タグ）の衝突も結合していた。足りない peer を入れるとき、ローカルのパスやプロトコル付きの指定が優先のレジストリのバージョンで置き換わることもあった（pnpm/tasks#272）。

> [!success] After
> 結合は semver の範囲だけ（両方の実装）。同じ非 semver の指定はそのまま残り、衝突するものは missing のまま。TypeScript では兄弟の部分的な結果が拒否した peer を復活させないようにし、peer の集合を作る時点で taken の peer のカタログの範囲を解決する。

⏳ 未リリース（v12.20.0 のリリースノートに記載） · トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### injected の peer のグラフが lockfile の往復で崩れない（[#17957](https://github.com/pnpm/pnpm/pull/17957)）

> [!quote] Before
> 生成したテストを injected のワークスペースのパッケージ・名前付きのカタログ・v9/v13 の両方の形式に広げたところ、子の辺のまとめ方がハッシュマップの順に依存し、optional の peer・入れ子の提供元のバリアント・依存の循環で v13 の往復が失敗するケースが見つかった。

> [!success] After
> リゾルバーのグラフの記録を走査の順にまとめ、v13 で推移的な名前と optional の peer の peer/子の分類を保つ。入れ子の識別子を、それが指す結び付きにも書く。v9 の従来の frozen の確認から v13 の記録したディレクトリの入力への移行を CLI のテストで確認。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### `pnpm deploy` が injected のワークスペースのパッケージの解決済みの snapshot を保つ（[#17973](https://github.com/pnpm/pnpm/pull/17973)）

### pnpr: npm の `publish` の既定のルールを `$owners` に（[#17969](https://github.com/pnpm/pnpm/pull/17969)）

> [!quote] Before
> npm のレジストリで `publish` の無い `packages:` の項目は `$authenticated` になり、サインインしたどのアカウントでもほかのアカウントのパッケージの新しいバージョンを公開し、dist-tag を動かせた。

> [!success] After
> npm の既定を `$owners` にし、最初の公開が名前を取り、その後の公開と dist-tag の移動はメンテナーか `auth.admins` だけ。Cargo・PyPI・OCI は `$authenticated` のままで、そこでの `$owners` は設定の読み込みと管理 API で拒否する。公開の認可をパッケージのロックの下でもう一度確かめ、2 つのアカウントが同時に新しい名前として公開できる隙間を閉じた。テスト用の registry-mock の設定は `publish: $authenticated` を明示して、これまでの挙動を保っている。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/pnpr|pnpr]]

### pnpr: 平たいレジストリの宣言だけを受け付ける（[#17959](https://github.com/pnpm/pnpm/pull/17959)）

### pnpr: npm 12 のトークン作成の権限・日数の期限・制限を扱う（[#17951](https://github.com/pnpm/pnpm/pull/17951)）
