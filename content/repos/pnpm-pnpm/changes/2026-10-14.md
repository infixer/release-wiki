## 新機能

### `pnpm token` コマンドを実装（[#16827](https://github.com/pnpm/pnpm/pull/16827)）

> [!tip] 何ができるようになったか
> pnpm v12 で「not implemented」だった `pnpm token` を、npm 11 の `token` コマンドにならって実装した。レジストリの認証トークンの一覧・作成・取り消しができる。
>
> - **`pnpm token list`**（`ls`、既定）: `GET /-/npm/v1/tokens` の全ページを取得（`urls.next` はレジストリのオリジン内に限り、ページ数に上限あり）。通常の表示・`--json`・`--parseable`
> - **`pnpm token revoke <id|token...>`**（`rm`・`delete`・`remove`）: キーの前方一致かトークンの値で引数を解決して `DELETE /-/npm/v1/tokens/token/<key>`。複数指定でき、重複は 1 回だけ取り消す。診断には引数の先頭 8 文字までしか出さない
> - **`pnpm token create [--read-only] [--cidr <cidr>]`**: アカウントのパスワードを尋ね（端末ではマスク、それ以外は stdin の 1 行目）、`readonly`・`cidr_whitelist` と一緒に送る。応答が失われても別のトークンを作らないよう POST は 1 回だけ
> - リクエストのリダイレクトはレジストリのオリジン内に限る

⏳ 未リリース（v12.13.0 に記載）· トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]

### `pnpm profile` コマンドを実装（[#16828](https://github.com/pnpm/pnpm/pull/16828)）

> [!tip] 何ができるようになったか
> pnpm v12 で「not implemented, use npm」だった `pnpm profile` を、npm の `profile` コマンドとレジストリの `-/npm/v1/user` プロトコルにならって実装した。
>
> - **`get [<key>...]`**: プロフィールを表、指定したキーの値、`--json`、`--parseable` で表示。設定途中の 2FA は `disabled` と表示
> - **`set <key> <value>`**: 省いた項目はレジストリに消されるため、ほかの書き込み可能な項目と一緒に送る。`set password` は現在と新しいパスワードを尋ね、コマンドラインでの値の指定は拒否
> - **`enable-2fa [auth-only|auth-and-writes]`**: パスワードを尋ね、初回は QR コードとシークレットを表示し、認証コードを送ってリカバリーコードを表示する。`--json`・`--parseable` は不可
> - **`disable-2fa`**: パスワードを尋ねる。2FA が無効なら、そう伝える
> - **注意**: 401 の OTP チャレンジでは `--otp` を求める。npm と違い、EOTP での対話的な OTP の入力と、2FA を有効にする前の legacy basic 認証から bearer トークンへの変換には対応しない

⏳ 未リリース（v12.13.0 に記載）· トピック: [[repos/pnpm-pnpm/topics/CLI-コマンド|CLI コマンド]]

### package map の設定を `nodePackageMap` にまとめる（[#15671](https://github.com/pnpm/pnpm/pull/15671)）

> [!tip] 何ができるようになったか
> package map の設定をまとめた `nodePackageMap` 設定を pnpm v12 に追加した（[#14937](https://github.com/pnpm/pnpm/issues/14937)）。Node.js の解決方法を変えずに、ほかのツールが pnpm の依存グラフを読めるようになる。
>
> - **使い方**: `nodePackageMap.mode` に `off`（既定）・`write-only`・`load`、`nodePackageMap.type` に `standard`（既定）・`loose`
> - **`write-only`**: isolated・hoisted のインストールで `node_modules/.package-map.json` を書くが、スクリプトに Node の `--experimental-package-map` を付けない
> - **`load`**: `nodeExperimentalPackageMap: true` と同じ。マップを書き、pnpm が管理するスクリプトで Node に読み込ませる
> - **旧設定**: v11.8.0 の `nodeExperimentalPackageMap`・`nodePackageMapType` は非推奨の書き方として引き続き使える。同じ設定元で両方あれば `nodePackageMap` が優先。環境変数は `PNPM_CONFIG_NODE_PACKAGE_MAP_MODE`・`PNPM_CONFIG_NODE_PACKAGE_MAP_TYPE`
> - マップのファイルは初回作成時も一時ファイルと `rename` で書き、読む側が書きかけのファイルを見ないようにした

⏳ 未リリース（v12.13.0 に記載）· トピック: [[repos/pnpm-pnpm/topics/設定|設定]]

### 共有ストア向けのファイル単位のストア索引 `storeIndexFormat: files`（[#16875](https://github.com/pnpm/pnpm/pull/16875)）

> [!tip] 何ができるようになったか
> `storeIndexFormat` 設定を追加した。`files` にすると、ストアのパッケージ索引を SQLite の `index.db` ではなくパッケージごとに 1 ファイルで持つ（置き場所は [#16879](https://github.com/pnpm/pnpm/pull/16879) で `index/` に変更）。
>
> - **嬉しい場面**: CI のキャッシュのように、複数のマシンが同時にマウントするネットワークファイルシステム上のストア。SQLite の WAL の共有メモリとファイルロックは 1 台の中でしか効かず、こうしたストアでは同時インストールで `index.db` が壊れていた
> - **計測（PR 本文、sshfs・遅延 1 ms・約 1,300 パッケージ）**: コールドで `sqlite` 47 秒 / `files` 41 秒、ウォームで 21 秒 / 22 秒。2 ジョブの同時実行では `sqlite` は `index.db` が壊れ、`files` は 1,299 件の索引が無傷

⏳ 未リリース（v12.13.0 に記載）· トピック: [[repos/pnpm-pnpm/topics/ストア|ストア]]

### Python の依存解決で PEP 658 のメタデータファイルを読み、先読みする（[#16881](https://github.com/pnpm/pnpm/pull/16881)）

> [!quote] Before
> Python の依存解決は直列で、ソルバーが求めるたびに索引のページかバージョンのメタデータを 1 つずつ取得していた。メタデータは wheel 全体をダウンロードして取り出していた。

> [!success] After
> 索引が wheel の横に公開するメタデータファイルを、索引ページの SHA-256 で確かめて読む（`python-metadata-v1` にキャッシュ、SHA-256 の無いものや非対応の索引は従来どおり wheel）。さらに、ソルバーが求める前に索引ページと、選ばれそうなバージョンのメタデータを先読みする（`resolver/ahead.rs`）。wheel は選ばれたリリースだけをダウンロードする。

⏳ 未リリース（v12.13.0 に「faster Python dependency resolution」と記載）· トピック: [[repos/pnpm-pnpm/topics/Python-サポート|Python サポート]]

### Python の先読みでのページのエラーが配布物を隠さないように（[#16885](https://github.com/pnpm/pnpm/pull/16885)）

### MinGW 向けの pnpm は MinGW の Rust ツールチェーンを入れる（[#16868](https://github.com/pnpm/pnpm/pull/16868)）

> [!quote] Before
> Windows ではホストのトリプルが `*-pc-windows-msvc` に固定され、MSYS2 のパッケージのような `x86_64-pc-windows-gnu` 向けの pnpm も、使えない MSVC のツールチェーンをダウンロードしていた。

### git の ref の照会をインストールごとに 1 回に（[#16900](https://github.com/pnpm/pnpm/pull/16900)）

> [!quote] Before
> `linkWorkspacePackages` が有効だと解決のキャッシュがプロジェクトごとになり、多くのプロジェクトが共有する git 依存でもプロジェクトごとに `git ls-remote` を実行していた（リモートのリポジトリで 1 プロジェクト約 1 秒）。

> [!success] After
> `GitResolver` が指定子ごとに解決結果を覚える。リゾルバーはインストールごとに作られるので、動くブランチは次のインストールで再度照会する。失敗はキャッシュしない。v11 は変更なし（[#16899](https://github.com/pnpm/pnpm/issues/16899)）。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### 依存かつ任意の peer でもある依存を、浅い出現で決める（[#16903](https://github.com/pnpm/pnpm/pull/16903)）

> [!quote] Before
> `ajv-formats` のように `ajv` を依存と任意の peer の両方に持つパッケージが、11.28.0（[#15503](https://github.com/pnpm/pnpm/pull/15503)）以降、v11 では `ajv` をどちらとしても持たないことがあった。v12 は動くが lockfile が v11 と異なっていた。

> [!success] After
> 浅いほうの出現で peer と依存の両方を決める。issue の再現では両バージョンとも 11.27.1 と同じ lockfile（`ajv-formats@3.0.1(ajv@8.20.0)`）を書く。既存の lockfile で普通の依存として記録済みなら、v12 はそれを保ち、v11 は peer の形に切り替える違いが残る。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/依存関係解決|依存関係解決]]

### 更新チェックが止まっても最新のインストールを待たせない（[#16902](https://github.com/pnpm/pnpm/pull/16902)）

> [!quote] Before
> `pnpm install`・`pnpm add` は日次の更新チェックを終わるまで待ってから `Done in ...` を出していた。接続を受けるが応答しないレジストリ（パケットを捨てるファイアウォールなど）では、何もすることの無いインストールでも接続と読み取りのタイムアウト（各 1 分）を待った（v12 のみ。[#16839](https://github.com/pnpm/pnpm/issues/16839) 関連）。

> [!success] After
> コマンドは更新チェックを待たない。終了時に走っているチェックは中断し、何も記録しないので次のコマンドで再度確認する（v11 と同じ）。`TRACE='pacquet::install=debug'` で最新のインストールの経路が分かるようにした。

⏳ 未リリース · トピック: [[repos/pnpm-pnpm/topics/インストール|インストール]]
